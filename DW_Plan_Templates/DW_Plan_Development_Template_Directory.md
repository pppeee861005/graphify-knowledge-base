# 📁 DW計劃開發模版目錄結構

**目的**：為快速發布新DW計劃提供標準化、可複製的目錄結構
**核心原則**：DW應用優先 | 定義書優於代碼 | 社群參與共好
**基於**：Plan 1（企業HR自動化）的完整驗證

---

## 📋 標準目錄結構

### 完整結構（推薦）

```
計劃X_[應用場景名稱]/
│
├── 📄 README.md ⭐
│   ├─ 文件名：計劃X_[應用場景]/README.md
│   ├─ 內容：DW應用優先導航
│   ├─ 字數：1,500-2,000 字
│   ├─ 說明：三層學習路徑、快速開始、常見問題
│   └─ 用途：讓所有人（CEO到開發者）快速理解
│
├── 📚 核心文檔（4份，新建）
│   │
│   ├─ 計劃X_[應用]定義書.md ⭐
│   │  ├─ 內容：完整業務邏輯定義
│   │  ├─ 字數：5,000-8,000 字
│   │  ├─ 結構：問題定義 → 核心場景（2-3個） → 驗證標準 → 執行策略 → 預算
│   │  ├─ 核心：決策規則用「若...則...」邏輯
│   │  ├─ 可修改性：✅ 任何人都能修改（無需技術背景）
│   │  └─ 用途：定義清晰，供Claude Code自動生成Workflow
│   │
│   ├─ 計劃X_[應用]預算控制書.md ⭐
│   │  ├─ 內容：成本估算、監控、ROI分析
│   │  ├─ 字數：3,000-4,000 字
│   │  ├─ 結構：成本估算 → 預期收益 → ROI分析 → 監控策略 → 優化方案
│   │  ├─ 核心：投資回報率 ≥300%，回報期 <3個月
│   │  └─ 用途：透明化成本和效益，助力決策
│   │
│   ├─ 計劃X_如何用Claude Code自動生成Workflow.md ⭐
│   │  ├─ 內容：5步教學 + 進階技巧 + 案例演練
│   │  ├─ 字數：4,000-7,000 字
│   │  ├─ 結構：
│   │  │  - Part 1：5步快速教學（20分鐘）
│   │  │  - Part 2：進階技巧（15分鐘）
│   │  │  - Part 3：2-3個真實案例演練
│   │  │  - Part 4：常見問題解答
│   │  ├─ 核心：「複製→修改→提交→執行→分享」的完整流程
│   │  └─ 用途：教用戶能力轉移，激發社群參與
│   │
│   └─ (可選) 計劃X_決策清單.md
│      ├─ 內容：5點確認清單 + GO/MODIFY/HOLD/CANCEL框架
│      ├─ 字數：2,000-3,000 字
│      └─ 用途：快速決策，確認執行方向
│
├── 📁 reference_implementations/（代碼參考實現，新建）
│   │
│   ├─ README.md
│   │  ├─ 內容：「為什麼看這些代碼」說明
│   │  ├─ 說明：三種使用方式（學習、改進、重新實現）
│   │  ├─ 說明：代碼是參考，不是必須複製的內容
│   │  └─ 說明：開發者如何貢獻多語言實現
│   │
│   ├─ [reference_implementation_1].js
│   │  ├─ 說明：複製自src/workflows/或原始代碼
│   │  ├─ 添加：簡短的代碼說明（5-10行註釋）
│   │  └─ 標記：「參考實現，非必須」

│   └─ [reference_implementation_2].js

│   │
│   ├─ 與定義書的映射.md

│   │  └─ 說明：為什麼這個架構是最優的
│   │
```

## 🚀 快速建立步驟

### Step 1：準備基礎結構（10分鐘）

```bash
# 創建主目錄
mkdir 計劃X_[應用場景名稱]
cd 計劃X_[應用場景名稱]

# 創建子目錄
mkdir reference_implementations notes other_creators_workflows

# 創建基本文件
touch README.md
touch 計劃X_[應用]定義書.md
touch 計劃X_[應用]預算控制書.md
touch 計劃X_如何用Claude Code自動生成Workflow.md
touch reference_implementations/README.md
```

### Step 2：填寫核心文檔（5-7天）

使用 `DW_Plan_Quick_Template.md` 快速生成框架：

```markdown
Day 1-2：定義書 + 預算書
  ├─ 收集業務需求
  ├─ 定義2-3個核心場景
  ├─ 設計決策規則（若...則...邏輯）
  └─ 估算成本和ROI

Day 2-3：README + 教學指南
  ├─ 完成README（三層學習路徑）
  ├─ 編寫5步快速教學
  ├─ 準備2-3個實際案例
  └─ 添加常見問題

Day 3-4：代碼整理
  ├─ 複製參考實現到reference_implementations/
  ├─ 添加簡短說明
  ├─ 建立映射文檔（代碼 ↔ 定義書）
  └─ 建立社群貢獻指南

Day 4-5：測試和完善
  ├─ 驗證定義書的完整性
  ├─ 測試教學案例的可執行性
  ├─ 完成所有文檔的交叉引用
  └─ 建立社群貢獻目錄

Day 5：提交
  ├─ git add + git commit
  ├─ 推送到GitHub（計劃X倉庫）
  └─ 更新主倉庫連接
```

### Step 3：建立Git倉庫結構

```bash
# 在GitHub建立
計劃X_[應用場景名稱] （公開倉庫）
  ├─ main分支 → 上述目錄結構
  └─ contributing分支 → 社群參與

# 在主倉庫中
graphify-knowledge-base/
  ├─ 計劃X_[應用場景名稱]/ → 子倉庫引用
  └─ PLAN_X_README.md → 計劃導航
```

## 💡 常見誤區

### ❌ 誤區1：代碼優於定義書
```
❌ 「先完成300行代碼再寫定義書」
✅ 「先完成定義書，代碼是參考實現」
```

### ❌ 誤區2：定義書預先設計Stages
```
❌ 「Stage 1用Haiku，Stage 2用Sonnet...」
✅ 「需要檢查XYZ，Claude Code決定如何檢查」
```

### ❌ 誤區3：忽視reference_implementations說明
```
❌ 「直接放代碼文件」
✅ 「添加README說明為什麼看這些代碼」
```

### ❌ 誤區4：沒有預留社群貢獻空間
```
❌ 「這是最終版本，不需要改進」
✅ 「預留other_creators_workflows/給社群改進」
```
