# 📋 DW 計劃生成與用戶確認模板

## 🎯 核心目的

當用戶提出任何 DW 應用需求時，不要直接執行，而是：

```
用戶需求
  ↓
Claude 生成詳細計劃 ⭐（本模板）
  ↓
用戶確認所有細節
  ↓
Claude 執行計劃
  ↓
完成並反饋
```

**核心原則**：透明、可控、可複用

## 📐 計劃生成的四大維度

### 1️⃣ 執行流程分解

```markdown
## 執行流程分解

我會按以下順序執行，每個步驟都是獨立的：

### 環節 1：[具體描述]（預計 X 分鐘）
**目標**：[什麼目標]
**方法**：[怎麼做]
**輸出**：[產生什麼]
**風險**：[可能出問題的地方]

### 環節 2：[具體描述]（預計 X 分鐘）
...

### 環節 N：[最後環節]（預計 X 分鐘）
...

**流程說明**：
- 整個流程是線性的（前一步必須完成才能做下一步）
- 或者是並行的（多個步驟可以同時進行）
- 預計總耗時：X 分鐘（標準）～ Y 分鐘（最悲觀）
```

### 2️⃣ 成本明細清單

```markdown
## 成本明細清單

根據定義書，我估算本次執行的成本如下：

| 環節 | 操作 | 預期成本 | 風險 | 說明 |
|------|------|---------|------|------|
| 環節 1 | [操作] | 0.XX | 低 | [成本說明] |
| 環節 2 | [操作] | 0.XX | 中 | [成本說明] |
| 環節 3 | [操作] | 0.XX | 低 | [成本說明] |
| **合計** | | **0.XX** | | |

**預算分配**：
- 預計成本：0.XX 單位
- 預算額度：0.XX 單位（你指定的）
- 預留緩沖：0.XX 單位（約 30%）
- 超支風險：低（充足的預留）

**成本可能超支的原因**：
1. [原因 1]：如果發生，可能增加 0.XX 成本
2. [原因 2]：如果發生，可能增加 0.XX 成本
3. [原因 3]：如果發生，可能增加 0.XX 成本
```

### 3️⃣ 時間進度預估

```markdown
## 時間進度預估

我按以下時間表執行：

| 環節 | 最樂觀 | 標準 | 最悲觀 | 備註 |
|------|--------|------|--------|------|
| 環節 1 | 2 min | 5 min | 8 min | 數據來源可能慢 |
| 環節 2 | 2 min | 3 min | 5 min | 標準 |
| 環節 3 | 3 min | 3 min | 3 min | 固定時間 |
| **總計** | **7 min** | **11 min** | **16 min** | |

**預計耗時說明**：
- **標準情況**：11 分鐘（最有可能）
- **樂觀情況**：7 分鐘（一切順利）
- **悲觀情況**：16 分鐘（遇到多個延遲）

**可能的延遲因素**：
1. [因素 1]：+X 分鐘，發生概率 10%
2. [因素 2]：+X 分鐘，發生概率 15%
3. [因素 3]：+X 分鐘，發生概率 5%

**應對方案**：
- 如果超過 X 分鐘，我會提前通知
- 如果發生 [特殊情況]，我會啟用備用方案
```

### 4️⃣ 風險評估表

```markdown
## 風險評估表

在執行過程中可能遇到的風險：

| # | 風險 | 級別 | 概率 | 影響 | 應對方案 |
|----|------|------|------|------|---------|
| 1 | [風險 1] | 中 | 20% | 延遲 X 分鐘 | [方案] |
| 2 | [風險 2] | 低 | 10% | 結果精度降 10% | [方案] |
| 3 | [風險 3] | 高 | 5% | 可能無法完成 | [方案] |
| 4 | [風險 4] | 低 | 30% | 結果準確度降低 | [方案] |
| 5 | [風險 5] | 中 | 15% | 成本超支 | [方案] |

**風險級別說明**：
- **低**：不影響最終結論，或有充分應對方案
- **中**：可能有輕微影響，但可控
- **高**：可能顯著影響結論，需要特別關注

**最重要的 3 個風險**：
1. [最高風險]：雖然概率只有 X%，但如果發生影響很大，應對方案是 [...]
2. [次高風險]：[...]
3. [其他風險]：[...]
```

## ✅ 用戶確認清單

在我開始執行前，請確認以下內容：

### A. 執行流程 - 確認順序和內容

```
□ 我理解執行的 5 個環節（或更多）
□ 這個順序對我來說有意義
□ 我不需要調整任何環節
□ 或者，我想調整：[具體調整]
```

**如果要調整**：
- 是否需要增加/移除環節？
- 是否需要改變順序？
- 是否需要在某個環節花更多/更少時間？

### B. 成本預算 - 確認花費合理

```
□ 預計成本 0.XX 對我來說合理
□ 預留緩沖 0.XX 足夠
□ 我同意最多花 0.XX 單位
□ 或者，我想改為：0.XX 單位
```

**如果成本太高**：
- 我可以簡化分析流程，可能減少成本但也會降低精度
- 我可以調整優先級，聚焦在最重要的維度

**如果預算有限**：
- 我會先優化成本高的環節
- 或者，我們可以分兩次執行

### C. 時間進度 - 確認能夠接受

```
□ 標準耗時 X 分鐘可以接受
□ 我能等待最多 Y 分鐘（最悲觀情況）
□ 如果超過 Z 分鐘，我需要提前知道
□ 或者，我需要加快速度：不超過 X 分鐘
```

**如果時間太長**：
- 我可以並行某些環節，可能減少耗時
- 我可以降低精度以加快速度
- 我們可以分次執行

**如果時間緊張**：
- 我會實時報告進度
- 我可以優先執行最重要的部分

### D. 風險評估 - 確認可以接受

```
□ 我理解 5 個主要風險
□ 我接受這些風險和應對方案
□ 最高風險「[風險]」，我知道應對方案是「[方案]」
□ 或者，我特別關心：[額外的風險點]
```

**如果對風險有疑慮**：
- 我可以解釋每個風險的詳細信息
- 我可以加強某個環節來降低風險（但可能增加成本）
- 我們可以先做一個小範圍的試點

### E. 最終確認 - 準備執行或調整

```
□ 以上四個維度我全都確認了，可以開始執行
□ 或者，我想調整，等我給意見
□ 或者，我需要更詳細的解釋，尤其是 [項]
□ 或者，我暫時不執行，我需要時間思考
```

## 💬 用戶的可能回應及我的應對

### 回應 1️⃣：「完全同意，按這個計劃執行」

```
我會：
✅ 立即開始執行
✅ 每 5 分鐘報告一次進度
✅ 如果發現超支/延遲，立即通知
✅ 執行完後生成最終報告
✅ 給你下一步建議
```

### 回應 2️⃣：「大體同意，但我想改 [具體項]」

```
我會：
1️⃣ 接收你的修改需求
2️⃣ 重新計算影響（成本/時間/風險）
3️⃣ 生成「調整後的新計劃」
4️⃣ 再次確認（回到確認清單）
5️⃣ 獲得二次確認後，立即執行

常見改變：
• 「我只能花 0.15，能簡化嗎？」
  → 我會簡化分析流程，調整成本

• 「能在 10 分鐘內完成嗎？」
  → 我會並行某些環節，可能降低精度

• 「我特別關心現金流，能深入嗎？」
  → 我會加強財務分析，調整成本和時間
```

### 回應 3️⃣：「能詳細解釋 [項] 嗎？」

```
我會：
1️⃣ 深度解釋該項（舉例、公式、對比）
2️⃣ 回答你的所有疑問
3️⃣ 確保你完全理解
4️⃣ 回到確認清單，再次確認

常見問題：
• 「環節 2 具體怎麼評估？」
  → 我會詳細說明評分邏輯、數據來源、計算公式

• 「為什麼需要預留 0.10？」
  → 我會舉過往案例說明超支的具體情況

• 「風險 3 影響多大？」
  → 我會用數字說明：「如果發生，評分可能偏差 ±10%」
```

### 回應 4️⃣：「暫停，我要重新檢查需求」

```
我會：
✅ 保存本計劃（Markdown 格式）
✅ 告訴你計劃文件位置
✅ 等待你重新提交需求
✅ 你再次提交後，從步驟 4.5 重新開始

保存格式：
計劃_[應用場景]_[時間戳].md
例如：計劃_三維獵殺_AAAA_20260605_143002.md
```

## 💡 設計理念

### 為什麼需要「計劃生成」這一步？

```
❌ 老模式：直接執行
用戶提需求 → Claude 直接執行 → 可能不符預期 → 後悔

✅ 新模式：計劃確認後執行
用戶提需求 → Claude 生成計劃 → 用戶確認 → 執行 → 滿意

新模式的 4 大好處：
1. 用戶完全掌握執行過程（透明）
2. 提前發現問題（成本、時間、風險）
3. 提高決策自信度（理解 + 認可）
4. 建立信任（不偷偷摸摸地執行）
```

### 最佳實踐

#### ✅ 應該做的

- 生成清晰、詳細、可驗證的計劃
- 用結構化表格展示成本、時間、風險
- 給用戶明確的「四步確認清單」
- 根據用戶反饋快速調整計劃
- 保存計劃供日後複用

#### ❌ 不應該做的

- 生成模糊的、容易誤解的計劃
- 隱藏成本或風險估算
- 如果用戶沒有明確說「執行」，就不要執行
- 修改計劃後不再次確認
- 計劃和實際執行出現大的偏差

## 📌 用戶應該如何與Claude Code溝通

### 🔴 關鍵：用戶的明確指令

當用戶提出需求時，應該包含以下明確指示：

```
「我想用[場景]驗證/監控[對象]，[具體參數]，預算[金額]。

⚠️ 請先生成詳細的Workflow計劃，包含：
• 執行流程分解（每個環節的具體步驟）
• 成本明細清單（逐項成本和風險評估）
• 時間進度預估（樂觀/標準/悲觀耗時）
• 風險評估表（潛在風險和應對方案）

然後提供用戶確認清單（A-E五個層面），
等我確認無誤後再開始執行，
不要直接執行分析。」
```

### 強制規則（Claude Code必須遵守）

✅ **先生成計劃，絕不直接執行**
✅ **提供完整的「用戶確認清單」**
✅ **等待用戶明確說「確認無誤」或「可以執行」**
✅ **如果用戶要求修改，生成調整後的新計劃再次確認**
✅ **只有用戶二次確認後才開始執行**

**為什麼需要這樣做？**
- 確保Claude理解「計劃優先於執行」的原則
- 防止Claude在未經確認就開始執行
- 給用戶完全的控制權和決策權
- 確保決策質量和用戶滿意度

## 🔗 使用場景

### 場景 1：用戶提出特定分析需求

```
用戶：「我想用三維獵殺驗證股票 AAAA，買入價位是 150 元，特別關心現金流，預算 0.25 單位。

⚠️ 請先生成詳細的Workflow計劃，包含：
• 執行流程分解
• 成本明細清單
• 時間進度預估
• 風險評估表

然後提供用戶確認清單，等我確認無誤後再開始執行，不要直接執行分析。」

Claude Code的回應：
1. 生成詳細計劃（4 大維度）
2. 展示確認清單
3. 等待用戶確認
4. 用戶確認後執行
```

### 場景 2：用戶要求評估多個對象

```
用戶：「幫我評估這 5 個候選人，用人才評估 Workflow。」

我的回應：
1. 評估成本：是否需要 1 個計劃還是 5 個計劃？
   → 通常用 1 個計劃搞定 5 個候選人（因為有複用成本）
2. 生成計劃
3. 用戶確認
4. 執行並生成 5 個評估報告
```

### 場景 3：複雜流程組合

```
用戶：「先用蜂群覺醒發現機會，再用三維獵殺驗證，最後用新聞獵手監控。」

我的回應：
1. 識別這是一個「多步驟流程」
2. 生成「複合計劃」：
   - 步驟 1：蜂群覺醒計劃
   - 步驟 2：三維獵殺計劃（基於步驟 1 的結果）
   - 步驟 3：新聞獵手計劃（長期監控）
3. 總成本估算 + 總時間估算
4. 用戶確認整個流程
5. 執行
```
