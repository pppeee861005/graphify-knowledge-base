# Claude Agent 四層架構深度提練報告
## 用生活場景理解計畫持有權

---

## 核心洞察：「誰持有計畫？」

### 🔑 一個問題，四層答案

在日常生活中，**計畫的持有權** 決定了協作的方式：

| 場景 | 計畫持有者 | 角色設定 | 應用層級 |
|------|----------|--------|--------|
| 家庭烹飪 | 主廚（你） | 主人翁 + 幫手們 | **L1 Subagents** |
| 多個廚房同步 | 你（人類監督） | 中央監控台 | **L1.5 Agent View** |
| 施工隊協作 | 工頭 + 各班組 | 平等議論 + 互相檢查 | **L2 Agent Teams** |
| 大規模工廠流程 | 流程本身（代碼） | 自動化機器 | **L3 Dynamic Workflows** |

**重要原則**：這四層不是「選哪一個」，而是「能力逐級升級」。

---

## 📊 四層架構完整對比 & 生活化解釋

### **第一層：Subagents（廚房型協作）**

#### 🏠 生活場景：家庭烹飪

你是主廚，決定每一步：
- **你決定**：先炒洋蔥、再加肉、最後調味
- **幫手們做**：你說「切菜」，他們就切；說「炒鍋」，他們就炒
- **你收集結果**：每一步的成品（炒好的洋蔥、煮熟的肉）都回到你手裡
- **下一步決策**：你看著中間產物，決定下一步怎麼辦

#### 🔧 技術對應

| 維度 | 說明 |
|------|------|
| **持有計畫的人** | Claude（每回合決定） |
| **代理者角色** | Subagent（worker） |
| **決策方式** | Claude 逐回合指派 |
| **中間結果放在哪** | Claude 的 context window（你眼前） |
| **規模上限** | 每回合少量任務（10-20 個） |
| **成本效率** | ⭐⭐⭐⭐⭐ 最高 |
| **人工干預** | 🤝 經常需要 |

#### 💡 什麼時候用
- ✅ 複雜但短期的任務（寫一篇文章、調試一個 bug）
- ✅ 需要頻繁調整方向（邊做邊想）
- ✅ 不著急（token 效率最重要）
- ✅ 單人或小組決策

#### ⚠️ 什麼時候不適合
- ❌ 任務太多（超過 20 個 subagent）
- ❌ 需要完全自動化（你要一直盯著）
- ❌ 中間產物會爆掉 context

---

### **第 1.5 層：Agent View（多廚房監控）**

#### 📡 生活場景：監管多個廚房

你經營了三個餐廳：
- **廚房 A** 在做意大利面
- **廚房 B** 在做日本料理
- **廚房 C** 在做中餐
- **你的角色**：中央控制室，可以看到三個廚房同時進行
- **監控方式**：實時儀表板，看到每個廚房的進度
- **干預方式**：可以隨時跳進任一廚房，直接和主廚談

#### 🔧 技術對應

| 維度 | 說明 |
|------|------|
| **持有計畫的人** | 你（人類監控多個 session） |
| **代理者角色** | 多個獨立的 background agent |
| **決策方式** | 你決定看哪個、何時介入 |
| **中間結果放在哪** | 各 session 獨立存在 |
| **核心能力** | 可 attach 進任一 agent 對話 |
| **版本要求** | v2.1.139+ |
| **人工干預** | 🤝 需要人類監督 |

#### 💡 什麼時候用
- ✅ 多個長期運行的任務（發文章、監控系統、持續創作）
- ✅ 任務間相對獨立（不需要互相協作）
- ✅ 你想要可視化控制（看進度，隨時介入）
- ✅ 並行但獨立的工作流

#### ⚠️ 什麼時候不適合
- ❌ 需要各任務間協作
- ❌ 需要完全自動化（無人監督）

---

### **第二層：Agent Teams（施工隊型協作）**

#### 🏗️ 生活場景：建築施工隊

一個工程，有不同專業的班組：
- **工頭**（Lead Agent）決定大方向：先打地基、再框架、再裝修
- **各班組**（Peer Agents）：地基班、框架班、電工班、水工班
- **特殊點**：
  - 電工班發現梁的位置不對，可以直接告訴框架班，不用繞過工頭
  - 水工班和電工班可以互相討論管線走向
  - 工頭不用參與每個細節，只監督整體進度
- **共享任務清單**：所有班組都能看到任務板，知道誰在做什麼

#### 🔧 技術對應

| 維度 | 說明 |
|------|------|
| **持有計畫的人** | Lead Agent（逐回合決策） |
| **代理者角色** | Peer sessions（平等的協作者） |
| **通訊方式** | 真正的 peer-to-peer（可直接通訊） |
| **中間結果放在哪** | 共享任務清單（task board） |
| **規模** | 少數長時間運行的 peers（3-10 個） |
| **狀態** | 🔬 實驗性功能 |
| **成本代價** | ⚠️ Token 消耗遠高於 L1 |

#### 💡 什麼時候用
- ✅ 多人協作的複雜項目（前後端分離的大重構）
- ✅ 各方需要互相溝通和檢查（測試 vs 開發 vs 設計）
- ✅ 任務不是序列而是並行（各自獨立但相關）
- ✅ 需要對等的決策權（不是 boss-worker 模式）

#### ⚠️ 什麼時候不適合
- ❌ 序列任務（A 必須做完 B 才能做）
- ❌ 同檔案編輯（衝突太多）
- ❌ 高依賴性工作（互相等待）
- ❌ Token 預算緊張（太費）

#### 🎯 特別提醒
**Agent Teams 的核心優勢**：peer-to-peer 通訊
- 不是傳統的樹狀 hierarchy（工頭 → 班組 → 工人）
- 是真正的 peer network（班組可直接協商）
- 你可以 attach 進任一 teammate session，直接對話

### **第三層：Dynamic Workflows（工廠自動化）**

#### 🏭 生活場景：工廠流水線

一個大型汽車工廠：
- **計畫寫在代碼裡**：流程不變（模具位置、焊接順序、檢查標準）
- **機器執行計畫**：不需要人在旁邊指揮，機器自己知道做什麼
- **規模驚人**：
  - 一次可以同時製造 500 台車
  - 每台車要經過 200+ 道工序
  - 完全無人化（或者最少人化）
- **中間產物**：不再存在每個環節的細節，只有最終成品報告
- **容錯機制**：質檢機器人相互對抗審查，有問題的車會被隔離重檢

#### 🔧 技術對應

| 維度 | 說明 |
|------|------|
| **持有計畫的人** | Script（程式碼本身） |
| **執行者** | Runtime（自動執行） |
| **決策方式** | 完全自動化（無人干預） |
| **中間結果放在哪** | 存在 script 變數（不佔 context） |
| **規模能力** | 📈 數十到數百個 agents |
| **並發限制** | 16 個同時執行 |
| **總量限制** | 1,000 agents per run |
| **狀態** | 🔬 研究預覽 |
| **成本代價** | 🚀 最貴（大規模執行） |

#### 💡 什麼時候用
- ✅ 超大規模任務（100+ agents）
- ✅ 完全可預測的流程（不需要人工調整）
- ✅ 需要質量保證（對抗性審查）
- ✅ 長期自動化運行（無人監督）
- ✅ 內容生成、大規模研究、系統部署

#### ⚠️ 什麼時候不適合
- ❌ 任務需要頻繁調整（計畫寫死了）
- ❌ 規模小於 100 agents（太費 token）
- ❌ 需要人工干預（自動化程度不夠）

#### 🔗 與 stock-swarm-wf 的關係
你的 npm 套件是**框架層**，Dynamic Workflows 是**應用層**：
- 官方 WF：Claude 動態寫 JS → runtime 執行（一次性用）
- 你的 WF：TypeScript 寫死編排 → npm 發布 → 任何人重複用

**兩者都在 L3，但你的更可發布、更可重複、更可控。**

## 🌳 決策樹：應該用哪一層？

```
開始
  │
  ├─ 「誰來決定下一步？」
  │
  ├─ 1️⃣ 我（Claude）逐回合決定
  │   └─ 「有多個獨立的長期任務嗎？」
  │       ├─ 否 → 用 L1 Subagents ⭐
  │       │        (家庭廚房)
  │       │
  │       └─ 是 → 用 L1.5 Agent View 📡
  │                (多廚房監控台)
  │
  ├─ 2️⃣ 我的團隊（Lead + Peers）協商決定
  │   └─ 用 L2 Agent Teams 🏗️
  │        (施工隊)
  │        ⚠️ 實驗性功能，token 很費
  │
  └─ 3️⃣ 流程本身（代碼）自動決定
      └─ 「規模有多大？」
          ├─ < 100 agents → 考慮 L1/L2
          │
          └─ >= 100 agents → 用 L3 Workflows 🏭
                             (工廠自動化)
                             需要 v2.1.154+
```

## 🎓 層級升級的真實成本

### 複雜度 vs 效率 vs 成本

```
Layer  │ 控制權  │ 靈活度 │ Token成本 │ 易用度 │ 規模
────────┼────────┼────────┼─────────┼────────┼──────
L1     │ 最高   │ ⭐⭐⭐⭐ │ 低      │ ⭐⭐⭐⭐⭐│ 小
L1.5   │ 中高   │ ⭐⭐⭐  │ 中低    │ ⭐⭐⭐⭐  │ 中
L2     │ 中     │ ⭐⭐   │ 很高    │ ⭐⭐⭐   │ 中
L3     │ 最低   │ ⭐     │ 最高    │ ⭐⭐   │ 超大
```

### 實踐建議

| 場景 | 推薦層級 | 理由 |
|------|---------|------|
| 寫一篇文章 | L1 | 短期、反覆調整 |
| 維護多個 blog | L1.5 | 並行但獨立 |
| 大型重構（3 人） | L2 | 需要互相檢查 |
| 批量生成 1000 文章 | L3 | 超大規模、預定義 |
| 快速原型 | L1 | 最快反饋迴圈 |
| 長期監控系統 | L1.5 | 可視化+人工介入 |

## 🔑 核心設計原則

### **計畫持有權 → 信息流 → 架構選擇**

```
計畫持有者        信息流方向        適用架構
───────────────────────────────────────────────
Claude          上報 → Claude → 決策   L1 Subagents
人類            監看 + 介入             L1.5 Agent View
Team Lead       協商 + 共享任務清單    L2 Agent Teams
Script/Code     自動執行 + 變數存儲    L3 Workflows
```

### **四層是能力升級，不是選擇替代**

- **L1 基礎**：其他層都建立在 L1 的能力上
  - Subagent 是最基本的 agent 單位
  - 所有高層都由多個 subagent 組成

- **L1.5 擴展人類**：給你多個 subagent 的監控能力
  - 多廚房 vs 單廚房

- **L2 添加協作**：Subagents 變成了 peers（可互通訊）
  - 從 worker 升級到 colleague
  - 引入共享任務清單

- **L3 啟用自動化**：計畫不再在 Claude context，在代碼中
  - 從逐回合決策 → 全自動執行
  - 規模從 10-20 → 1000+

## 📚 延伸思考

### 「誰持有計畫」的本質

這個問題不只是技術架構，還反映了**協作的本質**：

1. **L1（你持有計畫）**
   - 最靈活，但最累（你要時刻決策）
   - 適合創意工作（每步都可能改主意）

2. **L1.5（你監控多個計畫）**
   - 平衡點，你不干預細節，只看全局
   - 適合管理性工作（多項目並行）

3. **L2（團隊持有計畫）**
   - 真正的協作，計畫是集體智慧
   - 適合複雜工程（需要多角度檢查）

4. **L3（代碼持有計畫）**
   - 完全自動化，計畫即規則
   - 適合標準化流程（重複執行）

**最深的洞察**：隨著層級上升，人的角色從「執行者」變成「設計者」。

## 🎯 總結

Claude Agent 四層架構的核心：
- **不是功能列表**，而是**協作模式**
- **不是互相替代**，而是**能力升級**
- **不是一個永遠的選擇**，而是**根據任務動態切換**

記住「計畫持有權」這個金鑰問題，其他一切都迎刃而解。
