# 端到端圖文連載製作人 Skill

## 文件定位

這是一份**如何設計未來 Skill 的推薦方法論**，不是正式 `SKILL.md`，也不代表 Skill 已建立、安裝或啟用。

它的用途是先定義：

- 這個 Skill 應該解決什麼問題。
- 什麼情況應該觸發。
- 如何從現有產物接續工作。
- 哪些階段可以自動推進。
- 哪些決策必須回到作者。
- 未來應如何驗證它真的可以跨專案復用。

本方法論建立於：[豪力風神圖文連載工作流 V0.1.md](豪力風神圖文連載工作流%20V0.1.md)

---

## 一、推薦定位：工作流協調器，不是萬能寫作器

推薦把它設計成一個端到端的**圖文連載工作流協調器**。

它不是只負責寫稿，也不是只負責生圖。它要理解使用者現在位於哪一個創作階段，調用適合的寫作、研究、視覺與圖片生成能力，並把每一階段的結果保存為可接續的檔案。

### 一句話 Skill 契約

> 給我一份模糊手稿或任何階段的文章產物，協助我判斷作品規模、完成文字與視覺敘事，最後交付可驗收的圖文稿；保留作者的聲音、事實責任與最終決定權。

### 推薦名稱

- 技術名稱：`build-illustrated-series`
- 中文顯示名稱：意圖到圖文連載
- 建議中文指令：`/圖文連載`

名稱使用動詞開頭，直接表明 Skill 的工作是「建立圖文系列」。

---

## 二、Skill 的適用範圍

### 應該處理

- 將手稿、語音整理稿或零散筆記發展成文章。
- 判斷內容應保持單篇、拆成上下篇或發展成系列。
- 建立系列 Plan 與單篇文章藍圖。
- 將草稿修成正文，同時保留作者聲音。
- 根據正文設計配圖敘事，而非只做字面插畫。
- 將配圖意境轉成可執行 Prompt。
- 在使用者要求時生成圖片並保存到專案。
- 組裝圖文稿、Alt Text 與系列導航。
- 從既有中間產物繼續，而不是每次從頭開始。

### 不應自動處理

- 未經授權對外發布、寄送或建立公開草稿。
- 覆寫原始手稿或作者已確認的正文。
- 把未驗證的案例、數據與產品能力寫成事實。
- 為了符合流程而強迫所有題材拆成系列。
- 為了湊數固定生成三張圖片。
- 將作者語氣統一成某種平均化的 AI 文風。
- 在使用者只要求局部工作時，擅自重做整條流程。

## 三、觸發設計方法

Skill 的 `description` 是最重要的觸發機制，必須同時寫清楚「做什麼」與「何時使用」。

### 未來可參考的 Frontmatter 草案

> 下列內容只是方法論中的草案，不是已安裝 Skill。

```yaml
---
name: build-illustrated-series
description: 將模糊手稿、零散筆記或既有文章產物發展成完整單篇或圖文連載系列。負責判斷單篇與系列規模、建立系列和單篇計畫、撰寫草稿與正文、依文意設計視覺敘事、產生逐圖 Prompt、生成圖片並組裝可發布圖文稿。當使用者要求把手稿做成文章、連載、圖文系列，要求從現有草稿或配圖計畫繼續，或使用「/圖文連載」時使用。
---
```

### 自然語言觸發例

- 「把這份手稿發展成圖文系列。」
- 「這個想法應該寫成一篇還是一季？」
- 「依照第三篇正文設計配圖。」
- 「根據配圖 Plan 生成這一篇的圖片。」
- 「把正文和三張圖組成發布版。」
- 「從上次完成的系列 Plan 繼續。」

觸發不能只綁定斜線指令，否則使用者用自然語言描述同一需求時可能無法啟動。

## 四、最重要的能力：先辨認目前所處階段

端到端不代表每次都從第一步開始。Skill 應先盤點現有檔案，從**最遠且已確認的產物**接續。

### 狀態辨認表

| 現有輸入 | 推定階段 | 建議下一步 |
|---|---|---|
| 只有手稿或筆記 | 意圖探索 | 整理命題並判斷規模 |
| 已有系列 Plan | 系列架構完成 | 選定單篇並建立藍圖 |
| 已有單篇草稿 | 文字發展中 | 修訂為正文 |
| 已有穩定正文 | 文字完成 | 建立配圖 Plan |
| 已有配圖 Plan | 視覺定義完成 | 生成逐圖 Prompt |
| 已有 Prompt | 圖片規格完成 | 在明確要求下生成圖片 |
| 已有正文與圖片 | 素材完成 | 組裝圖文發布版 |
| 已有發布版 | 待驗收 | 檢查事實、圖文節奏、導航與平台格式 |

### 接續原則

1. 先讀取現有產物與狀態標記。
2. 不重做已確認階段，除非使用者明確要求重新評估。
3. 若上游文件與下游成品互相衝突，指出差異並詢問以哪一份為準。
4. 若檔名不標準，依內容判斷，不因命名不同就忽略有效成果。
5. 長系列需要保存接續點，避免跨會話遺失決策。

## 五、推薦的內部工作狀態

未來 Skill 可採用七個狀態，但允許由任一狀態開始：

```text
DISCOVER  接住原始意圖
    ↓
SCOPE     判斷單篇或系列
    ↓
PLAN      建立系列與單篇架構
    ↓
WRITE     草稿發展為正文
    ↓
VISUAL    文意轉譯為配圖計畫
    ↓
GENERATE  Prompt 轉譯與圖片生成
    ↓
ASSEMBLE  圖文組裝與驗收
```

每個狀態都需要明確的輸入、輸出、完成條件與下一步，避免 Skill 一次做完所有事情卻無法回溯。

## 六、人類決策關卡的設計

Skill 應自動處理繁瑣工作，但在會改變作品方向或產生外部影響的位置停下。

### 必須確認的關卡

#### 1. 規模確認

AI 提出單篇、上下篇或系列建議，附上理由與替代方案。作者確認後才大量生成篇章。

#### 2. 系列架構確認

確認核心命題、篇數、每篇問題與敘事順序。避免在錯誤架構上一次生成八篇。

#### 3. 正文語意確認

確認單篇真正想說的事情已穩定，才開始設計視覺。

#### 4. 視覺方向確認

先確認配圖意境，再轉 Prompt 與生圖。改文字 Plan 比反覆重生圖片更快、更便宜。

#### 5. 發布確認

完成圖文稿不代表可以公開。發布、寄送、排程與建立平台草稿都需要明確指令。

### 不必逐步詢問的地方

- 讀取專案內相關文件。
- 整理命題、建立候選方案與檢查清單。
- 依已確認 Plan 生成單篇草稿。
- 依已確認配圖 Plan 撰寫 Prompt。
- 驗證檔案命名、圖片尺寸與 Markdown 連結。

Skill 應把作者注意力留給真正需要品味與責任的決策。

## 七、不同工作應採用不同自由度

依 Skill 設計原則，不應把所有步驟寫成同樣嚴格的指令。

| 工作 | 建議自由度 | 原因 |
|---|---|---|
| 判讀原稿與提煉命題 | 高 | 需要理解語境、作者個性與隱含思想 |
| 單篇或系列判斷 | 高 | 必須依內容密度與敘事關係判斷 |
| 文章與視覺創作 | 高 | 多種做法可能同樣有效 |
| 系列 Plan 與 Prompt 結構 | 中 | 有推薦欄位，但內容應隨題材改變 |
| 檔案命名與輸出位置 | 中低 | 一致性可減少後續混亂 |
| 原稿保護、事實標記、發布授權 | 低 | 出錯會造成不可逆或信任風險 |
| 圖片驗證與連結檢查 | 低 | 可使用固定檢查規則 |

這能避免兩個極端：既不把創作寫成僵硬流水線，也不讓高風險操作只靠臨場發揮。

## 八、推薦的 Skill 資源架構

若未來正式建立，建議使用以下結構：

```text
build-illustrated-series/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── scope-decision.md
│   ├── article-development.md
│   ├── visual-storytelling.md
│   ├── factual-integrity.md
│   └── quality-gates.md
└── assets/
    ├── series-plan-template.md
    ├── episode-plan-template.md
    ├── visual-plan-template.md
    ├── image-prompt-template.md
    └── illustrated-article-template.md
```

### `SKILL.md` 應保存

- 核心工作流。
- 狀態辨認與接續規則。
- 階段選擇方式。
- 人類決策關卡。
- 必須遵守的安全與品質原則。
- 何時讀取哪一份 reference 或使用哪一份 template。

### `references/` 應保存

- 單篇與系列的判斷準則。
- 從手稿到正文的發展方法。
- 視覺寓言與三種圖片職責。
- 事實、推論與未來想像的區分。
- 各階段品質門檻與失敗處理。

### `assets/` 應保存

可被複製到新專案的 Markdown 模板。模板只提供欄位與結構，不綁定《AI 即一切》的內容、篇數、色彩或意象。

### 第一版暫不需要 `scripts/`

這套工作流的核心仍是判斷與創作，第一版使用文字指引與模板即可。只有在多次使用後，確定以下機械工作反覆出現，再加入腳本：

- 建立標準專案目錄。
- 批次檢查命名與缺漏檔案。
- 驗證 Markdown 圖片連結。
- 產生系列導航。
- 檢查圖片尺寸與比例。

腳本負責確定性工作，不負責替作者做創作判斷。

## 九、漸進揭露原則

正式 Skill 不應把所有寫作理論、視覺案例與模板全部塞進 `SKILL.md`。

推薦分成三層：

1. **Metadata**：只說明 Skill 做什麼、何時觸發。
2. **SKILL.md**：只載入核心流程、狀態與關卡。
3. **References／Assets**：只有進入相應階段才讀取。

例如：

- 使用者只問「這應該是一篇還是系列」，只讀 `scope-decision.md`。
- 使用者已有正文、只要配圖，就讀 `visual-storytelling.md` 與 Prompt 模板。
- 使用者只要組裝圖文稿，不重新載入完整寫作方法。

這能減少上下文浪費，也降低 Skill 在局部任務中過度行動。

## 十、推薦的輸出契約

Skill 應在每一階段交付一個可獨立閱讀、可接續、可驗收的產物。

```text
專案名稱/
├── 原始手稿.md
├── 系列文章plan.md
├── 第01篇文章plan.md
├── 第01篇草稿.md
├── 第01篇正文.md
├── 配圖plan.md
├── 第01篇配圖prompt.md
├── 配圖/
│   ├── 第01篇_圖一_封面_名稱.png
│   ├── 第01篇_圖二_轉場_名稱.png
│   └── 第01篇_圖三_結尾_名稱.png
└── 第01篇圖文發布版.md
```

### 輸出規則

- 不覆寫原始手稿。
- 若同名正式成品已存在，先確認是修改還是建立版本檔。
- 所有圖片保存進專案，不只留在生成工具的預設目錄。
- 每次完成後回報產物路徑與下一個可執行階段。
- 不把討論筆記、草稿與發布版混成同一檔案。

## 十一、寫作與視覺的共同品質原則

### 保護作者聲音

- 優先保留作者反覆使用、帶有個人辨識度的句子與比喻。
- 修正結構與表達，不把所有文字改成同一種 AI 腔調。
- 若原稿語意不清，提出解讀與選項，不擅自補成確定立場。

### 保護事實完整性

- 標記實際觀察、理論推論與未來假設。
- 實證篇必須保留原始檔、截圖、版本、失敗與人工介入。
- 不用概念圖替代真實證據。
- 高風險主張要標示審核、授權與責任邊界。

### 保護視覺敘事

- 配圖先定義敘事職責，再決定畫面。
- 封面只保留一個第一秒矛盾。
- 文中圖負責認知轉場，不只是重複正文。
- 結尾圖負責情緒餘韻，不加入新的複雜命題。
- 生成數量由文章需要決定，不由模板決定。

## 十二、應避免的 Skill 反模式

- **一鍵大量生成**：未確認系列架構就一次寫完所有篇章。
- **強迫連載化**：把本來適合單篇的內容拆成多篇。
- **流程凌駕意圖**：為了跑完整套流程，重做使用者已經完成的工作。
- **三圖教條**：每篇固定封面、轉場、結尾，即使其中沒有敘事必要。
- **視覺先於文意**：正文尚未穩定就開始大量生圖。
- **風格硬編碼**：把《AI 即一切》的暗金、黑色與城市意象套到所有主題。
- **混淆事實與推演**：為了文章流暢，把未來可能性寫成現在能力。
- **自動發布**：將「完成發布版」誤解成「可以替使用者公開」。
- **上下文膨脹**：把所有範例、模板與方法全部放進 `SKILL.md`。
- **只測成功案例**：Skill 只能重現《AI 即一切》，卻無法處理其他題材。

## 十三、正式建立前的測試方法

至少準備五個測試情境：

### 測試 1｜應該保持單篇

提供一份聚焦、篇幅短、只有一個問題的手稿。檢查 Skill 是否能克制拆系列的衝動。

### 測試 2｜應該發展成系列

提供一份包含多個獨立命題、真實案例與未來推演的長稿。檢查拆分是否形成認知弧線，而非平均切段。

### 測試 3｜從正文直接進入視覺

提供已確認正文，要求只做配圖。檢查 Skill 是否跳過前面階段，不重寫文章。

### 測試 4｜從配圖 Plan 生成圖片

提供配圖 Plan，要求產生 Prompt 與圖片。檢查是否保持視覺一致性、保存到正確目錄並完成驗收。

### 測試 5｜證據密集的技術文章

提供包含真實工具操作與產品能力的素材。檢查 Skill 是否區分證據、推論與未來想像，並保留人工責任。

每次測試都要觀察：

- 是否正確辨認起始階段。
- 是否保住作者原始意圖。
- 是否在必要關卡取得確認。
- 是否產出可接續的正式檔案。
- 是否避免越權發布與覆寫。
- 是否能解釋失敗並從正確階段恢復。

## 十四、成功標準

未來 Skill 不應只用「完成了幾篇、生成了幾張圖」衡量。

建議使用以下標準：

1. 作者能在成品中認出自己的思想與聲音。
2. 單篇與系列判斷有清楚理由，且作者願意採用。
3. 每篇只承擔一個主要認知任務。
4. 圖片延伸文意，而不是把標題畫成字面場景。
5. 文字、視覺與檔案可以跨會話繼續工作。
6. 事實、推論與未來想像不混淆。
7. 成品在速度、品質、成本、安全與個人化上優於原本做法。
8. 使用者可以只要求其中一段流程，而不被迫跑完整條生產線。

最終評估問題是：

> Skill 是否讓作者把注意力留給意圖、真實、品味與決定，而把可以調度的複雜度交給 AI？

## 十五、何時才適合正式建立 Skill

滿足以下條件後，再進入正式建立階段：

- [ ] 至少完成三個不同主題的工作流案例。
- [ ] 已驗證至少一個應保持單篇的案例。
- [ ] 已驗證至少一個非 AI 主題的系列。
- [ ] 已驗證從中間階段接續，而不是只會從手稿開始。
- [ ] 固定規則、可變參數與作者偏好已被分開。
- [ ] 人類確認關卡不會造成過度打斷。
- [ ] 檔案命名與版本策略已穩定。
- [ ] 圖片數量與視覺規則不再依賴單一案例。
- [ ] 事實查核與發布授權邊界已清楚。
- [ ] 已決定 Skill 的安裝位置與使用範圍。

屆時才依正式程序：初始化 Skill、編寫 `SKILL.md`、建立必要的 references／assets、產生 `agents/openai.yaml`、執行驗證，再以新案例進行前向測試。

## 方法論結論

「端到端」不代表 AI 一口氣替作者完成一切。

它真正代表的是：

> 無論作者從模糊手稿、系列 Plan、單篇正文、配圖計畫或既有圖片的哪一點進入，系統都能辨認目前位置，接續下一個正確階段，保存每次決策，最後交付完整圖文結果。

最好的 Skill 不是把創作變成沒有作者的自動化工廠，而是把中間複雜度組織起來，讓作者更專注於只有他能決定的事情。
