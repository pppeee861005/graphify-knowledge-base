# 豪力風神流圖文工作流 V0.2-SOP

## 1. 文件目的

本 SOP 將《豪力風神圖文連載工作流 V0.1》的探索結果，轉化為可重複執行、可逐關驗收的標準流程。

流程從作者的手寫稿、口述或模糊概念開始，依序完成作品規模判斷、系列規劃、單篇正文、視覺設計、生圖、圖文組裝，最後使用 Codex 桌面版的 `computer use` 能力，在作者已登入的 Substack 中批次建立草稿。所有對外發布都保留給作者人工校對、人工決定與人工執行。

本 SOP 的核心不是追求一次生成最多內容，而是：

> 保護作者原始意圖，讓它找到真正需要的篇幅、清楚的思想結構、可以被記住的畫面，以及可由作者驗收並親自發布的完成形態。

---

## 2. 適用範圍

適用於：

- 思想型、技術型、敘事型與混合型圖文文章。
- 單篇、上下篇或多篇連載。
- 需要封面、概念轉場圖、結尾餘韻圖、真實截圖或資料圖的內容。
- 最終準備發表至 Substack 的系列文章。

不適用於：

- 尚未取得作者授權的內容。
- 事實來源、圖片版權或人物隱私仍有重大疑慮的內容。
- 要求 AI 在作者未檢查前自動公開發布或寄送電子報的流程。

---

## 3. 核心原則與不可跨越的邊界

1. **原稿永不覆寫**：原始手稿、口述逐字稿與素材必須獨立保存。
2. **一篇只回答一個核心問題**：系列可有一個總命題，但每篇必須有自己的完成感。
3. **先穩定正文，再設計配圖**：正文仍在大幅重排時，不進入正式生圖。
4. **圖片承擔敘事任務**：不為湊數插圖，不用概念圖取代真實證據。
5. **事實、推論、想像分開**：所有數據、案例、引述、版本與連結均須查核。
6. **作者保留方向與品味**：AI 管理複雜度，作者決定意圖、價值、真實性與最終採用。
7. **草稿建立與公開發布分離**：Codex 可在明確授權後建立並保存 Substack 草稿，但不得按下發布、排程、寄送或建立公開連結。
8. **人工發布是最終防線**：每一篇都必須由作者人工回讀、預覽、確認設定並親自發布。

---

## 4. 角色分工

| 角色 | 主要責任 |
|---|---|
| 作者／總編輯 | 提供原始意圖與真實資料；核准規模、正文、視覺與成品；人工校對；人工發布 |
| Codex | 整理素材、分析結構、發展草稿、建立視覺規格、協助圖文組裝、建立檢查表 |
| Codex `computer use` | 在作者明確授權、Substack 已登入且目標視窗可見時，逐篇建立並保存草稿 |
| 事實查核者 | 核對數據、引述、人物、日期、案例、連結、版本與免責說明；可由作者兼任 |

任何階段若角色對作品方向有分歧，以作者決定為準，並把被否決方案與原因記錄下來，避免後續重複返工。

## 5. 專案啟動條件與建議檔案結構

### 5.1 啟動時至少需要

- 一份原始手稿、口述、零散筆記或概念說明。
- 作者想解決的問題，或希望讀者離開時產生的改變。
- 已知的真實案例、個人經驗與可用素材。
- 專案資料夾與明確的檔案命名方式。

### 5.2 建議結構

```text
系列名稱/
├── 原始手稿.md
├── 核心命題與素材盤點.md
├── 待查證事項.md
├── 系列文章plan.md
├── 第01篇文章plan.md
├── 第01篇草稿.md
├── 第01篇正文.md
├── 配圖plan.md
├── 第01篇配圖prompt.md
├── 配圖/
│   ├── 第01篇_圖一_封面_名稱.png
│   ├── 第01篇_圖二_轉場_名稱.png
│   └── 第01篇_圖三_結尾_名稱.png
├── 第01篇圖文發布版.md
├── Substack草稿建置清單.md
└── 發布紀錄.md
```

系列不固定八篇；以下第 8 階段以第 1～8 篇為批次案例，可依實際篇數增減。

## 6. 端到端流程總覽

```text
階段 1　保存原始意圖與盤點素材
    ↓ 作者確認核心命題
階段 2　判斷單篇、上下篇或系列
    ↓ 規模關卡
階段 3　建立系列 Plan 與單篇藍圖
    ↓ 架構關卡
階段 4　發展草稿、查核並完成正文
    ↓ 正文關卡
階段 5　把文意轉譯為配圖 Plan
    ↓ 視覺關卡
階段 6　建立 Prompt、生成並驗收圖片
    ↓ 圖片關卡
階段 7　組裝圖文發布版並完成上架資料包
    ↓ 成品關卡
階段 8　Computer Use 批次建草稿 → 人工校對 → 人工發布
```

前一關未通過，不進入下一階段。若後續發現根本性問題，回到造成問題的最早階段修正，不只在成品表面打補丁。

## 7. 標準作業程序

### 階段 1｜保存原始意圖與盤點素材

#### 輸入

- 手寫稿、口述、零散筆記、片段句子或未成形概念。
- 作者最想說、但尚未說完整的問題。

#### 操作

1. 將原稿原樣保存為 `原始手稿.md`，不得直接覆寫。
2. 找出重複出現的命題、比喻、人物、案例、情緒與關鍵句。
3. 建立 `核心命題與素材盤點.md`，將素材分為：
   - 作者已確信的觀點。
   - 仍在推演的假設。
   - 需要外部查證的事實。
   - 帶有作者個性、必須盡量保留的原句。
4. 將數據、引述、新聞、產品能力、人物經歷與外部連結寫入 `待查證事項.md`。
5. 用一句話暫定作品核心命題，再用一句話描述讀者完成閱讀後的認知轉變。

#### 作者確認

- 這真的是我想說的事情嗎？
- 有沒有哪個句子雖然粗糙，卻是整部作品的靈魂？
- AI 是否擅自補上我未曾表達的經驗或立場？

#### 完成標準

- 原稿已獨立保存。
- 核心命題可用一句話表達。
- 素材與待查證事項都有清單。
- 作者確認沒有被 AI 改寫成另一個人的觀點。

#### 產出

- `原始手稿.md`
- `核心命題與素材盤點.md`
- `待查證事項.md`

---

### 階段 2｜判斷單篇、上下篇或系列

#### 判斷準則

建議拆成系列的訊號：

- 有三個以上可獨立成立的核心問題。
- 同時包含思想論述、真實案例與未來推演。
- 不同段落需要不同證據或讀者背景。
- 多次出現「這個之後再談」。
- 多個最強段落互相爭奪文章結尾。
- 任一大段都無法刪除，但全部塞入又造成閱讀過載。

建議保持單篇的訊號：

- 所有內容都在回答同一問題。
- 拆篇後必須反覆重述大量背景。
- 後續篇章只有補充例子，沒有新的認知轉折。
- 拆分唯一目的只是增加發布數量。

#### 操作

1. 分別提出單篇、上下篇與系列三種方案。
2. 為每個方案寫出優點、缺點、預估重複量與讀者負擔。
3. 若採系列，為每篇寫下「本篇只回答的一個問題」。
4. 畫出讀者認知的升級順序，而不是只把原稿平均切段。
5. 記錄作者採用方案與未採用方案的理由。

#### 規模關卡

作者必須明確核准：

- 作品形式：單篇／上下篇／系列。
- 系列篇數。
- 每篇唯一核心問題。
- 為何這個拆分服務原始意圖，而不只是增加數量。

#### 產出

- 規模決策紀錄。
- 篇章問題清單。
- 初步敘事順序。

---

### 階段 3｜建立系列 Plan 與單篇藍圖

#### 系列 Plan 必須包含

1. 系列名稱、副題與一句話核心命題。
2. 目標讀者與讀者承諾。
3. 讀者從第一篇到最後一篇的認知旅程。
4. 分幕結構與篇章總覽。
5. 每篇核心問題、開場、衝突、轉變與完成感。
6. 每篇證據、限制、反方觀點與責任邊界。
7. 上一篇承接、下一篇鉤子與系列導航。
8. 最終篇如何回收伏線。
9. 預計發布節奏與發布前品質門檻。

#### 每篇藍圖必須包含

- 本篇只回答的一個問題。
- 開場場景或第一段鉤子。
- 反直覺命題。
- 機制拆解。
- 案例、資料或真實證據。
- 限制、責任與反方觀點。
- 哲學收束。
- 下一篇鉤子與導航文字。

#### 架構關卡

- 任一篇抽出後，是否仍有自己的入口、衝突、轉變與完成感？
- 任兩篇是否在重複回答同一問題？
- 第一篇是否值得開始？最後一篇是否真正完成整季承諾？
- 作者是否核准篇次與認知升級順序？

#### 產出

- `系列文章plan.md`
- `第01篇文章plan.md` 至實際最後一篇

---

### 階段 4｜發展草稿、查核並完成正文

#### 操作

1. 依單篇藍圖生成完整草稿，先讓思想充分展開，允許局部冗長。
2. 第二輪把草稿收斂成正文：
   - 刪除不服務本篇核心問題的旁支。
   - 合併重複論點。
   - 保留作者最有力量的句子與語氣。
   - 調整為適合手機閱讀的短段落與小標題。
3. 清楚標示並核對：
   - 已發生的事實。
   - 基於證據的合理推論。
   - 尚未發生的未來想像。
4. 查核數據、日期、人物、案例、引述、產品功能、版本與外部連結。
5. 補上必要的限制、風險、免責聲明、人工責任與反方觀點。
6. 檢查開場是否快速建立問題，結尾是否完成本篇並打開下一篇。

#### 正文關卡

- 本篇能否用一句話說明唯一任務？
- 作者經驗與語氣是否被保留？
- 是否有未查證內容被寫成確定事實？
- 是否存在只有為了顯得厲害、卻不服務讀者的段落？
- 情緒弧線與思想順序是否已穩定，不再需要大幅重排？

#### 完成標準

- 所有重要事實已查核或清楚標註不確定性。
- 正文結構與情緒已穩定。
- 作者逐篇核准後，才可進入視覺階段。

#### 產出

- `第01篇草稿.md`
- `第01篇正文.md`
- 更新後的 `待查證事項.md`

---

### 階段 5｜把文意轉譯為配圖 Plan

#### 圖片職責

預設評估三種圖片，但不強制湊滿：

1. **封面主視覺**：第一秒只呈現一個矛盾，負責攔截注意力。
2. **概念轉場圖**：放在認知真正轉彎之處，負責一次觀看方式的改變。
3. **結尾餘韻圖**：承接最後思想，留下比解釋更長久的感受。

若文章只有兩個真正需要畫面的節點，就只做兩張。實證篇可使用真實截圖、資料圖或操作紀錄，概念圖不得代替證據。

#### 每張圖的 Plan 必須包含

- 圖片名稱與用途。
- 第一秒鉤子。
- 畫面意境與唯一主要衝突。
- 主體、象徵物與象徵關係。
- 構圖、視覺焦點、色彩、材質與光線。
- 希望讀者產生的情緒。
- 禁止方向與常見 AI 陳腔。
- 在正文中的精確插入位置。
- Alt Text 草案。
- 驗收標準。

#### 視覺關卡

- 不看文章標題，圖片仍能讓作者感覺到本篇命題嗎？
- 圖片是否建立世界規則，而非只是把標題畫出來？
- 圖片是否保留人類意圖、授權與決定權？
- 系列圖片放在一起是否像同一個世界，又沒有重複構圖？

#### 產出

- `配圖plan.md`

---

### 階段 6｜建立 Prompt、生成並驗收圖片

#### Prompt 規格

每張圖的 Prompt 至少包含：

- 使用情境、尺寸與畫幅。
- 場景、背景、人物、主體與象徵物。
- 唯一主要視覺衝突。
- 構圖、手機裁切安全區與焦點層級。
- 光線、材質、色彩與情緒。
- 系列視覺 DNA 與一致性鎖定句。
- 必須保留的規則。
- 共用及單圖負面 Prompt。
- 首輪偏差的修正句。
- 單圖驗收標準。

#### 生成順序

1. 先生成封面，確立人物、色彩、材質與光線。
2. 封面通過後，再生成轉場圖與結尾圖。
3. 每張生成後立即檢查，不等全部完成才驗收。
4. 首輪不合格時，先記錄偏差，再修改 Prompt；不要只重複抽卡。
5. 正式成品存入 `配圖/`，以篇次、圖序、用途與名稱命名。

#### 圖片驗收清單

- [ ] 縮成手機尺寸後仍能辨識主體。
- [ ] 第一眼只有一個主要矛盾。
- [ ] 不看標題仍能感覺文章命題。
- [ ] 沒有亂碼、Logo、浮水印或不必要文字。
- [ ] 沒有明顯解剖、透視、陰影或物件錯誤。
- [ ] 不落入常見 AI 素材庫陳腔。
- [ ] 系列視覺一致，但構圖不機械重複。
- [ ] 圖片來源、生成方式與使用權可追溯。

#### 產出

- `第01篇配圖prompt.md`
- `配圖/` 內的正式圖片資產

---

### 階段 7｜組裝圖文發布版與上架資料包

#### 組裝原則

1. 封面負責攔截，不必提前解釋全文。
2. 轉場圖放在認知真正轉彎的位置，不按固定字數插圖。
3. 結尾圖後保留沉默，不再接大段新論述。
4. 圖片已表達的內容，正文不逐字重複。
5. 實證篇保留真實截圖、版本、操作紀錄與失敗案例。
6. 每張圖都寫簡潔、具敘事功能的 Alt Text。
7. 每篇加入清楚的系列名稱、篇次、上一／下一篇導航、必要 CTA 與免責文字。

#### 每篇上架資料包

每篇進入 Substack 前，必須準備齊全：

- 標題。
- 副標題或摘要。
- 封面圖片。
- 完整正文。
- 文中圖片與插入位置。
- 每張圖的 Alt Text。
- 系列名稱與篇次。
- 上一篇、下一篇或系列首頁導航文字；尚未公開的文章不得填入虛構公開連結。
- CTA、作者署名、免責聲明與來源連結。
- 建議 slug、標籤或分類；是否使用以作者當下設定為準。

#### 成品關卡

- 圖片與正文合在一起是否比各自單獨更有力量？
- 所有圖片、連結、導航與 Alt Text 是否正確？
- Markdown 是否含有不適合直接貼入 Substack 的註解、內部標記或檔案路徑？
- 每篇是否已取得作者的「可建立平台草稿」核准？

#### 產出

- `第01篇圖文發布版.md` 至最後一篇。
- 正式圖片資產。
- `Substack草稿建置清單.md`。

### 階段 8｜使用 Codex Computer Use 批次建立 Substack 草稿，最後人工校對與人工發布

此階段是 V0.2-SOP 新增的最後一步。它把「內容完成」延伸到「平台草稿已備妥」，但不把公開發布交給 AI。

> **Skill 化標註：**因為「批量在 Substack 上建立草稿」屬於頻繁、重複且規格固定的操作，現已將這段流程提煉為獨立的 `substack-create-draft` Skill。實際建立或更新草稿時，優先調用該 Skill 統一執行；本 SOP 則負責定義它的輸入、驗收標準、安全邊界，以及後續人工校對與人工發布責任。

#### 8.1 執行前授權與環境條件

開始前必須同時滿足：

- [ ] 作者明確要求本次建立 Substack 草稿，並指定篇次，例如第 1～8 篇。
- [ ] 第 1～8 篇的圖文發布版與正式圖片已通過成品關卡。
- [ ] 作者已在目標瀏覽器登入正確的 Substack 帳號與 publication。

依 OpenAI 官方說明，Computer Use 可在 Windows 或 macOS 上看見並操作圖形介面；在 Windows 執行時目標應用程式必須位於作用中的桌面，任務應限定在明確的應用程式與流程內，並由使用者審核權限提示。參考：[OpenAI Computer Use 官方文件](https://learn.chatgpt.com/docs/computer-use)。

#### 8.3 批次建立方式

「批次」代表按照同一套規格連續處理多篇，但每一篇仍須獨立保存與驗證：

1. 先用第 1 篇做試跑。
2. 保存後回到草稿列表，確認第 1 篇草稿存在且沒有公開狀態。
3. 第 1 篇欄位、圖片與格式正確後，再依序建立第 2～8 篇。
4. 每篇完成後立即在清單打勾，不把八篇全部貼完才回頭檢查。
5. 操作過程不依賴固定螢幕座標；以目前可見的標籤、按鈕與頁面狀態為準。
6. 若網站介面更新或欄位名稱不同，Codex 應停下確認，不自行推測高風險操作。
7. 全部完成後回到草稿列表，核對草稿數量、篇次與標題。

#### 8.6 作者人工校對

作者必須逐篇開啟草稿並使用 Substack 預覽，以桌面與手機閱讀效果進行最後檢查：

##### 文字

- [ ] 標題、副標題、篇次與正文來源一致。
- [ ] 開頭沒有遺失，結尾沒有截斷。
- [ ] 粗體、斜體、小標、引言、分隔線與清單格式正確。
- [ ] 沒有內部註解、Prompt、檔案路徑、待辦標記或 Markdown 殘碼。
- [ ] 錯字、標點、空格、段落與手機閱讀節奏正確。
- [ ] 事實、推論、想像、引述與免責聲明清楚。

##### 圖片與版面

- [ ] 封面正確，沒有裁掉主要視覺焦點。
- [ ] 文中圖片順序、位置、尺寸與畫質正確。
- [ ] Alt Text 可理解圖片的敘事功能。
- [ ] 圖片後沒有多餘空段、重複說明或錯位文字。
- [ ] 手機預覽仍能辨識主體與閱讀全文。

##### 連結與系列

- [ ] 外部來源連結可開啟且指向正確頁面。
- [ ] 上一篇連結只連到已公開文章。
- [ ] 尚未公開的下一篇不使用虛構網址；可保留純文字預告。
- [ ] 系列名稱、篇次與文章順序一致。
- [ ] CTA、留言引導、訂閱引導與作者署名正確。

##### 平台設定

- [ ] 正確 publication。
- [ ] 正確作者、分類、標籤與受眾設定。
- [ ] slug、SEO、社群預覽圖與摘要符合作者決定。
- [ ] 電子郵件寄送、付費牆、留言與推薦設定符合本篇策略。
- [ ] 發布日期與節奏符合系列計畫。

任何一項未通過，都先修正草稿並重新預覽，不進入發布。

#### 8.7 作者人工發布

1. 作者只選擇一篇已完成全部人工校對的草稿。
2. 作者親自核對發布對象、電子郵件寄送、付費牆、留言、日期與時間。
3. 作者親自按下發布或排程按鈕，並處理平台的最後確認畫面。
4. 發布後，作者開啟公開頁面與收到的電子郵件版本進行回讀。
5. 將永久連結、實際發布時間、寄送狀態與異常寫入 `發布紀錄.md`。
6. 確認前一篇已公開後，才把其永久連結補入後續尚未發布草稿的系列導航。
7. 下一篇重複相同人工校對與人工發布流程，不因前一篇正確就跳過檢查。

> **最終紅線：Codex 不代替作者按下 Publish、Send 或 Schedule。作者必須看見最終內容、理解發布設定，並親自完成對外發布。**

#### 8.8 異常處理

| 異常 | 處理方式 |
|---|---|
| 發現同名或同篇草稿 | 停止建立該篇，記錄兩者狀態，交由作者判斷保留哪一份 |
| 登入失效或出現驗證 | 停止操作，由作者親自登入或完成驗證 |
| 進入錯誤 publication | 不新增、不修改；返回並請作者確認正確目標 |
| 圖片上傳失敗或錯圖 | 保存現有草稿、記錄缺圖，不用相似圖片代替 |
| 內容貼入後格式崩壞 | 先保存草稿，記錄問題；必要時分段修正並重新預覽 |
| 網站出現警告或陌生按鈕 | 不猜測、不繼續，截取可見狀態並回報作者 |
| 不慎進入發布確認畫面 | 不確認，立即退出並檢查文章是否仍為草稿 |
| 草稿疑似已公開或寄送 | 立即停止全部批次工作並通知作者人工查核 |

## 8. 全流程四大作者決策關卡

| 關卡 | 作者確認內容 | 未通過時 |
|---|---|---|
| 規模關卡 | 單篇、上下篇或系列是否符合真正意圖 | 回到素材盤點，不為拆而拆 |
| 正文關卡 | 單篇命題、事實、語氣與情緒是否穩定 | 暫停視覺設計，先修正文 |
| 視覺關卡 | 圖片是否像作者想看見的世界，且服務文意 | 修改意境或刪除弱圖，不急著上架 |
| 成品關卡 | 圖文、導航、平台草稿與發布設定是否可接受 | 修正草稿並重新預覽，作者未核准不得發布 |

## 10. 品質與效率評估

每次完成系列後，使用五個維度復盤：

| 維度 | 評估問題 |
|---|---|
| 更快 | 是否減少跨工具搬運、重複貼文與上架返工？ |
| 更好 | 命題、文字、圖片與發布呈現是否彼此增強？ |
| 更低成本 | 是否減少弱圖、重寫、錯誤草稿與重複操作？ |
| 更安全 | 是否保留原稿、查核、權限、草稿與人工發布邊界？ |
| 更個人化 | 是否保住作者語氣、經驗、價值觀與審美？ |

每次復盤至少記錄：

- 哪個步驟真正節省時間。
- 哪個步驟造成返工。
- 作者在哪裡否決或改變 AI 建議。
- Computer Use 在哪個欄位或操作最容易出錯。
- 哪些規則可進入下一版固定 SOP。
- 哪些只是本系列偏好，應保留為可變參數。

最終核心指標是：

> 是否以更低的總成本，更忠實、更有力量、更安全地完成作者原始意圖，並由作者對公開結果負最後責任？
