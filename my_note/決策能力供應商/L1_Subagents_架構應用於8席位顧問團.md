# L1 Subagents 架構應用於 AI顧問團 8 席位開發

**基於**：Claude Agent 四層架構深度研究
**應用場景**：8 個席位的 AI 顧問團 18 個月並行開發計劃
**核心目標**：用 L1 Subagents 的「Coordinator 持有計劃」模式，協調 8 個席位從「戰報→機房→教科書→劇場」的信任生產線開發

---

## 一、L1 Subagents 核心機制回顧

### 1.1 L1 的本質：誰持有計劃？

```
在 L1 Subagents 模式中：

計劃持有者：Coordinator（Claude）
執行者：Subagents（worker agents）
信息流：
  Coordinator 逐回合決策
      ↓
  分配任務給 Subagents（並行執行）
      ↓
  Subagents 完成任務，結果回流到 Coordinator 的 context window
      ↓
  Coordinator 評估中間結果，決定下一回合的動作
      ↓
  循環直到任務完成
```

### 1.2 L1 的關鍵特性

| 特性 | 說明 | 適用性分析 |
|------|------|-----------|
| **逐回合決策** | Coordinator 看到每回合結果後再決定下一步 | ✅ 適合「邊開發邊調整」的席位研發 |
| **中間結果聚合** | 所有 Subagent 輸出都回到 Coordinator context | ✅ 適合「跨席位的方法論統一」 |
| **規模上限** | 每回合少量任務（10-20 個 subagent） | ✅ 8 席位 × 4 文體 = 32 subagents（可控） |
| **成本效率** | Token 效率最高 | ✅ 18 個月持續開發需要成本控制 |
| **人工干預** | 需要頻繁調整方向 | ✅ 每個席位的規則庫和轉介資源都需要迭代 |

**結論**：L1 Subagents 是 8 席位並行開發的理想架構。

## 二、Coordinator 的角色與計劃持有

### 2.1 Coordinator（Claude）持有什麼計劃？

Coordinator 不是「總工程師」，而是「產品線總監」，持有的是 **18 個月分階段開發的完整藍圖**：

```
Coordinator 的計劃全景：

📊 Phase 1（4個月）：奠基
   ├─ 席位1（租約哨兵）：上線
   └─ 席位2（行政官僚）：定義書+規則庫

📊 Phase 2（6個月）：擴展
   ├─ 席位2（行政官僚）：上線
   ├─ 席位3（財務顧問）：定義書→評測→上線
   ├─ 席位4（大宗購買）：定義書→評測→上線
   └─ 席位5（健康顧問）：定義書→評測→上線

📊 Phase 3（9個月）：完整生態
   ├─ 席位6（職涯顧問）：定義書→評測→上線
   ├─ 席位7（教育顧問）：定義書→評測→上線
   ├─ 席位8（資訊心理）：定義書→評測→上線
   └─ 統一平台：8 席位中央入口 + 本地化
```

**Coordinator 的核心責任**：
1. ✅ **分配任務**：每個 Phase 開始時，決定「哪個席位現在進入哪個階段」
2. ✅ **評估進度**：每個月覆盤，檢查各席位的漏報率/誤報率/用戶信任度
3. ✅ **決策調整**：根據中間結果決定是否「推遲某席位 / 砍非核心功能 / 追加預算」
4. ✅ **方法論統一**：確保所有席位都遵循「三大鐵律」和「信任生產線 SOP」

### 2.2 Coordinator 不持有什麼？

❌ **不持有**：每個席位的具體規則庫內容（這是 Subagent 的責任）
❌ **不持有**：每日的代碼實現細節（這是執行層的責任）
❌ **不持有**：每篇劇場的具體情節（這是內容層的責任）

**原則**：Coordinator 只持有「架構級別的計劃」，不持有「執行級別的細節」。

## 三、Subagents 的責任範圍設計

### 3.1 選項分析：Subagent 按什麼劃分？

| 劃分方式 | Subagent 數量 | 優點 | 缺點 | 決策 |
|---------|-------------|------|------|------|
| **按席位** | 8 個 | 每個 Subagent 專注一個席位的完整生命周期 | 並行度不夠（Phase 1 只用 2 個） | ❌ |
| **按 Phase** | 3 個 | 符合時間線 | 不符合「席位獨立」的邏輯 | ❌ |
| **按階段** | 4 個（戰報/機房/教科書/劇場） | 符合信任生產線 SOP | 跨席位串聯複雜 | ❌ |
| **按席位 × 階段** | 8 × 4 = 32 個 | 最高並行度 + 清晰的責任邊界 | Subagent 數量多 | ✅ **選擇** |

### 3.2 最終設計：席位 × 階段 = 32 個 Subagents

```
Subagent 命名規範：
  [席位編號]_[階段簡碼]_agent

例如：
  01_BR_agent（席位1_戰報_agent）
  01_MR_agent（席位1_機房_agent）
  01_TB_agent（席位1_教科書_agent）
  01_ST_agent（席位1_劇場_agent）

  02_BR_agent（席位2_戰報_agent）
  02_MR_agent（席位2_機房_agent）
  ...

  08_ST_agent（席位8_劇場_agent）
```

**階段簡碼對照**：
- **BR**（Battle Report）：戰報層
- **MR**（Machine Room）：機房層
- **TB**（Textbook）：教科書層
- **ST**（Stage / Theater）：劇場層

### 3.3 每個 Subagent 的責任

以 `01_BR_agent`（席位1_戰報_agent）為例：

**職責**：
1. 負責「租約哨兵」的戰報文檔生成與維護
2. 遵循《信任生產線 SOP》的戰報層規則（300-800字 / 錨點數字 / 待補債務登記）
3. 記錄每日開發的真實進展、踩坑、燒穿預算等事件
4. 不干預其他席位的戰報

**輸入**：
- Coordinator 分配的任務：「記錄今日租約哨兵 W1D3 的進度」
- 開發團隊提交的原始日誌

**輸出**：
- 符合戰報規範的 Markdown 文檔
- 待補債務清單（如有）
- 需要升級的風險信號（如成本爆炸）

**回流給 Coordinator**：
- 戰報完成狀態
- 是否觸發「債務清償提醒」
- 是否觸發「成本預警」

## 五、文件結構設計：支持 L1 架構的目錄樹

1. **按席位分倉**：每個席位一個獨立目錄（符合 Subagent 的責任邊界）
2. **四文體分層**：每個席位目錄下有 4 個子目錄（戰報/機房/教科書/劇場）
3. **中央協調**：根目錄有 Coordinator 持有的全局計劃文檔
4. **回鏈可追溯**：每篇劇場文章可追溯到機房報告，機房報告可追溯到戰報

### 5.3 目錄樹的關鍵設計點

| 文件 | Coordinator 用途 | 更新頻率 |

| 信任生產線-SOP.md | 四文體標準（所有 Subagents 遵循） | 每月覆盤檢視 |

| 成功標準儀表板.md | KSI 監控（漏報率/誤報率/用戶信任度） | 每月更新 |

#### (2) 席位層（8 個獨立目錄）

**標準結構**（每個席位目錄）：
```
席位XX_名稱/
  ├─ README.md（願景 + 快速導航）
  ├─ 定義書.md（業務邏輯層，最重要）

  └─ 04_劇場/（傳播敘事）
```

- 每篇機房報告是否有「源頭戰報連結」？

## 六、子系列命名方案

### 6.1 挑戰：如何在一個大系列內組織多個席位？

**問題**：
- AI顧問團是「一個大系列」（18 個月、8 個席位）
- 但每個席位又是「獨立的子系列」（各有自己的戰報→機房→教科書→劇場）
- 如何命名，才能讓讀者清楚知道「這是哪個席位的哪個階段」？

### 6.2 命名方案設計

#### 方案 A：扁平化命名（不推薦）

```
AI顧問團_E01_租約哨兵戰報W1.md
AI顧問團_E02_租約哨兵戰報W2.md
AI顧問團_E03_租約哨兵機房報告.md
AI顧問團_E04_行政官僚戰報W1.md
...
```

**缺點**：
- ❌ 席位與階段混在一起，不清晰
- ❌ 難以快速識別「這是哪個席位的劇場文章」

#### 方案 B：二級命名（推薦）✅

```
命名格式：
  [大系列簡碼]_[席位編號]_[階段簡碼]_[集次]_[標題].md

例如：
  AC_01_BR_W1_租約哨兵首戰.md（AI顧問團_席位01_戰報_W1）
  AC_01_MR_M1_OCR階段評測.md（AI顧問團_席位01_機房_里程碑1）
  AC_01_TB_01_定義書.md（AI顧問團_席位01_教科書_第1篇）
  AC_01_ST_01_第一次戰鬥.md（AI顧問團_席位01_劇場_第1篇）

  AC_02_BR_W1_規則庫構建.md（AI顧問團_席位02_戰報_W1）
  AC_02_MR_M1_50份測試評測.md（AI顧問團_席位02_機房_里程碑1）
  ...
```

**簡碼對照表**：

| 簡碼 | 全名 | 說明 |
|------|------|------|
| **AC** | Advisory Council | AI顧問團大系列 |
| **01–08** | 席位編號 | 01=租約, 02=行政, 03=財務, ... |
| **BR** | Battle Report | 戰報層 |
| **MR** | Machine Room | 機房層 |
| **TB** | Textbook | 教科書層 |
| **ST** | Stage/Theater | 劇場層 |
| **W1–W4** | 周次 | 戰報用 |
| **M1–M4** | 里程碑 | 機房用 |
| **01–99** | 集次 | 教科書/劇場用 |

### 6.3 命名方案的優勢

✅ **清晰的層級結構**：
- 讀者看到 `AC_01_ST_03` 就知道：AI顧問團→席位1→劇場→第3篇
- Coordinator 看到 `AC_03_MR_M2` 就知道：席位3（財務）的機房報告（里程碑2）

✅ **支持自動化處理**：
- 可用腳本自動生成「進度追蹤表」（掃描所有 `AC_XX_BR_WX` 文件）
- 可自動檢查「回鏈完整性」（`AC_01_ST_01` 是否引用了 `AC_01_MR_M4`？）

✅ **支持跨席位查詢**：
- 想看所有戰報？→ 搜索 `AC_*_BR_*`
- 想看席位1的所有文檔？→ 搜索 `AC_01_*`
- 想看所有劇場文章？→ 搜索 `AC_*_ST_*`

### 6.4 文件完整命名示例（席位1的完整生命周期）

```
席位01_租約哨兵/
  ├─ 01_戰報/
  │    ├─ AC_01_BR_W1_租約哨兵首戰.md
```

## 七、L1 架構的關鍵檢查清單

### 7.1 Coordinator 的每週檢查清單

**時間**：每週六覆盤日
**檢查對象**：所有活躍的 Subagents
**檢查內容**：

| 檢查項 | 檢查方式 | 觸發條件 |
|--------|---------|---------|
| ✅ 戰報是否按時產出？ | 掃描 `AC_XX_BR_WX` 文件時間戳 | 逾期 >2 天 → 調查原因 |
| ✅ 債務是否清償？ | 檢查債務台帳 | 債齡 >30 天 → 強制處理 |
| ✅ 機房報告是否有「系統錯了什麼」？ | 搜索關鍵詞 | 缺失 → 退回修改 |
| ✅ 劇場是否有回鏈？ | 檢查文末是否有機房編號 | 缺失 → 紅線違規 |
| ✅ 成本是否爆炸？ | 檢查預算控制書的監控指標 | 超支 >20% → 啟動降級方案 |
| ✅ 漏報率/誤報率是否達標？ | 檢查機房報告的評測數據 | 漏報率 >5% → 推遲上線 |

## 八、與現有系列的連接

### 8.1 AI顧問團 vs AI蜂群投資系列

**關係**：
- AI蜂群投資系列（SWARM）= 高端用戶場景（個人投資者）
- AI顧問團（AC）= 普通人場景（租約、補助、健康...）

**共用的架構**：
- 都採用 L1 Subagents 的「Coordinator 持有計劃」模式
- 都遵循「戰報→機房→教科書→劇場」的信任生產線

**差異**：
- SWARM：7 篇文章（7 個 Workflow 應用）
- AC：8 個席位 × 4 文體 = 32 個系列

**交叉引用設計**：
```
SWARM_S01E07_終極顧問.md（個人投資顧問）
  └─ 文末交叉引用：
     「如果你需要的不是投資顧問，而是租約顧問、健康顧問...
      請見：AI顧問團產品線 → AC_01_ST_01（租約哨兵劇場）」

AC_01_ST_01_租約哨兵的誕生.md
  └─ 文末交叉引用:
     「租約哨兵只是 AI 顧問團 8 個席位的第一個。
      如果你想看 AI 如何協助投資決策，請見：
      SWARM_S01E07_終極顧問（AI蜂群投資系列）」
```

### 8.2 AI顧問團 vs DW 方法論

**關係**：
- DW 方法論 = 底層架構（Dynamic Workflows）
- AI 顧問團 = DW 的垂直應用場景（規則庫比對型）

**教科書層的連接**：
```
AC_01_TB_03_教學指南.md（租約哨兵）
  └─ 引用 DW 方法論：
     「本系統採用 Dynamic Workflows 架構，詳見：
      - DW_Plan_Quick_Template（通用模板）
      - DW 學習計劃中心（學童版）」

DW_Plan_Quick_Template.md
  └─ 案例引用：
     「想看 DW 在真實場景的應用？請見：
      - 計劃13_租約哨兵（規則庫比對型 Workflow）
      - 計劃7_AI蜂群投資（並行監控型 Workflow）」
```

## 九、總結：L1 架構的核心價值

### 9.1 為什麼 L1 Subagents 最適合 AI 顧問團？

| L1 特性 | AI 顧問團需求 | 匹配度 |
|---------|-------------|--------|
| **逐回合決策** | 每個席位的規則庫和轉介資源都需要迭代調整 | ⭐⭐⭐⭐⭐ |
| **中間結果聚合** | Coordinator 需要看到所有席位的進度，決定資源分配 | ⭐⭐⭐⭐⭐ |
| **規模可控** | 8 席位 × 4 文體 = 32 subagents（L1 上限 10-20 可控） | ⭐⭐⭐⭐ |
| **成本效率** | 18 個月持續開發，需要 Token 成本控制 | ⭐⭐⭐⭐⭐ |
| **人工干預** | 每個席位的評測和真人測試都需要人工參與 | ⭐⭐⭐⭐⭐ |

### 9.2 L1 架構的三大保證

✅ **方法論統一**：
- Coordinator 確保所有 Subagents 遵循「三大鐵律」和「信任生產線 SOP」
- 任何席位的任何階段都不會偏離核心價值觀

✅ **透明可追溯**：
- 每篇劇場文章都能追溯到機房報告
- 每篇機房報告都能追溯到戰報
- Coordinator 每週檢查回鏈完整性

✅ **成本可控**：
- Coordinator 監控每個席位的成本燃燒
- 一旦某席位成本爆炸，立即觸發降級方案
- 18 個月總預算可預測（~130 萬）
