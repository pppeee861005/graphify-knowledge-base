**Coordinator 的審計檢查流程**：

```
每週覆盤日，Coordinator 執行回鏈審計：

1. 掃描所有劇場文章（AC_*_ST_*）
2. 檢查每篇劇場文章是否有「對應機房編號」
3. 點擊連結，驗證機房報告是否存在
4. 檢查機房報告是否有「源頭戰報連結」
5. 點擊連結，驗證戰報是否存在
6. 檢查戰報中的「待補項」是否已在後續文章中補上連結

不合格 → 紅線違規 → 退回修改
合格 → 通過審計 → 更新「回鏈完整率」指標
```

**Subagent 命名規範**：
```
[席位編號]_[階段簡碼]_agent

BR = Battle Report（戰報）
MR = Machine Room（機房）
TB = Textbook（教科書）
ST = Stage/Theater（劇場）
```

**Coordinator 的並行管理能力**：
- L1 Subagents 的上限：10–20 個並行任務
- 實際需求：每個 Phase 同時活躍的 Subagents ≤ 15 個
  - Phase 1：席位1（4個）+ 席位2（2個）= 6 個 ✅
  - Phase 2：席位1–5（約 10–12 個）✅
  - Phase 3：席位1–8（約 15 個）✅

**結論**：32 個 Subagents 總量雖多，但分階段並行數量在 L1 可控範圍內。

為什麼選 L1？
  1. 規模可控：32 個 Subagents，分階段並行 ≤15 個
  2. 成本最優：18 個月持續開發，Token 成本最低
  3. 可迭代：每個席位的規則庫和轉介資源都需要根據評測調整
  4. 可干預：Coordinator 每週評估，可隨時調整策略
  5. 可審計：中間結果回流，Coordinator 可檢查品質

  1. ❌ 不需要「peer-to-peer 通訊」
     - 席位1的戰報不需要和席位2的戰報「對話」
     - 各席位相對獨立，不是協作關係
  2. ❌ Token 成本太高
     - L2 的 peer 通訊非常費 Token
     - 18 個月持續開發承受不起

為什麼不選 L3？
  1. ❌ 規模不夠大（32 個 Subagents < 100 agents）
  2. ❌ 流程無法預定義（每個席位的規則庫需迭代）
  3. ❌ 需要頻繁人工干預（評測、真人測試、調整策略）

## 總結

這套 L1 Subagents 架構的核心優勢：

✅ **清晰的責任邊界**：
- 每個 Subagent 只負責一個席位的一個階段
- 例如 `01_BR_agent` 只負責席位1的戰報，不干預其他

✅ **可追溯的信任鏈**：
- 劇場 → 機房 → 戰報
- 每層都能追溯到源頭

✅ **靈活的並行控制**：
- Phase 1：6 個 Subagents
- Phase 2：10–12 個
- Phase 3：15 個
- 永遠在 L1 的可控範圍內

✅ **成本可控**：
- 18 個月總預算 ~130 萬
- L1 是 Token 效率最高的架構
