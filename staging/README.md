**建立日期**：2026-05-22
**版本**：1.0
**目的**：知識資産的臨時收集、分析、歸類區域

---

## 🎯 Staging 的定義

**Staging 是知識管理流程中的「中轉站」**，用於：

1. ✅ **臨時存放**：收集來自各種來源的知識素材
2. 🔍 **等待分析**：標記以待進一步分析或決策
3. 📊 **待歸類**：確認最終分類前的過渡期
4. ➡️ **最終移動**：經過分析後移至相應系列目錄

---

## 📋 工作流程

```
來源素材
    ↓
進入 staging/
    ↓
標記狀態 + 分析
    ↓
決定歸類
    ↓
移動到最終目錄
```

**時間線**：
- 📥 **第 1 天**：素材進入 staging（通常來自碎片化輸入）
- 🔍 **第 2-3 天**：分析評估、決定歸類
- ➡️ **第 4-7 天**：通過分析後移至正式目錄

## 📝 命名規則

### 暫存文件的命名格式

```
[狀態前綴]_[日期]_[內容簡述].md
```

| 狀態前綴 | 含義 | 例子 |
|---------|------|------|
| **待分析** | `todo_` | `todo_20260522_AgentOS新框架.md` |
| **分析中** | `analyzing_` | `analyzing_20260522_黑箱倫理.md` |
| **待決策** | `decision_` | `decision_20260522_系列歸屬.md` |
| **已確認** | `approved_` | `approved_20260522_AG_新素材.md` |

### 文件內容格式

```markdown
---
title: [標題]
source: [來源]（如：筆記、對話、外部素材）
date_created: YYYY-MM-DD
status: todo / analyzing / decision / approved
proposed_category: [建議分類]
tags: [相關標籤]
notes: [分析備註]
---

# [標題]

[內容主體]
```

## 🗂️ Staging 的結構

```
staging/
├─ README.md（本文件）
├─ todo/               # 待分析
├─ analyzing/          # 分析中
├─ decision/           # 待決策
└─ approved/           # 已確認，待移動
```

### 子目錄用途

| 子目錄 | 用途 | 停留時間 |
|--------|------|---------|
| **todo/** | 新進素材，尚未標記 | 1-2 天 |
| **analyzing/** | 正在進行深度分析 | 2-3 天 |
| **decision/** | 分析完成，待確認歸類 | 1-2 天 |
| **approved/** | 已確認分類，待移動 | <1 天 |

## 💭 分析與決策指南

### 第一步：評估素材

問自己以下問題：

- **內容性質**：這是文章、筆記、教程、還是素材？
- **系列歸屬**：最可能屬於哪個系列？（AG、DK、FA、AS、NANA 等）
- **完成度**：這是初稿、草稿，還是已發布？
- **優先級**：這是 P0、P1，還是 P2 級別？

### 第二步：選擇目標分類

| 系列簡碼 | 系列名稱 | 位置 |
|---------|---------|------|
| **AG** | Antigravity | `系列文章/Antigravity系列/` |
| **DK** | 暗知識 | `系列文章/暗知識系列/` |
| **FA** | From Addiction（從毒癮到創造者） | `系列文章/從毒癮到創造者/` |
| **AS** | Agent System | `系列文章/Agent系列/` |
| **NANA** | 龍蝦娜娜科幻小說 | `科幻小說/龍蝦娜娜系列/` |
| **Tut** | 教程 | `技術文章/` |
| **Other** | 其他分析文章 | `分析與報告/` |

### 第三步：命名與標記

使用以下格式為文件重新命名（適用於已確認的文件）：

```
[系列簡碼]_[集次或類型]_[標題].md
```

**例子**：
- `AG_新素材_框架創新.md`
- `DK_W4_支援_倫理問題.md`
- `NANA_S02E01_娜娜的回歸.md`

## 🔄 移動到正式目錄的步驟

### 當文件準備好時

1. **確認分類**：在 `approved/` 子目錄中等待
2. **檢查命名**：確保按 `[系列簡碼]_[描述]` 格式命名
3. **執行移動**：
   ```bash
   git mv staging/approved/[文件名] 系列文章/[系列目錄]/
   ```
4. **更新記錄**：在 MEMORY.md 中更新索引

## 🎓 最佳實踐

### ✅ DO（應該做）

- ✅ **定期檢查**：每天檢查是否有新文件進入 staging
- ✅ **及時標記**：新進文件立即標記狀態，不留空白
- ✅ **詳細分析筆記**：在文件頭部記錄分析過程和決策依據
- ✅ **保持簡潔**：staging 不是長期存儲，及時推進流程
- ✅ **版本控制**：所有 staging 文件都納入 git 版本控制

### ❌ DON'T（不應該做）

- ❌ **長期積壓**：不要讓文件在 staging 停留超過 7 天
- ❌ **忘記分類**：不要存放「還沒想好」的文件
- ❌ **混亂命名**：不要用模糊的名稱如「新文章」「待整理」
- ❌ **重複存儲**：staging 只是臨時區，不是備份區
- ❌ **未標記狀態**：不要將文件扔進去就不管

## 💬 Staging 的哲學

Staging 不是垃圾桶，也不是檔案室。

它是：
- **思考的空間** — 允許不確定性存在
- **分析的過程** — 從混亂到清晰的橋樑
- **決策的工具** — 幫助我們做出更好的分類選擇

一個好的 staging 系統，能讓知識從「零碎輸入」變成「有序產出」。
