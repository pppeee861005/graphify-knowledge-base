# 📘 Prompt 指南 — L2 Agent Teams 監測報告生成

> **用途**：複製本指南的 Prompt，即可在任何日期重跑「五信號板監測報告」的五班組協作流程。
> **模式**：L2 Agent Teams（施工隊協作 · 中心輻射 hub-and-spoke）
> **首次實戰**：2026-06-20（基調🟡執行滯後，token 消耗 192,482）

---

## 一、一句話啟動指令（給工頭/主控）

把下面這段貼給 Claude，並把 `{{日期}}` 換成目標日期（如 20260627）：

```
生成 五信號板完整監測報告_{{日期}}.md，採用 L2：Agent Teams（施工隊協作）模式
—— 中心輻射（hub-and-spoke），由我（工頭/主控）統一調度 5 個班組，班組之間
不直接對話，全部經主控轉派與仲裁。執行前先說你的理解，再執行。
```

**關鍵詞檢查表**（缺一不可，否則退化成普通問答）：
- ✅「L2 Agent Teams / 施工隊協作」→ 觸發多班組
- ✅「中心輻射 hub-and-spoke」→ 班組互不私聊
- ✅「經主控轉派與仲裁」→ 矛盾與廢棄判斷歸主控
- ✅「先說理解再執行」→ 防止跑偏

## 二、主控（工頭）的執行骨架（T0→T18）

```
T0  設定大方向：「三步驗證 — 源頭 → 現實 → 時效」
T1  第一波並行派遣：班組1（源頭）+ 班組2（現實·聯網）+ 班組3（時效）
T3  班組1矛盾回報 → 主控餵給班組4
T5  班組2數據回報 → 主控轉給班組3標時效
T7  ⚖️ 主控仲裁：早期版本是否廢棄/如何標記（非班組協商）
    第二波：班組2B（補查新情報）+ 班組4（口徑協調）
T10 班組4三大風險 → 主控轉給班組5設計監測
T13 主控收齊全部 → 查遺漏、版本一致、框架清晰
T15 工頭生成最終報告（三步驗證+四層對比+版本管理+決策建議）
T16 呈報決策人
T17 決策人裁示（廢棄/標記/監測頻率/監測計劃）
T18 主控協調執行裁示（編輯/git/匯入）
```

**依賴關係**（決定派遣波次）：
- 班組4 需要 班組1+2+3 的產出 → 排第二波
- 班組5 需要 班組4 的三大風險 → 排第三波（或第二波末）
- 班組1/2/3 互相獨立 → 第一波並行

## 三、五班組 Prompt 模板（主控派遣用）

> 每個班組都加開頭：「今天是 {{日期}}。全程繁體中文。產出回報主控，不直接給其他班組。」

### 班組1：數據源審查（源頭）
```
審查現有所有版本的可信度與內部矛盾，判斷哪些是「實時查證」、哪些是
「情景推演/假設」。必讀：歷史監測報告、README、即時數據查證檔、F5論斷。
回報主控：①版本清單+可信度評分(⭐) ②數據誤差證據表(逐項對標) 
③源頭性質判定(實時 vs 假設情景) ④廢棄建議(裁決權在主控)。
不要聯網——那是班組2的活。
```

### 班組2：現實核實（現實·**必聯網**）
```
實際聯網查詢(WebSearch/WebFetch) {{日期}}前後的真實數據：
①十年期美債殖利率 ②WTI原油 ③VIX ④伊朗里亞爾 ⑤地緣局勢(簽署/衝突/
海峽/制裁進度)。回報主控：實時值表(數值+來源+時戳+距紅線) + 地緣逐條 
+ 查證限制聲明 + 初步基調判斷。
⚠️鐵律：查不到就誠實說「無法查證」，絕不用推演填補——這是早期版本的致命錯誤。
```

### 班組3：時效性檢查（時效）
```
設計時效驗證框架，防止「歷史事件誤植當日」「推演當實時數據」再發生。
回報主控：①時效分級(F1鮮活24h/F2次新/F3過期/F4無時戳退回/S0推演隔離) 
②時序防錯檢查清單(可勾選) ③時戳標註規範[內容]⟨等級|發生時刻|來源|查證時刻⟩
④當日報告的時效陷阱提示。框架設計任務，不需聯網。
```

### 班組2B：補查（按需·聯網）
```
主控已掌握大局，只補查 {{尚未核實的新情報點}}。每點給：①查到的事實(來源+
時戳) ②查證限制(查不到就說) ③對基調判斷的影響(強化/修正/不變)。
⚠️同鐵律：查不到不可推演填補。
```

### 班組4：口徑協調（綜合·不聯網）
```
主控轉派三份原料：【A】班組1源頭結論【B】班組2實時數據【C】班組3時效框架。
回報主控：①四層對比表[維度|早期紅警版|前版|實時查證|裁定] ②最大三個矛盾
(量化誤差) ③整體基調裁定(雙向論證:為何不是🟢/為何不是🔴) ④60天三大風險
(描述+觸發信號+為何重要，供班組5)。
```

### 班組5：風險預警（設計·不聯網）
```
主控轉派班組4的三大風險。回報主控：①三大風險監測機制表[風險|指標|來源|
頻率|黃線|紅線|升級動作] ②監測頻率方案 ③60天時間軸(D+7/15/30/45/60里程碑)
④異常升級協議(P0/P1/P2)。參考既有五信號板格式。
```

## 四、主控的 6 道品質關卡（不可省）

| 關卡 | 檢查什麼 |
|------|---------|
| 三步驗證 | 每筆數據都過 源頭→現實→時效 |
| 聯網實證 | 班組2/2B 真的查網，不是憑記憶 |
| 用戶情報交叉驗證 | 用戶補的情報 × 班組查證 × 外媒，三方對標 |
| 時效標籤 | 週末/休市數據誠實標註，不冒充當日 |
| 主控仲裁 | 版本廢棄/標記統一裁決，非班組私聊 |
| 誠實缺口聲明 | 查不到的明說「無法查證、不推演填補」 |

**最高紅線**：🚫 **絕不把情景推演當實時數據**（這是早期紅警版油價+63%造假的根源）。

## 五、典型 token 消耗參考（6/20 實測）

| 班組類型 | 典型消耗 | 特徵 |
|---------|---------|------|
| 讀檔密集（班組1） | ~6萬 | 最貴，讀多份歷史檔深度對標 |
| 聯網查證（班組2/2B） | ~2.5-3萬/個 | 中等，依查詢次數 |
| 框架設計（班組3） | ~4.5萬 | 較重，清單+規範 |
| 純綜合（班組4/5） | ~1.5萬/個 | 最省，主控已餵齊原料、0工具 |
| **6班組合計** | **~19萬** | 不含主控主迴圈 |

**省 token 訣竅**：把原料在主控端整理好再餵給綜合型班組（4/5），它們就不必自行檢索，0 工具調用最省。
