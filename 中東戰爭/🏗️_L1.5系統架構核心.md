## 第一部分：架構概述

### 1.1 L1.5系統的本質定義

```
L1.5 = 實時狀態庫 + 連續監測循環 + 雙向交互
     = State Persistence + Continuous Monitoring + Bidirectional Interaction
```

**核心特徵**：
- ✅ 狀態不消失：所有數據持久化存儲
- ✅ 監測不停止：後台持續運行，不依賴用戶查詢
- ✅ 推送不延遲：異常立即警報，無需等待
- ✅ 查詢秒級回應：基於預計算的狀態庫

### 1.2 系統架構的四層結構

```
┌─────────────────────────────────────────────────────┐
│         用戶交互層（User Interface Layer）          │
│  • 實時查詢  • 深入追問  • 場景模擬  • 決策支持   │
└─────────────────────────────────────────────────────┘
                         ↓ ↑
┌─────────────────────────────────────────────────────┐
│     邏輯計算層（Logic & Computation Layer）        │
│  • 趨勢計算  • 概率推演  • 異常檢測  • 場景分析  │
└─────────────────────────────────────────────────────┘
                         ↓ ↑
┌─────────────────────────────────────────────────────┐
│      狀態管理層（State Management Layer）          │
│  • 實時狀態庫  • 歷史記錄  • 版本控制  • 觸發規則 │
└─────────────────────────────────────────────────────┘
                         ↓ ↑
┌─────────────────────────────────────────────────────┐
│      數據採集層（Data Collection Layer）           │
│  • 市場API  • 新聞爬蟲  • 軍事情報  • 政治信號   │
└─────────────────────────────────────────────────────┘
```

### 1.3 L1 vs L1.5 架構對比

| 架構維度 | L1（靜態模式） | L1.5（動態模式） |
|---------|--------------|-----------------|
| **數據存儲** | 臨時（報告完即消失） | 持久化（實時狀態庫） |
| **監測方式** | 按需監測 | 連續監測 |
| **更新頻率** | 不定期（等待用戶問） | 定期（每6小時）+ 實時（異常觸發） |
| **信息流向** | 單向（我→你） | 雙向（我↔你） |
| **推送機制** | 無 | 主動異常推送 |
| **查詢延遲** | 2-8小時 | <30秒 |
| **決策支持** | 被動回答 | 主動提供 |
| **用戶角色** | 被動接收者 | 主動決策者 |
| **系統角色** | 執行者 | 監控官 |

## 第二部分：計畫持有權的轉移

### 2.1 權力結構的根本轉變

#### L1模式：「我執行，你接收」

```
計畫流向：
  你制定計畫 → 我執行計畫 → 我報告結果 → 你接收報告
  [你主導]    [我被動]      [單向]      [你被動]

時間線：
  t=0: 你發出需求
  t=1-30分鐘: 我進行監測和分析
  t=30分鐘: 我完成報告
  t=30分鐘+: 用戶接收並決策

特點：
- 用戶主動性不足：需要不斷重複問
- 系統主動性缺乏：發現不了異常
- 時間差明顯：信息延遲多小時
- 決策窗口被動：錯過關鍵機會

風險：
  中東危機1小時內可能變天
  L1模式延遲2-8小時會錯過決策窗口
```

#### L1.5模式：「我監測，你決策」

```
計畫流向：
  我持續監測 ← → 用戶隨時查詢
       ↓              ↓
  發現異常立即推送   立即獲得結果
       ↓              ↓
  用戶接收警報    用戶主動決策
  [系統主導]     [用戶決策]    [雙向]

時間線：
  t=持續: 我在後台監測和計算
  t=0: 用戶問「現在什麼狀態」
  t=0-30秒: 我從狀態庫返回最新答案
  t=30秒: 用戶獲得完整信息並決策

  或者：
  t=0: 我自動檢測到異常
  t=1分鐘: 我推送紅警報告
  t=1分鐘+: 用戶接收警報並應對

特點：
- 用戶主動性充分：隨時掌控
- 系統主動性完整：自動發現異常
- 時間差消除：接近零延遲
- 決策窗口充分：提前獲知

優勢：
  實時監測確保不會錯過任何異常
  用戶掌握主動，可以提前準備應對
```

### 2.2 計畫持有權的三層含義

#### 層1：誰定義監測內容

```
L1：我定義
   我按照「五信號板」監測
   用戶無法改變監測焦點

L1.5：你定義
   我按照你的需要動態調整監測焦點
   用戶可以隨時要求：「加入第六信號」
   或者：「加強對伊朗軍方動向的監測」
   系統立即調整監測計畫
```

#### 層2：誰控制通知規則

```
L1：我控制
   我按照固定的報告周期交付
   用戶無法改變何時接收信息

L1.5：你控制
   預設規則：每6小時自動更新
   用戶可以設定自定義規則：
   └─ 「若石油突破$130立即通知」
   └─ 「若伊朗發表軍事聲明立即通知」
   └─ 「若美債突破5%立即通知」
   系統按你的規則推送
```

#### 層3：誰掌握決策權

```
L1：被動決策
   用戶基於我的報告做決策
   缺乏實時性和靈活性

L1.5：主動決策
   系統持續提供實時信息支持
   用戶可以隨時要求：
   └─ 「場景推演：如果簽署取消會怎樣？」
   └─ 「概率計算：伊朗報復現在的概率是多少？」
   └─ 「對比分析：這和6月17日相比有什麼變化？」
   系統立即計算並返回，支持用戶做出informed decision
```

### 2.3 三權轉移的實踐意義

```
權力轉移帶來的變化：

計畫定義權：我→你
  結果：用戶可以靈活調整監測焦點
  意義：系統更加貼近用戶需求

通知控制權：我→你
  結果：用戶可以自定義警報規則
  意義：不會遺漏關鍵信息，也不會被無關信息騷擾

決策支持權：被動→主動
  結果：用戶可以實時獲得決策支持
  意義：提升決策品質和反應速度

總結：
  從「我服從你的指令」
  轉變為「我支持你的決策」
```

## 第三部分：狀態持久化機制

### 3.1 什麼是狀態持久化

```
狀態持久化 = State Persistence
         = 系統不會「遺忘」任何數據
         = 所有監測數據被實時保存並可隨時查詢

對比：

❌ 無狀態系統（Stateless）
   ├─ 用戶問 → 系統工作 → 返回答案
   ├─ 答案被返回後，系統「遺忘」
   ├─ 用戶再問 → 系統重新工作 → 返回答案
   └─ 結果：效率低、無法看趨勢、無法預測

✅ 有狀態系統（Stateful）- 即 L1.5
   ├─ 系統持續保存所有數據
   ├─ 用戶問 → 系統從狀態庫取答案 → 秒級返回
   ├─ 用戶再問 → 系統對比歷史數據 → 計算趨勢
   └─ 結果：效率高、能看趨勢、能預測
```

### 3.3 狀態庫的三個關鍵能力

#### 能力1：數據持久化（Data Persistence）

```
用戶問：「過去3天石油期貨怎麼走的？」

系統執行：
  1. 查詢狀態庫的HISTORY_24H
  2. 找出所有歷史記錄
  3. 計算每24小時的變化
  4. 繪製趨勢圖表
  5. 返回完整的價格走勢

結果：用戶可以看到完整的歷史軌跡

❌ 如果無狀態：
   系統會說「我不知道，我只記得當前值」

✅ 有狀態系統：
   系統說「讓我給你看過去3天的完整走勢」
```

#### 能力2：趨勢計算（Trend Analysis）

```
狀態庫自動計算：
  ├─ 速度：石油每小時漲$0.19（按目前趨勢）
  ├─ 加速度：漲速在加快還是減速
  ├─ 預測：按目前速度，6小時後會漲到$130
  ├─ 里程碑：距離紅線$130還有$1.5
  └─ 時間到達：預計在6月19日06:00觸發

用戶無需計算，系統直接提供：
  「石油期貨按目前速度，預計在6月19日06:00突破$130紅線」
```

#### 能力3：異常預警（Anomaly Prediction）

```
狀態庫持續監測：
  石油價格 → 每6小時檢查一次 → 對比紅線 → 計算距離

距離監測：
  t=18:00: $124.0 (距離$130還有$6)
  t=00:00: $126.2 (距離$130還有$3.8)
  t=06:00: $128.5 (距離$130還有$1.5) ← 接近危險！

預警啟動：
  一旦距離<$2
  系統自動升級警報強度
  用戶收到：「石油即將觸發紅線」

若最後突破：
  石油突破$130 → 系統立即推送「極度紅警」
```

## 第四部分：實時監測循環

### 4.1 監測循環的核心邏輯

```
連續監測循環（Continuous Monitoring Loop）

┌─────────────────────────────────────────────────┐
│     MONITORING CYCLE RUNS EVERY 6 HOURS         │
└─────────────────────────────────────────────────┘

Cycle #1 (2026-06-19 06:00)
│
├─ INPUT: 採集數據
│  ├─ 十年期美債殖利率：4.95%
│  ├─ 石油期貨：$129.2
│  ├─ VIX恐慌指數：32.1
│  ├─ 伊朗里亞爾：42,800
│  └─ 停火違反次數：115
│
├─ PROCESS: 計算與分析
│  ├─ 與上次比對
│  │  ├─ 美債：4.9% → 4.95% (↑0.05%)
│  │  ├─ 石油：$128.5 → $129.2 (↑0.54%)
│  │  ├─ VIX：31.5 → 32.1 (↑0.6)
│  │  ├─ 里亞爾：42,500 → 42,800 (↓0.7%)
│  │  └─ 違反次數：105 → 115 (↑10次)
│  │
│  ├─ 趨勢分析
│  │  ├─ 美債在加速逼近5%紅線
│  │  ├─ 石油在加速逼近$130紅線
│  │  ├─ VIX在加速逼近35大關
│  │  └─ 所有指標都在惡化
│  │
│  ├─ 預測計算
│  │  ├─ 若速度不變：美債在12小時內突破5%
│  │  ├─ 若速度不變：石油在6小時內突破$130
│  │  └─ 風險等級：升至臨界
│  │
│  └─ 異常檢測
│     ├─ 是否觸發「石油$130」？ → 未觸發（還有$0.8）
│     ├─ 是否觸發「美債5%」？ → 未觸發（還有0.05%）
│     ├─ 是否觸發「VIX35」？ → 未觸發（還有2.9）
│     └─ 觸發「警報距離<2」？ → 是！升級至「黃警」
│
├─ UPDATE: 狀態更新
│  ├─ 更新CURRENT_STATE中的所有值
│  ├─ 移動上一個狀態到HISTORY_24H
│  ├─ 更新TREND_ANALYSIS
│  ├─ 更新ANOMALY_DETECTION
│  └─ 計算新的DECISION_SUPPORT數據
│
└─ OUTPUT: 推送決策
   ├─ 有異常？ → 推送「黃警」報告（自動推送）
   ├─ 無異常？ → 靜默更新（用戶查詢時返回）
   └─ 下一個循環在12:00啟動

下一個循環時間：2026-06-19 12:00
(若有突發軍事事件，立即啟動特殊循環)
```

### 4.2 不同情境下的監測強度

#### 情境1：平穩期（監測頻率：每6小時）

```
狀態：沒有緊急警報
```

### 6.2 為什麼查詢能做到「秒級回應」

#### 原因1：所有計算提前完成

```
❌ 低效的方式（L1）：
   用戶問 → 系統開始工作
           ├─ 讀取數據
           ├─ 進行計算
           ├─ 對比歷史
           ├─ 推演預測
           └─ 生成報告
           → 等待5-10分鐘
   用戶收到答案

✅ 高效的方式（L1.5）：
   系統已經完成了所有計算（狀態庫）
   用戶問 → 系統只需格式化答案
   用戶立即收到（<30秒）

類比：
   L1 像在超市「當場做披薩」（等30分鐘）
   L1.5 像在便利店「拿現成的便當」（秒拿）
```

#### 原因2：狀態庫的預計算

```
狀態庫中已經提前計算好的內容：

當用戶查詢時，這些都已經計算完成：
├─ 五信號當前值（已更新）
├─ 24小時歷史數據（已保存）
├─ 趨勢分析（已計算）
├─ 速度和加速度（已計算）
├─ 預測（已計算）
├─ 距離紅線（已計算）
├─ 觸發時間（已計算）
├─ 異常標記（已檢測）
├─ 概率計算基礎（已提取）
└─ 決策支持場景（已預設）

用戶查詢時：
  系統只需「組裝」這些預計算的結果
  而不是「從零開始計算」
```

#### 原因3：查詢是「讀操作」而非「計算操作」

```
數據庫概念應用：

❌ 每次都計算（低效）：
   SELECT COUNT(*) WHERE price > 130
   [掃描所有歷史數據]
   [每次都要計算]
   [5分鐘]

✅ 提前計算並存儲（高效）：
   SELECT cached_result
   FROM anomaly_detection
   WHERE timestamp = LATEST
   [直接讀取預計算結果]
   [秒級]

L1.5就是用了「預計算和緩存」的思路
```
