# 信任生產線 SOP

> **核心命題**:讀者從劇場進來,一路往源頭挖,挖到最底層發現是一篇凌晨的潦草戰報——那一刻的信任感,是任何精美文章都做不到的。
>
> **本文件定位**:四件套文體(戰報 → 機房 → 教科書 → 劇場)的開發流程標準作業程序。適用於 AI 指揮官筆記全部內容生產,以及所有開源專案(lease-guard-wf、stock-swarm-wf 等)的配套發布。
>
> **版本**:v1.0|**制定**:2026-06|**修訂規則**:每月覆盤日檢視一次,改了就升版號

## 第一章|生產線總圖

### 1.1 信息流向(單向,不可逆)

```
⚡ 戰報 ──長成──▶ 🏭 機房 ──提煉──▶ 📚 教科書 ──改編──▶ 🎭 劇場
(原始事實)      (完整收據)        (可複用模式)       (傳播敘事)

◀──────────────── 回鏈方向(每層往源頭掛連結)────────────────
```

**兩條方向各自的鐵律:**
- **信息只能順流**:劇場的情節必須能追溯到機房的報告;機房的數字必須源自戰報記錄的真實事件;教科書的模式必須有機房的實證。**禁止逆流**——不可以先編好故事再回頭補造收據。
- **連結只能回流**:每篇文章發布時,必須掛上它的上游源頭連結。劇場掛機房編號,機房掛源頭戰報,教科書掛實證機房。

### 1.2 四文體職責矩陣

| 文體 | 證明什麼 | 速度 | 修飾度 | 讀者 | 失敗模式 |
|------|----------|------|--------|------|----------|
| ⚡ 戰報 | 指揮官是活人,正在打仗 | 當天 | 潦草是優點 | 同行、鐵粉 | 膨脹(劇場感漏進收據區)、欠債不還 |
| 🏭 機房 | 仗是真的,數字可審計 | 里程碑後 3 日內 | 冷靜、零形容詞 | 開發者、嚴肅讀者 | 自評滿分、預估混充實測 |
| 📚 教科書 | 方法可學、可複用 | 模式被 ≥2 次實證後 | 結構化、完整 | 學習者、fork 者 | 代碼不可跑、紙上談兵 |
| 🎭 劇場 | 這件事值得在乎 | 不限 | 全力修飾 | 大眾、新讀者 | 虛構偽裝成真實 |

**判斷一篇內容屬於哪層的速查法**:看它最怕什麼。怕被發現是假的 → 機房;怕無聊 → 劇場;怕學不會 → 教科書;怕失去現場感 → 戰報。

## 第二章|各層作業規程

### 2.0 環境註記:GitHub 是生產線的地基

四文體是 Substack 上的呈現層;GitHub repo 是事實層。規則:**機房引用的每個數字,在 repo 的 `eval/` 或 commit 紀錄裡都找得到對應物**。文章可以刪改,git history 不會說謊——這是「可審計」的最終擔保。

### 2.1 ⚡ 戰報層

**觸發條件**:打完一仗就寫,不超過 24 小時。「仗」= 首次部署、踩到值得記的坑、燒穿預算、意外發現。

**寫作規則:**
1. 短。目標 300–800 字,超過就是在寫機房的東西,搬走。
2. 第一人稱,允許潦草、允許「細節待補」——但每個「待補」自動成為一筆債(見第三章)。
3. **禁止未定義的「成功」**。最低要求一個錨點數字:「跑了 4 小時,監控 8 檔,burn 0.3 單位,2 次警報,1 次誤報」。
4. **禁止技術膨脹**。秒級就寫秒級,不寫毫秒級;能跑就寫能跑,不寫完美。潦草是真實感,膨脹是劇場感漏進收據區。
5. 文末固定三件事:待辦清單、相關連結、(若涉投資/法律/健康)免責聲明。

**發布前 30 秒自查**:☐ 有錨點數字 ☐ 無膨脹詞 ☐ 待補項已登記債務台帳

### 2.2 🏭 機房層

**觸發條件**:里程碑完成(評測跑完、Phase 結束、真人測試結束)後 3 日內。

**寫作規則:**
1. **數字分艙**:每個數字標注「(實測)」或「(預估,待驗證)」。一篇混入一個被識破的預估值,全篇實測值被連坐。
2. **刪除所有自評**:禁用星級、「完美」「優秀」「精確控制」。評分者和被評者是同一個系統時,形容詞就是負資產。冷靜陳述,讓數字自己說話。
3. **「系統錯了什麼」為必填章節**:漏報、誤報、崩潰、循環性(AI 修 AI 自己生成的 bug 要如實標注),每項附根因。敢寫「檢查器沒抓到的 bug 有多少?我不知道,這正是 18% 覆蓋率的意思」這種話的人,市面上幾乎沒有——這就是差異化。
4. **內部一致性檢查**:成果欄宣稱的數字,不可與待辦欄矛盾(例:測試未運行,覆蓋率不得出現在成果欄)。
5. **加一層人聲**:開頭三句話(做了什麼實驗、花了多少、學到哪件反直覺的事)+ 結尾第一人稱(下次我會改什麼)。原始日誌建立信任,人的判斷建立追隨——收據不能沒有簽名者。
6. 文末掛:源頭戰報連結、repo 對應路徑(eval 報告 / commit)、免責聲明。

**發布前自查清單**:
☐ 實測/預估已分標 ☐ 零自評形容詞 ☐ 「系統錯了什麼」章節存在且非空
☐ 成果與待辦無矛盾 ☐ 有開頭人聲與結尾人聲 ☐ 回鏈戰報 ☐ repo 路徑可達 ☐ 免責聲明

### 2.3 📚 教科書層

**觸發條件**:同一模式在 **≥2 個機房報告**中被實證後,才有資格被抽象成教科書。一次成功是個案,兩次才是模式。

**寫作規則:**
1. **代碼不落地不發文**:文章中的每段代碼必須存在於 repo 且可運行。文章是 repo 的導讀,不是代碼的容器。
2. 必備五件:模式定義、適用/不適用場景、可跑的最小實例(指向 repo)、實證連結(≥2 篇機房)、fork/移植指南。
3. 標注模式的邊界與已知失效情況——教科書的可信度來自它承認自己哪裡不管用。
4. 鐵律條款(如三大鐵律)在 fork 指南中標注為「原封帶走,不可本地化」。

**發布前自查**:☐ 代碼在 repo 可跑 ☐ ≥2 機房實證已掛鏈 ☐ 失效邊界已寫明

### 2.4 🎭 劇場層

**觸發條件**:對應的機房報告已公開發布。**沒有機房,不准開演。**

**寫作規則:**
1. **開頭標明文體**:固定欄位「本篇為沙盤推演劇場,系統真實表現見機房報告 #N」。虛構與真實分艙是這一層的生死線。
2. **禁止虛構績效數字**:不寫具體報酬率、不寫「三週獲利 X%」。可虛構情節與人物,不可虛構收據。讀者爽點設計為「看穿」而非「賺到」——前者是供應決策能力,後者是踩進投顧灰色地帶。
3. 劇情中出現的系統能力,以對應機房報告實證過的為上限。劇場可以放大情緒,不可以放大能力。
4. 文末固定:對應機房編號連結、免責聲明(本篇情節與代號為劇情設計)。

**發布前自查**:☐ 開頭文體標注 ☐ 無虛構績效 ☐ 能力未超機房實證 ☐ 機房回鏈 ☐ 免責聲明

## 第三章|債務管理制度(回鏈紀律)

> 戰報允許先開支票,這是文體特權;特權的代價是支票必須兌現,且**還債要可見**。

### 3.1 規則
1. 戰報中每個「待補 / 細節後述 / 下篇再講」= 一筆債,發布當天登記入債務台帳(格式見專案追蹤表附表 A)。
2. 還債 = 細節文章發布 **+ 回頭編輯原戰報,在原「待補」處掛上連結**。兩個動作都完成才算清償。
3. 債齡上限 **30 天**。逾期二選一:還清,或回原文公開註記「此項不補了,原因:____」。沉默的爛尾是信任的慢性出血。
4. 每週覆盤日(週六)檢查台帳;**債務未清者,不開新戰報的新支票**(可發戰報,但不可再寫「待補」)。

### 3.2 還債的複利
讀者點進舊戰報看到債務被還清,信任複利;看到三個月前的「待補」原封不動,整個文體變成空頭支票機。**回鏈不是禮貌,是審計軌跡。**

## 第五章|紅線清單(任何一層皆適用)

1. **不虛構收據**——虛構的執行紀錄比沒有紀錄更糟:它把你從「還沒給證據的人」變成「給過假證據的人」。
2. **不寫具體報酬率**,除非有對帳單級證據;模擬盤成績必須標注模擬盤。
3. **涉投資、法律、健康內容,免責聲明無例外**,機房文體不豁免。
4. **不自評**。讓讀者評,讓數字評,讓時間評。
5. **不逆流生產**——先有故事再補造事實,生產線即報廢。

## 第六章|健康度指標(每月看一次)

- 債務清償率(30 天內清償 ÷ 總開債)→ 目標 100%
- 回鏈完整率(抽查 5 篇,上游連結可達比例)
- 機房自查清單違規數 → 目標 0
- 四文體比例:長期失衡警訊——只有劇場 = 在表演;只有機房 = 在自言自語;只有戰報 = 債台高築;只有教科書 = 脫離戰場
- 一個反直覺指標:**「系統錯了什麼」章節的字數**。它在變長,代表你在打更難的仗;它歸零,代表你開始說謊或停止成長,兩者都是警報

## 附錄|生產線的存在理由(新進協作者必讀)

AI 可以量產工整的文章,唯獨量產不了:凌晨打完仗的潦草、公開承認的漏報、還清的債務、和一條經得起往回挖的審計軌跡。

**這條生產線生產的不是內容,是「可審計性」。** 可審計,就是 AI 內容洪水時代裡,一個人類創作者最後的、也是最寬的護城河。
