# Dynamic Workflows - 問題與預算定義書

**版本**：1.0
**目的**：定義要解決的問題、驗證標準、預算限制
**不需要**：預先設計 Workflow、指定 Agent 數量、規劃代碼結構
**輸出給**：Claude Code（自動生成並執行 Dynamic Workflow）

---

## 一、問題定義

### 1.1 問題陳述

**用一句話清晰描述：你要解決什麼問題？**

例如：
- ❌ 「優化代碼」
- ✅ 「檢查 leave_approval.js 的語法、邏輯、Bug，並生成測試用例」

```markdown
我的問題：
[一句話陳述]
```

### 1.2 背景與約束

**為什麼要解決這個問題？有什麼限制條件？**

```markdown
背景：
- [背景信息 1]
- [背景信息 2]

約束條件：
- [約束 1]
- [約束 2]
```

### 1.3 輸入與輸出

**明確「進去什麼」和「出來什麼」**

```markdown
輸入（Input）：
- 類型：[什麼類型的數據/對象/文件]
- 規模：[多少？]
- 格式：[什麼格式？]

輸出（Output）：
- 類型：[什麼類型的結果]
- 格式：[結構化輸出？文本報告？]
- 關鍵信息：[必須包含什麼？]
```

## 二、驗證標準

### 2.1 成功指標（衡量成功的標準）

**定義 3-5 個具體、可測量的成功標準**

不需要說「怎麼做」，只需說「什麼是成功」

```markdown
成功指標：

| # | 指標 | 衡量方式 | 目標 |
|---|------|--------|------|
| 1 | [指標名稱] | [如何衡量] | [數值] |
| 2 | [指標名稱] | [如何衡量] | [數值] |
| 3 | [指標名稱] | [如何衡量] | [數值] |

例如：
| # | 指標 | 衡量方式 | 目標 |
|---|------|--------|------|
| 1 | Bug 發現率 | 自動檢查發現的 Bug 數 | ≥ 80% |
| 2 | 測試覆蓋率 | 生成的測試用例覆蓋 | ≥ 15% |
| 3 | 執行時間 | 從開始到完成的時間 | < 10 分鐘 |
| 4 | 成本精度 | 實際成本 vs 預定成本 | ≤ 10% 偏差 |
```

### 2.2 驗收標準（什麼時候認為完成了？）

**用黑白分明的條件定義「完成」**

```markdown
驗收條件：

- [ ] [具體的完成條件 1]
- [ ] [具體的完成條件 2]
- [ ] [具體的完成條件 3]

例如：
- [ ] 所有語法錯誤已識別並記錄
- [ ] 邏輯審查報告已生成
- [ ] 至少 20 個測試用例已創建
- [ ] 執行報告已生成且清晰可讀
- [ ] 成本在預定預算 ±10% 範圍內
```

### 2.3 失敗標準（什麼時候停止？）

**定義失敗或升級的條件**

```markdown
失敗/升級條件：

- 若 [條件 A] → [升級給人工] 或 [使用降級方案]
- 若 [條件 B] → [終止執行]

例如：
- 若 Bug 發現率 < 50% → 升級給人工代碼審查
- 若 Token 消耗超過預算的 120% → 終止並返回部分結果
- 若 Agent 衝突無法解決 → 升級給 HR VP 人工決策
```

## 三、執行策略

### 3.1 目標陳述

**用一句話說：你期望 Claude Code 幫你做什麼？**

不是「怎麼做」，而是「做什麼」

```markdown
目標：
[一句話]

例如：
- 「自動檢查代碼質量，發現所有 Bug，生成修復建議」
- 「評估員工申請，檢查政策和法律合規性，給出審批建議」
- 「批量驗證 100 份文檔的安全性和合規性，生成匯總報告」
```

### 3.2 執行思路（完全由 Claude Code 動態編排）

**只描述最終目標和限制條件，Stage 由 Claude Code 自動決定**

```markdown
執行思路：

[用一句話或幾句話描述最終目標，讓 Claude Code 決定需要多少 Stage、
每個 Stage 用什麼 Agent、用什麼執行模式（並行/串行/對抗等）]

例如（✅ 正確的寫法）：
"評估這份申請是否符合公司政策和法律要求，
若有衝突則標記並升級給人工決策，
若沒有衝突則給出最終批准/拒絕建議"

或者（✅ 另一種寫法）：
"從多個維度檢查代碼質量（具體維度和檢查順序由 Claude Code 決定），
綜合評分，生成改進建議"

或者（✅ 最簡潔的寫法）：
"驗證這 100 份文檔是否符合安全和合規標準"

❌ 錯誤的寫法（預先設計 Stage）：
"Stage 1: 語法檢查（Haiku）
 Stage 2: 邏輯審查（Sonnet）→ 並行政策+法律檢查
 Stage 3: 決策（決策 Agent）"
```

### 3.3 限制條件和約束

**定義「邊界」而不是「流程」**

```markdown
限制條件：

- [約束 1]：[具體說明]
- [約束 2]：[具體說明]
- [約束 3]：[具體說明]

例如：
- 不能修改原始數據
- 必須保留完整的審計日誌
- 若出現模糊情況，優先保守（傾向拒絕）
- 所有決策必須有清晰的理由說明

或者：
- 檢查應該儘量並行（節省時間）
- 但不要超過 5 個並行檢查（控制複雜度）
- 若某個檢查失敗，應該嘗試降級而不是直接失敗
```

### 3.4 決策規則

**定義「在什麼情況下應該怎麼決策」，讓 Claude Code 自動編排實現方式**

```markdown
決策規則：

規則 1：[條件] → [決策結果]

規則 2：[條件] → [決策結果]

規則 3：[條件] → [決策結果]

例如：
規則 1：若各維度評分都 ≥ 80
       → 最終決策：APPROVE（批准）

規則 2：若有維度評分 < 60
       → 最終決策：REJECT（拒絕），記錄原因

規則 3：若有維度評分在 60-80 之間（模糊區域）
       → 升級給人工：返回詳細評分和分析，供人工決策

或者：
規則 1：若政策檢查 PASS 且法律檢查 PASS
       → 最終決策：APPROVED

規則 2：若政策檢查 FAIL 或法律檢查 FAIL
       → 最終決策：REJECTED

規則 3：若政策檢查和法律檢查結論矛盾（一個 PASS 一個 FAIL）
       → 最終決策：ESCALATED（升級給人工）
```

### 3.5 降級與升級條件

**定義「什麼情況下要降級或升級」，具體怎麼降級/升級由 Claude Code 決定**

```markdown
降級條件（自動簡化，不升級）：

條件 1：[什麼情況下應該簡化？]
→ 簡化方向：[向什麼方向簡化]
→ 結果標記：[標記為 PARTIAL / DEGRADED 等]

條件 2：[什麼情況下應該簡化？]
→ 簡化方向：[向什麼方向簡化]
→ 結果標記：[標記為什麼]

例如：
條件 1：若 Token 消耗達到 80%
→ 簡化方向：停止低優先級檢查，只完成高優先級
→ 結果標記：PARTIAL_COMPLETION

條件 2：若某個檢查項無法驗證
→ 簡化方向：使用保守估計（默認為 FAIL/REJECT）
→ 結果標記：CONSERVATIVE_ESTIMATE

升級條件（需要人工介入）：

條件 1：[什麼情況下必須升級給人工？]
→ 升級給：[誰決策]
→ 提供給人工：[什麼信息]

條件 2：[什麼情況下必須升級給人工？]
→ 升級給：[誰決策]
→ 提供給人工：[什麼信息]

例如：
條件 1：若自動決策邏輯無法覆蓋（模糊區域）
→ 升級給：決策者/主管
→ 提供信息：完整的檢查結果、為什麼無法自動決策、建議的決策方向

條件 2：若發現潛在衝突（多個維度有不同意見）
→ 升級給：部門負責人
→ 提供信息：各維度的評分、衝突點、完整的分析報告

條件 3：若成本超支 (> 120%)
→ 升級給：項目經理
→ 提供信息：當前成本、已完成的工作、剩餘未完成的工作
```

## 四、預算分配

### 4.1 預算概況

```markdown
**總預算**：[X] 單位（或相當於 Y 美元）

**預留率**：[Z]%（建議 ≥ 50%）

**說明**：
- 預算用途：[主要用在什麼上]
- 預期成本：[預估多少成本]
- 應急預留：[多少預算用於應急]
```

### 4.2 成本估算邏輯

**根據「問題的複雜度」和「輸入規模」估算，不需要預先規劃每個 Phase**

```markdown
成本估算依據：

輸入規模：[多少數據/項目/文件]
複雜度：[簡單/中等/複雜]
需要的模型：[主要使用什麼模型]

估算公式（參考）：
- 快速檢查（Haiku）：0.05 單位 / 個
- 標準分析（Sonnet）：0.2 單位 / 個
- 複雜決策（Opus）：0.5 單位 / 個

例如：
"預期需要 1 次快速語法檢查（Haiku，0.05）
+ 1 次邏輯分析（Sonnet，0.2）
+ 1 次測試生成（Sonnet，0.3）
= 約 0.55 單位"

或者：
"需要檢查 100 份文件，每份約 0.01 單位
= 約 1 單位（再加 50% 預留 = 1.5 單位）"
```

### 4.3 成本敏感性

**定義在成本超出時應該怎麼辦**

```markdown
成本敏感性：

- 若成本達到預算的 80% → [警告 / 進入節省模式]
- 若成本達到預算的 100% → [終止 / 返回部分結果]
- 若成本達到預算的 120% → [立即停止，升級]

例如：
- 若成本達到 0.4 單位（預算 0.5 的 80%）
  → 進入節省模式：只處理優先級最高的檢查項

- 若成本達到 0.5 單位（預算上限）
  → 返回已完成的結果，標記為 PARTIAL_COMPLETION

- 若成本超過 0.6 單位（超支 20%）
  → 立即終止，升級給用戶決策
```

## 📋 使用範例

### 例 1：代碼檢查和測試

```markdown
# 新世界 HR 系統 Phase 1 - 問題與預算定義書

## 一、問題定義

### 1.1 問題陳述
檢查 leave_approval.js 的語法、邏輯、Bug，
並生成足夠的單元測試確保關鍵功能有覆蓋。

### 1.2 背景與約束
背景：
- 代碼已初步實現，需要質量保障
- 依賴 Google Workspace API 和自定義工具函數
- 有 4 個依賴的 sub-workflow（checkPolicy, checkCompliance）

約束：
- 不能修改現有 API 接口
- 不能修改 Google Workspace 集成邏輯
- 只能改進代碼質量和測試

### 1.3 輸入與輸出

輸入：
- 類型：JavaScript 代碼檔案集合
- 規模：5 個主文件 + 3 個工具文件
- 格式：.js 檔案

輸出：
- 類型：Bug 列表、修復建議、測試代碼
- 格式：Markdown 報告 + JavaScript 測試檔案
- 關鍵信息：每個 Bug 的嚴重度、修復方案、測試覆蓋範圍

## 二、驗證標準

### 2.1 成功指標

| # | 指標 | 衡量方式 | 目標 |
|---|------|--------|------|
| 1 | Bug 發現和修復 | 發現的 Bug 數 / 修復數 | ≥ 80% |
| 2 | 測試用例數 | 自動生成的測試數 | ≥ 20 個 |
| 3 | 測試覆蓋率 | 代碼覆蓋率工具測量 | ≥ 15% |
| 4 | 執行時間 | 從開始到完成 | < 15 分鐘 |
| 5 | 成本控制 | 實際成本 / 預定成本 | ≤ 100% |

### 2.2 驗收標準

- [ ] 發現並記錄所有明顯的語法和邏輯錯誤
- [ ] 生成至少 20 個測試用例
- [ ] 測試覆蓋率 ≥ 15%
- [ ] 提供修復建議，清晰說明修改位置
- [ ] 執行報告包含所有 Bug 和測試用例清單
- [ ] 成本在預定範圍內

### 2.3 失敗標準

- 若 Bug 發現率 < 50% → 升級給人工代碼審查
- 若生成測試 < 15 個 → 完成現有測試，標記為 PARTIAL
- 若成本超過預算 20% 以上 → 停止，返回已完成結果

## 三、執行策略

### 3.1 目標陳述
自動識別代碼中的所有問題（語法、邏輯、可靠性），
並生成修復建議和測試代碼，確保代碼質量達到可交付標準。

### 3.2 執行思路

由 Claude Code 自動決定檢查的順序和方式：
評估代碼質量，發現所有語法和邏輯問題，
生成修復建議和測試代碼。

（具體用什麼 Stage、什麼執行模式由 Claude Code 動態決定）

### 3.3 限制條件

- 不能修改原始代碼檔案
- 必須記錄每個 Bug 的位置、嚴重度、修復建議
- 若某個依賴無法驗證，使用保守估計（假設有問題）
- 測試代碼必須可直接運行

### 3.4 決策規則

規則 1：若發現的 Bug 嚴重度為 Critical
       → 優先排序，首先處理

規則 2：若無法驗證某個工具函數的正確性
       → 標記為「需要人工驗證」

規則 3：若發現設計級別的問題（不只是實現 Bug）
       → 升級給 Code Owner，由人工決策是否修改架構

規則 4：若生成的測試覆蓋率達到目標（≥15%）
       → 完成，返回結果

### 3.5 降級與升級條件

降級條件：
- 若 Token 消耗達到 80% → 停止低優先級檢查，返回已發現的結果
- 若某個檢查項超時 → 跳過，標記為「超時」

升級條件：
- 若發現設計級別缺陷 → 升級給 Technical Lead
- 若無法自動判斷修復方案 → 升級給代碼作者確認
- 若成本即將超支 → 升級給項目經理決策是否繼續

## 四、預算分配

**總預算**：1 單位
**預留率**：70%（預期成本 0.3-0.4，預留 0.6+）

成本估算依據：

輸入規模：5 個 JS 檔案（總約 2000 行代碼）
複雜度：中等（涉及 API 調用和複雜邏輯）
預期需要：多個檢查維度 + 測試生成

參考數據：
- 簡單檢查（Haiku）：約 0.05-0.1 單位
- 標準分析（Sonnet）：約 0.2-0.4 單位 / 維度
- 測試生成（Sonnet）：約 0.2-0.3 單位

粗略估算：0.5-0.7 單位
預留 50% → 總預算 1 單位

（Claude Code 會根據實際需要優化成本）

成本監控策略：
- 若成本達到 0.8 單位 → 警告，進入節省模式
- 若成本達到 1.0 單位 → 返回部分結果
- 若成本達到 1.2 單位 → 立即停止並報告

## 五、預期成果物

執行報告應包含：
- [ ] Bug 清單（ID、檔案、位置、描述、嚴重度）
- [ ] 修復建議（代碼片段、原因說明）
- [ ] 測試用例代碼（可直接運行）
- [ ] 測試覆蓋率分析
- [ ] 成本統計和預算分析
- [ ] 改進建議

## 六、額外信息

相關背景：
- 項目：新世界 HR 系統 Phase 1
- 前期執行報告：執行報告_完整版.md
- 相關檔案：leave_approval.js, checkPolicy.js, checkCompliance.js
```

## 💡 填寫建議

### ✅ 好的做法
- 描述「是什麼問題」，而不是「怎麼解決」
- 用具體的數字定義成功標準
- 考慮邊界情況和失敗場景
- 預留充足的預算（≥50%）
- 清晰說明決策點，讓 Claude Code 自動判斷

### ❌ 避免的做法
- 預先指定 Agent 數量或名稱
- 設計 Workflow 架構細節
- 過度詳細（應該 1-2 頁）
- 預算預留太少
- 決策條件含糊不清

## 🎯 核心要點

**這份文檔的目的不是讓你「做得很細」，而是讓 Claude Code 理解：**

1. **你要解決什麼問題**（清晰的目標）
2. **怎樣才算成功**（具體的指標和驗收標準）
3. **預算限制是什麼**（成本上限和預留策略）
4. **在什麼情況下應該怎麼決策**（決策邏輯，不是實現細節）

**然後 Claude Code 會自動決定：**
- 需要多少個 Agent
- 用什麼執行模式（Pipeline / Aggregation / Adversarial 等）
- 如何優化成本
- 何時升級給人工
