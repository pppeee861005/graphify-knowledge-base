# Dynamic Workflows 最佳實踐

**目的**：避免常見錯誤，最大化 Workflow 執行效果
**適合**：已經理解基本概念，想要優化的用戶

---

## 實踐 1：寫清晰的問題陳述

### ❌ 不清晰的例子

```
"優化代碼"
"改進系統"
"做一個檢查"
```

→ Claude Code 不知道你到底要什麼，會浪費時間猜測

### ✅ 清晰的例子

```
"檢查 leave_approval.js 的語法正確性、邏輯完整性和 API 調用有效性，
識別所有 Bug，並生成單元測試確保核心功能有覆蓋"
```

→ Claude Code 立即明白：
- 輸入：leave_approval.js
- 檢查維度：語法 + 邏輯 + API 有效性
- 輸出：Bug 列表 + 測試代碼

### 💡 技巧

**用「從...到...」的結構**：
```
"從 [輸入] 開始，
檢查 [多少個維度]，
最終輸出 [什麼結果]"
```

例子：
```
"從 100 份客戶反饋開始，
檢查情感傾向（正面/中立/負面）和關鍵問題分類，
最終輸出分類統計和優先級排序的問題清單"
```

## 實踐 2：定義具體的成功指標（而不是模糊的目標）

### ❌ 模糊的例子

```
成功指標：
- Bug 發現率要高
- 測試覆蓋要好
- 成本要便宜
```

→ 太模糊，Claude Code 不知道「高」是多少、「好」是什麼標準

### ✅ 具體的例子

```
成功指標：
- Bug 發現率 ≥ 80%（發現的 Bug 數 ÷ 預期的 Bug 總數）
- 測試覆蓋率 ≥ 15%（行覆蓋率）
- 成本 ≤ 0.5 單位
- 執行時間 < 10 分鐘
```

→ 清晰明確，Claude Code 可以準確驗證

### 💡 技巧

**用「數字 + 衡量方式」的組合**：

| 指標 | 模糊 | 具體 |
|------|------|------|
| Bug 發現 | 要找到所有 Bug | 發現率 ≥ 80% |
| 代碼質量 | 質量要好 | 複雜度 < 10，覆蓋率 ≥ 15% |
| 成本控制 | 成本要低 | 不超過 0.5 單位 |
| 執行速度 | 要快速 | 完成時間 < 10 分鐘 |

## 實踐 3：明確的決策規則（而不是讓 Claude Code 猜）

### ❌ 模糊的例子

```
決策規則：
- 若發現問題就標記
- 若有衝突就解決
- 若無法確定就默認通過
```

→ 太模糊，Claude Code 不知道「標記為什麼」、「怎麼解決」、「為什麼要默認通過」

### ✅ 明確的例子

```
決策規則：
- 若發現 Critical 級別 Bug → 優先處理，生成修復方案
- 若有 2 個 Agent 意見不一致 → 升級給人工，返回詳細對比
- 若無法驗證某個依賴 → 假設它有問題（保守估計），記錄理由
- 若測試覆蓋率達到 15% → 完成，停止生成更多測試
```

→ 完全清晰，Claude Code 知道怎麼做

### 💡 技巧

**用「若...則...」的邏輯**：

```
若 [具體條件] → [具體行動] → [標記為什麼狀態]

例如：
若 API 調用返回超時 → 重試一次，若仍超時則使用 cache
若 Bug 嚴重度為 Critical → 立即報告，不等待其他 Bug
若某個檢查項得分在 60-80 之間 → 標記為"需人工確認"
```

## 實踐 4：充足的預算預留（≥ 50%）

### ❌ 危險的預算

```
總預算：0.5 單位
預期成本：0.45 單位
預留：0.05 單位（10%）

→ 只要有一點點變化就會超支！
```

### ✅ 安全的預算

```
總預算：1.0 單位
預期成本：0.35 單位
預留：0.65 單位（65%）

→ 即使遇到變化也有緩衝
```

### 💡 技巧

**根據複雜度調整預留率**：

| 複雜度 | 預留率 | 說明 |
|--------|--------|------|
| 簡單（單個檢查） | ≥ 30% | 邏輯清晰，不確定因素少 |
| 中等（多維度評估） | ≥ 50% | 有多個檢查維度，可能有互動 |
| 複雜（多 Agent 對抗） | ≥ 70% | 有衝突解決、升級等不確定性 |

**預算分段**：
```
總預算：1.0 單位

分段：
- 必需成本：0.3 單位（確定要花的）
- 進階成本：0.2 單位（可能需要）
- 應急預留：0.5 單位（以防萬一）

監控：
- 達到 30% → 正常
- 達到 50% → 進入節省模式
- 達到 80% → 警告
- 達到 100% → 停止
```

## 實踐 5：明確的降級與升級條件

### ❌ 模糊的例子

```
降級策略：若遇到問題就簡化處理
升級策略：若有需要就升級給人工
```

→ 不清楚什麼是「問題」、什麼時候「有需要」

### ✅ 明確的例子

```
降級條件：
- 若某個 Agent 耗時 > 30 秒 → 使用上次的 cache 結果
- 若 Token 消耗達到 80% → 停止低優先級檢查，只完成高優先級
- 若某個檢查無法獲得確定答案 → 使用保守估計（假設不通過）

升級條件：
- 若發現架構級別問題（不只是實現 Bug）→ 升級給架構師人工審核
- 若有無法自動解決的衝突 → 升級給決策人，返回完整分析
- 若成本接近上限 → 升級給項目經理，由其決策是否繼續
```

→ 非常清晰，Claude Code 知道什麼時候簡化，什麼時候升級

### 💡 技巧

**分層級定義**：

```
Level 1 - 自動簡化（不升級，繼續執行）：
  - 某個檢查超時 → 跳過，記錄為「超時」
  - Token 用量過高 → 停止低優先級，完成高優先級

Level 2 - 人工介入（升級）：
  - 發現無法自動決策的衝突 → 升級給 [人物名稱]
  - 發現架構級別問題 → 升級給 [人物名稱]
  - 成本即將超支 → 升級給 [人物名稱]

Level 3 - 完全停止：
  - 成本超支 > 20% → 立即停止，返回已完成結果
  - 遇到系統錯誤 → 停止並報告
```

## 實踐 6：信任 Claude Code 的自動決策

### ❌ 不信任的做法

```
"我要確保 Workflow 用 Pipeline 模式"
"我要指定用 3 個 Agent"
"我要控制每個 Stage 的成本"
```

→ 你在做 Claude Code 應該做的事，浪費時間和預算

### ✅ 信任的做法

```
"我定義目標和約束，Claude Code 自動選擇最優的 Workflow 設計"
"我定義決策規則，Claude Code 自動決定何時升級"
"我定義預算上限，Claude Code 自動優化成本"
```

→ 充分利用自動化，專注於業務邏輯

### 💡 技巧

**定義「邊界」而不是「方案」**：

| 錯誤做法 | 正確做法 |
|---------|---------|
| 「用 Sonnet 做邏輯檢查」 | 「需要深度邏輯分析，Claude Code 選擇模型」 |
| 「先做語法檢查再做邏輯檢查」 | 「檢查語法和邏輯，順序由 Claude Code 決定」 |
| 「3 個 Agent 並行執行」 | 「需要多維度評估，並行數由 Claude Code 決定」 |
| 「每個維度最多 0.1 單位」 | 「總預算 0.5，Claude Code 優化分配」 |

## 實踐 7：驗收條件要可驗證

### ❌ 無法驗證的例子

```
驗收條件：
- [ ] Bug 修復得好
- [ ] 測試寫得充分
- [ ] 成本要合理
```

→ 「好」「充分」「合理」都是主觀的，無法自動驗證

### ✅ 可驗證的例子

```
驗收條件：
- [ ] 發現並記錄的 Bug 數 ≥ 預期的 50%
- [ ] 生成的測試用例數 ≥ 20 個
- [ ] 測試覆蓋率（行數）≥ 15%
- [ ] 實際成本 ≤ 預定預算的 110%
- [ ] 執行時間 < 15 分鐘
```

→ 全部可以用數據驗證

### 💡 技巧

**用測量標準替代評判標準**：

| 評判標準（❌） | 測量標準（✅） |
|--------------|-------------|
| Bug 修復好 | Bug 嚴重度 Critical 的修復率 ≥ 90% |
| 測試充分 | 測試覆蓋率 ≥ 15%，用例 ≥ 20 個 |
| 成本合理 | 實際成本 ≤ 預定預算 × 1.1 |
| 質量高 | 關鍵功能的測試通過率 100% |
| 速度快 | 完成時間 < [具體時間] |

## 實踐 8：記錄執行經驗（形成個人最佳實踐）

### 執行完一個 Workflow 後，記錄：

```markdown
# 執行經驗記錄

**項目**：[項目名稱]
**執行日期**：[日期]
**成本**：預定 0.5，實際 0.48（精度 96%）

## 發現的規律

1. **代碼檢查的成本**：
   - 語法檢查（Haiku）：約 0.05 單位
   - 邏輯分析（Sonnet）：約 0.2-0.3 單位
   - 測試生成（Sonnet）：約 0.2-0.25 單位

2. **執行時間**：
   - 2000 行代碼 → 約 8-10 分鐘

3. **有效的決策規則**：
   - 若 Bug 超過 20 個 → 分優先級處理很有效
   - 若政策和法律衝突 → 升級給人工是正確的

4. **下次改進**：
   - 增加測試維度，預計成本增加 10-15%
   - 調整預算預留為 60%，更安全

## 個人最佳實踐總結

- 對於[類型]的問題，預留[Y]%預算比較安全
- [某個決策規則]效果很好，可以複用
- [某個升級條件]必須明確，否則容易出現[問題]
```

→ 積累後，你對「類似問題」的預算估算和規則設計會越來越準確

## 實踐 9：監控「實際 vs 預定」的偏差

### 執行完後，分析：

```
預定成本：0.5
實際成本：0.48
偏差：-4%（好的範圍內，< 10%）

↓ 分析原因 ↓

原因：
- 語法檢查比預期快（代碼質量較高）
- 測試生成接近預期
- 沒有觸發升級（衝突很少）

學習：
- 下次類似項目可以稍微降低預留（60% → 50%）
- 語法檢查的成本可以從 0.05 改為 0.04
```

### 監控表：

| 項目 | 預定 | 實際 | 偏差 | 原因 | 改進 |
|------|------|------|------|------|------|
| [項目 1] | 0.5 | 0.48 | -4% | [原因] | [改進] |
| [項目 2] | 0.6 | 0.65 | +8% | [原因] | [改進] |
| [項目 3] | 0.4 | 0.38 | -5% | [原因] | [改進] |

## 實踐 10：分享和複用決策規則

### 發現了有效的規則後：

✅ **複用到類似項目**：
```
HR 系統的規則：
"若政策和法律衝突 → 升級給 VP"

複用到：
- 採購審批系統
- 合同審查系統
- 員工晉升審批
```

✅ **分享給團隊**：
```
最佳實踐：
"在評估類問題中，決策規則分為 3 層：
  Layer 1 - 自動決策（規則清晰）
  Layer 2 - 人工升級（有衝突）
  Layer 3 - 停止（成本超支）

這個框架適用於 HR、採購、合規等所有審批場景"
```

→ 個人最佳實踐變成團隊資產

## 📊 最佳實踐檢查清單

### 在提交定義書前，檢查：

- [ ] 問題陳述清晰，沒有模糊詞彙（「好」「高」「低」等）
- [ ] 成功指標都是具體數字，能夠衡量
- [ ] 決策規則明確，「若...則...」邏輯完整
- [ ] 降級和升級條件都定義了
- [ ] 預算預留 ≥ 50%
- [ ] 驗收條件可驗證，不是主觀判斷
- [ ] 輸入和輸出明確
- [ ] 沒有預先設計 Stage、Agent 或執行模式

---

**核心總結**：

> **好的定義書，應該清晰到讓 Claude Code 無需任何猜測。
> 模糊之處越少，Workflow 執行得越高效。**
