在 Codex Multi-agent V2 的 **Graph Engineering** 範式中，**「對抗性審查」（Adversarial Review）** 是一種透過多個獨立且異質的 Subagent 同時對同一份代碼進行多維度檢查的機制，旨在透過「複數視角」與「模型競爭」來大幅提高代碼質量與 bug 檢出率。

以下是它在 Subagent 中運作的具體方式：

### 1. 多模型並行調度
對抗性審查的核心在於**「異質性」**。開發者會要求主 Agent 調配多個使用**不同底層模型**（如 Kimi、MiniMax、GPT-4o）的 Subagent。
*   每個 Subagent 代表一個獨立的**「審查軌道」（Review Track）**。
*   由於不同模型的訓練數據和推理邏輯不同，它們能從不同角度發現代碼中的漏洞。

### 2. 角色分工與專業化
在對抗性審查流程中，每個 Subagent 可以被賦予不同的側重點或工具：
*   **模型配置：** 可以為不同的審查任務配置不同的推理層級（Thinking Level），例如將關鍵的安全性審查設置為「高推理等級」。
*   **工具調用：** 某些 Subagent 可能專門調用 **Pi Agent** 工具進行代碼分析，而另一個 Subagent 可能負責使用 **Super Design** 插件審查 UI 邏輯。

### 3. 主 Agent 的調度與彙總
這種審查並非雜亂無章，而是由一個強大的主 Agent（通常使用 GPT-4o 等高級模型）擔任**調度者（Dispatcher）**：
*   **任務拆解：** 主 Agent 將對抗審查任務下發給各個 Subagent。
*   **動態派生：** 系統能根據任務複雜度，動態生成多個專門負責特定漏洞掃描或性能優化的子代理。
*   **結果合併：** 當所有審查軌道完成任務後，主 Agent 會**收集、判斷並合併**所有 Subagent 的詳細輸出結果，分析其中的差異，最終給出一個統一且經過交叉驗證的結論。

### 4. 效益：節省成本與提升效率
透過這種方式，開發者可以將較簡單的審查分派給成本較低的國產模型（如 Kimi 或 MiniMax），僅在需要高難度調度時使用 GPT 模型，從而在保證審查強度的同時，精確控制 **Token 消耗**。

總結來說，對抗性審查將開發流程從「單一 AI 的自我檢查」提升到了**「多模型協作與對抗」**的層級，這是 Graph Engineering 範式下自動化工作流的高級體現。
