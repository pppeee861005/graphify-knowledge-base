# 循環工程
## 從提示詞到系統的範式轉移

> **核心問題**：如何從「每次都手動下命令」進化到「系統自動運轉」？
>
> **核心答案**：建立一套能自我提示、自我驗證、自我修復的閉環。

---

## 第一層：範式轉變

### 舊世界 ← → 新世界

```
舊：工程師寫提示詞
    → Agent 執行
    → 工程師看結果
    → 工程師寫下一個提示詞
    （無限循環，工程師永遠在）

新：工程師設計系統
    → 系統自我提示
    → 系統自我執行
    → 系統自我驗證
    → 工程師只需監督
    （人類終於可以休息）
```

### 轉變的本質

| 維度 | 舊思路 | 新思路 |
|------|--------|--------|
| **觸發** | 人工手動 | 自動定時 (`/loop`) |
| **目標** | 逐步指令 | 直接目標 (`/goal`) |
| **記憶** | 每次重新解釋 | 持久化知識 (`Skills`) |
| **衝突** | 手工協調 | 物理隔離 (`Worktrees`) |
| **驗證** | 人工檢查 | 獨立校驗 (`Sub-agents`) |
| **集成** | 孤立文件 | 生態連接 (`Connectors`) |

---

## 第二層：五大支柱

### ❤️ 1. 心跳（Automations）

**是什麼**：系統的節奏感，不是人的節奏

```
/loop（定時任務）
  └─ 每小時/每天自動運行
  └─ 例：自動分類 Issue、生成日報、檢查健康度
  └─ 特點：無需人工觸發，無需等待

/goal（目標驅動）
  └─ 持續迭代直到成功
  └─ 例：「所有測試通過」「代碼無警告」
  └─ 特點：不達目標不停止，無人監督自動完成
```

**現實意義**：
```
之前：工程師每天檢查進度（重複、低效、易遺漏）
現在：系統自動檢查，遇到問題自動報告
結果：工程師解放，系統始終清醒
```

---

### 🌳 2. 隔離（Worktrees）

**是什麼**：多個 Agent 在同一倉庫平行工作，卻互不干擾

```
傳統做法：
  Agent A 改 main 分支
  Agent B 改 main 分支
  → 衝突 → 手工解決 → 浪費時間

Worktrees 做法：
  Agent A 在 worktree-A 工作
  Agent B 在 worktree-B 工作
  Agent C 在 worktree-C 工作
  → 完全隔離 → 自動並行 → 任務完成後自動清理
```

**現實意義**：
```
之前：只能一個 Agent 做完，下一個再開始（串聯）
現在：十個 Agent 同時做十個事，互不打擾（並行）
結果：效率提升 10 倍，零衝突
```

---

### 📚 3. 記憶（Skills）

**是什麼**：系統的「經驗庫」，而非工程師的大腦

```
規範文件（SOP）
  └─ 「我們怎樣寫代碼」
  └─ Agent 自動讀取並遵循

技能文件（Skills）
  └─ 「過去學到的最佳實踐」
  └─ Agent 自動調用並複用

狀態文件（Progress）
  └─ 「我們現在進度如何」
  └─ 系統第二天從這裡繼續
```

**現實意義**：
```
之前：每個新對話都要說「我們的項目是...」（意圖債務）
現在：Agent 從 Skills 庫自動讀取背景（零重複）
結果：Agent 永不迷茫，系統記性比人更好
```

---

### 🔗 4. 連接（Connectors）

**是什麼**：系統與外部世界的橋樑

```
File System
    ↓
Database
    ↓
Issue Tracker ← Agent
    ↓
CI/CD Pipeline
    ↓
Communication Tools
```

**能做的事**：
- 自動讀取需求（從 GitHub Issues）
- 自動查詢數據（從數據庫）
- 自動創建 PR（完成後）
- 自動更新工單（實時進度）
- 自動通知團隊（結果發布）

**現實意義**：
```
之前：「嘿，Agent 完成了，手工創建 PR」
現在：Agent 完成 → 自動 → PR 創建 + Issue 關閉 + Slack 通知
結果：零人工交接，完全自動化
```

---

### 🤝 5. 驗證（Sub-agents）

**是什麼**：「一個人做，另一個人檢查」的機制

```
生成 Agent（Haiku 模型，快）
  └─ 寫代碼 / 寫文檔 / 寫分析
  └─ 快速、成本低

    ↓ 把結果交給

驗證 Agent（Opus 模型，強）
  └─ 檢查邏輯 / 檢查安全 / 檢查風格
  └─ 準確、無漏洞

    ↓ 不通過就

修復迴圈
  └─ 生成 Agent 改進
  └─ 驗證 Agent 再檢查
  └─ 直到通過為止
```

**現實意義**：
```
之前：一個 Agent 又寫又檢查（容易「自我感覺良好」）
現在：兩個獨立的 Agent（一個不可能騙另一個）
結果：品質自動提升，錯誤大幅減少
```

## 第四層：核心指令對比

### /loop vs /goal

你需要一個**定時的檢查** ？ → 用 `/loop`

```
/loop "每小時檢查一次代碼質量"
  └─ 定時執行
  └─ 發現問題歸檔
  └─ 沒有問題靜默
  └─ 適合例行公事
```

你需要一個**確定的結果** ？ → 用 `/goal`

```
/goal "確保所有測試通過且無代碼警告"
  └─ 持續迭代
  └─ 不達目標不停止
  └─ 中途有錯自動修復
  └─ 適合複雜任務
```

### 選擇標準

| 場景 | 選擇 | 例子 |
|------|------|------|
| 日常監測 | `/loop` | 每天統計進度 |
| 定期檢查 | `/loop` | 每週掃描安全漏洞 |
| 質量保證 | `/goal` | 確保所有測試綠燈 |
| 問題修復 | `/goal` | 解決特定 Bug |
| 複雜任務 | `/goal` | 完成整個功能模塊 |

## 第五層：/loop 實踐指南

### 適合處理的例行公事

#### 信息收集類
```
✓ 自動分類 Issue
  每天早上 9 點收集新提交的需求
  自動按優先級分類
  結果進入「待處理」收件箱

✓ 統計 CI 失敗
  每小時檢查構建狀態
  收集失敗記錄
  按類型彙總報告
```

#### 進度追蹤類
```
✓ 生成日報
  每天下午 5 點運行
  統計今日完成的任務數
  列出明日優先級

✓ 代碼提交分析
  每週一運行
  分析過去一周的提交
  發現可能的問題
```

#### 預防性檢查類
```
✓ 安全掃描
  每天運行依賴檢查
  發現過時或有漏洞的包
  自動建議更新

✓ 質量監測
  每小時檢查代碼複雜度
  發現即將超標的文件
  提前預警
```

#### 記憶維護類
```
✓ 更新項目看板
  每天同步最新進度
  保持 Skills 庫新鮮
  整理過時文檔
```

### /loop 的黃金法則

```
規則 1：一次執行的時間 < 5 分鐘
  └─ 太慢了無法高頻運行

規則 2：結果要么有價值，要么靜默
  └─ 不要製造垃圾通知

規則 3：不依賴人工審核
  └─ 目的是解放人力，不是增加負擔

規則 4：結果清晰可追蹤
  └─ 每次執行都要留下日誌

規則 5：逐步遞進，不要一步到位
  └─ 先實現 80% 的功能
  └─ 再打磨剩餘 20%
```

## 第六層：工程師的新角色

### 工作重心的轉移

| 舊時代 | 新時代 |
|--------|--------|
| 寫提示詞 | 設計系統 |
| 手工執行 | 監督驗證 |
| 逐步調試 | 整體監測 |
| 處理細節 | 掌控全局 |

### 新的挑戰

#### 理解債（Comprehension Debt）

```
風險：系統運行太快，人類跟不上

症狀：
  ├─ 「我不知道系統怎麼做決策的」
  ├─ 「這個 Skill 是什麼時候加進去的」
  └─ 「為什麼這段代碼長這樣」

防護：
  ├─ 定期 Review 系統決策
  ├─ 維護詳細的變更日誌
  └─ 不要讓系統完全自主，要有人類的視野
```

#### 認知投降（Cognitive Surrender）

```
風險：過度相信系統，放棄人類的判斷

症狀：
  ├─ 「系統說沒問題就沒問題」
  ├─ 「不檢查代碼品質」
  └─ 「盲目信任自動化」

防護：
  ├─ 保持懷疑精神，定期人工審查
  ├─ 建立紅線，某些決策必須人工參與
  └─ 相信系統，但驗證結果
```

  └─ 精細調整：10 小時

Year 1+

## 第九層：常見陷阱

### ❌ 陷阱 1：過度自動化

```
症狀：「所有工作都交給 Agent，人類徹底休息」

後果：
  ├─ 無法理解系統決策
  ├─ 出現問題無法快速應對
  └─ 「認知投降」

正確做法：
  └─ 保留 20% 的人工檢查
  └─ 關鍵決策必須人類審批
  └─ 定期「解剖」系統邏輯
```

### ❌ 陷阱 2：Skills 庫過時

```
症狀：「老規則指導新任務」

後果：
  ├─ 系統優化效果遞減
  ├─ 決策質量下降
  └─ 最終比手工還差

正確做法：
  └─ 每月檢查一次 Skills
  └─ 移除過時的規則
  └─ 加入新發現的最佳實踐
```

### ❌ 陷阱 3：目標設定不明確

```
症狀：/goal 無限迴圈，永不停止

後果：
  ├─ 浪費資源
  ├─ 系統崩潰
  └─ 信任崩塌

正確做法：
  └─ 目標必須「可驗證」
  └─ 停止條件必須「明確」
  └─ 設置超時保護
```

## 第十層：總結

### 循環工程的本質

```
不是「自動化所有工作」
而是「設計一個能自我改進的系統」

不是「消除工程師」
而是「讓工程師從重複工作解放」

不是「100% 無人值守」
而是「90% 自動 + 10% 人工監督」
```

### 最終境界

```
你設計的系統：
  ├─ 自己提示自己（不需要你下命令）
  ├─ 自己檢查自己（不需要你驗證）
  ├─ 自己修正自己（不需要你調試）
  ├─ 自己改進自己（不需要你優化）
  └─ 但永遠接受你的監督和指引

你的工作變成了：
  ├─ 設計者（定義規則）
  ├─ 監督者（檢查結果）
  ├─ 改進者（迭代系統）
  └─ 信任管理者（平衡自動和人工）
```

### 開始的方式

```
Step 1：看著你現在的日常工作
Step 2：找一個「重複的、無創意的」任務
Step 3：用 /loop 把它自動化
Step 4：看著它運行，享受解放感

然後重複。

三個月後，你會驚訝於有多少時間被釋放。
一年後，你會問自己「為什麼沒有更早開始？」
```

## 附錄：快速參考

### 命令速查

```
每小時檢查進度？
  → /loop "檢查進度" --frequency=hourly

確保測試全過？
  → /goal "所有測試通過"

避免代碼衝突？
  → 使用 Worktrees 隔離

複用經驗？
  → 在 Skills 庫中記錄

質量有保障？
  → 配置 Sub-agents 驗證層

自動交付？
  → 配置 Connectors 連接系統
```

### 決策樹

```
我需要自動化一個工作

  ├─ 是定時執行的？
  │   ├─ YES → /loop
  │   └─ NO → 下一個問題
  │
  ├─ 需要確定的結果嗎？
  │   ├─ YES → /goal
  │   └─ NO → /loop
  │
  ├─ 涉及多個文件修改？
  │   ├─ YES → 使用 Worktrees
  │   └─ NO → 直接執行
  │
  ├─ 需要驗證品質？
  │   ├─ YES → 配置 Sub-agents
  │   └─ NO → 跳過驗證層
  │
  └─ 需要連接外部系統？
      ├─ YES → 配置 Connectors
      └─ NO → 完成配置
```
