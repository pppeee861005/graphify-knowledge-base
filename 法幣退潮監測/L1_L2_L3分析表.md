# 法幣退潮監測 — 四層架構分析表

**背景**：本表以「五信號驗證任務」(黃金遊戲攻略)的架構框架為基礎，針對「法幣退潮監測」項目進行調適。

**核心問題**：該項目應該用 L1、L1.5、L2 還是 L3？答案是：**L3（每日自動監測）+ L2（月度深度報告）的混合架構**。

### 層級選擇決策樹

| 層級 | 場景定位 | 計畫持有人 | 班組配置 | 適配本案 |

| **L1** | 快速回應 | Claude 逐回合決策 | 單個查詢 | 🟡 快速提問用 |

## 🔍 詳細方案對比

### L1：快速查詢型

#### 應用場景

用戶問：「Rocky，當前金銀比是多少？美元指數在多少？」

#### 執行流程

```
T0 你問「當前金銀比是多少？」
   ↓
T1 我（Claude）決定步驟1：查詢黃金價格
   ↓ 調用 Subagent 查詢黃金
T2 Subagent 返回：「黃金 $2050/oz」
   ↓ 我看著結果 → 決定步驟2：查詢白銀價格
   ↓ 調用 Subagent 查詢白銀
T3 Subagent 返回：「白銀 $24/oz」
   ↓ 我計算：2050/24 = 85.4
T4 我回答你：「當前金銀比是 85.4，環比上升 0.5」
T5 你問：「為什麼上升？」
   ↓ 我決定是否查詢更多背景信息
```

#### 班組配置

```
Subagent-1: 黃金/白銀/美元指數查詢
Subagent-2: 簡單計算（金銀比、脫鉤係數）
```

#### 決策方式

- Claude 逐步驟決策 → 等待 Subagent 回應 → 下一步決策
- **特點**：完全序列化，無並行

#### 成本評估

| 維度 | 評分 |
|------|------|
| Token 消耗 | ⭐⭐ 低 |
| 執行時間 | ⏱️ 快（秒級） |
| 人工干預 | 🤝 需要（用戶提問觸發） |
| 質量保障 | 🟡 中（單一查詢） |
| 複雜度控制 | ⭐⭐⭐⭐⭐ 最簡單 |

#### 適配本案的評分

```
整體評分：⭐⭐⭐⭐ (4/5) 【快速反應最優】

優點：
✅ 用戶提問時立即回應
✅ Token 消耗極低
✅ 無需預先設置複雜流程

缺點：
❌ 無法進行「定期自動監測」
❌ 無法深度分析跨月趨勢
❌ 依賴用戶主動提問

適合場景：用戶臨時提問「當前金銀比？」「美元指數在多少？」
不適合場景：自動化每日監測、月度深度分析
```

### L1.5：每日簡報型

#### 應用場景

系統每日早上 8:00 自動生成「五層信號簡報」（無深度分析），用戶瀏覽後自己綜合。

#### 執行流程

```
T0 定時任務觸發（每日 08:00）
   ↓
T1 啟動 3 個獨立 background sessions：
   ├─ Session-A: 數據查詢層
   ├─ Session-B: 數據時效性檢查
   └─ Session-C: 異常偵測層

T1-T10 三個 session 各自獨立運行
   • Session-A 執行：
     - 查詢美元指數 → DXY 2.8%
     - 查詢黃金價格 → $2050/oz
     - 查詢白銀價格 → $24/oz
     - 計算金銀比 → 85.4

   • Session-B 執行：
     - 驗證 DXY 數據（24小時內 ✓）
     - 驗證黃金數據（1小時內 ✓）
     - 驗證白銀數據（1小時內 ✓）

   • Session-C 執行：
     - DXY 上升 2.8%（環比）→ 正常
     - 金銀比 85.4（環比上升 0.5）→ 注意
     - 無異常警報

T11 三個 session 完成
   你看到三份獨立的報告

T12 你要自己綜合：
   「DXY 上升、金銀比也上升…這是什麼信號？」
   → 需要自己進行跨層分析
```

#### 班組配置

```
Session-A（獨立）：數據查詢層
  • 查詢黃金、白銀、美元指數
  • 計算金銀比
  • 不知道 Session-B 的發現

Session-B（獨立）：時效性檢查層
  • 驗證數據新鮮度
  • 標記過期數據
  • 不知道 Session-A 的詳細數據

Session-C（獨立）：異常偵測層
  • 檢測突變（>5%）
  • 不知道 Session-A 和 B 的發現
```

#### 決策方式

- 三個 session 各自運行（互不通訊）
- 你監看三份報告 → 自己綜合 → 做決策
- **特點**：並行但獨立，無協作

#### 成本評估

| 維度 | 評分 |
|------|------|
| Token 消耗 | ⭐⭐⭐ 中低 |
| 執行時間 | ⏱️ 快（並行）|
| 人工干預 | 🤝 中等（需綜合） |
| 質量保障 | 🟡 中（無 peer review） |
| 複雜度控制 | ⭐⭐⭐⭐ 容易 |

#### 適配本案的評分

```
整體評分：⭐⭐⭐ (3/5) 【每日監測的次優方案】

優點：
✅ 三個 session 並行，比 L1 快
✅ 可每日自動生成簡報
✅ Token 消耗相對低

缺點：
❌ Session-A、B、C 互不通訊
   → Session-B 無法告訴 Session-A「時效性有問題，需重查」
   → 必須你（人類）做為中介綜合意見
❌ 容易遺漏跨層關聯
   → 如果 A 查到「金銀比上升」，B 發現「數據舊」
   → 兩個信息無法自動關聯
❌ 無法進行「交叉驗證」
   → 三份報告各自獨立，無互相檢查

可能發生的問題：
  • 你同時看到「DXY 上升」和「金銀比上升」
  • 但無法確定「這是脫鉤信號」還是「數據延遲」
  • 需要你手動對比三份報告

適合場景：多項目並行監控、獨立進度監看
不適合場景：需要深度分析、需要交叉驗證（本案月度報告需求）
```

### L2：月度深度報告型 — 【本案月度現用】

#### 應用場景

每月月末（28-31日）執行深度分析：收集 30 天的數據 → 5 個班組並行 → 主控統一交叉驗證 → 生成月度報告。

#### 執行流程

```
T0 月末任務起動（2026-06-28）
   工頭（Claude Lead Agent）設定大方向：
   「五層信號三步驗證：源頭→現實→時效」

T1 主控並行派遣班組（中心輻射，默認模式）
   ├─ 班組1（數據源審查）：檢驗 30 天 API 數據可信度
   ├─ 班組2（現實核實）：查詢當前實時數據
   ├─ 班組3（時效性檢查）：驗證整月數據新鮮度
   ├─ 班組4（信號關聯分析）：對標五層信號狀態
   └─ 班組5（趨勢預警）：識別未來 30-60 天風險

T3 班組1 回報主控（數據源審查）
   班組1 → 回報主控：
   「第一層信號（DXY vs Gold 相關係數）本月波動 0.15 ~ 0.22」
   「第二層信號（金銀比）本月平均 84.2，環比下降 0.8」
   「第三層信號（COMEX 庫存）本月累計下降 2.3%」
   「→ 趨勢判斷：所有指標同向」

   → 主控把此發現轉派給班組4 進行信號關聯分析

T5 班組2 回報主控（現實核實）
   班組2 → 回報主控：
   「最新美元指數：2.95（當日）」
   「最新黃金價格：$2048/oz（當日）」
   「最新白銀價格：$23.8/oz（當日）」
   「金銀比當日值：86.1」
   → 主控檢查與班組1 的基線對比

T7 班組3 回報主控（時效性檢查）
   班組3 → 回報主控：
   「所有數據在 24 小時內，新鮮度 ✓」
   「COMEX 庫存最後更新於昨日 18:00 ✓」
   「無過期數據」
   → 主控確認整月數據質量無問題

T9 班組4 回報主控（信號關聯分析）
   班組4 → 回報主控（進行了跨層對標）：
   「第一層（價格脫鉤）：DXY 上升 + Gold 上升（同向比例 28%）」
   「第二層（金銀比）：持續下降趨勢，斜率 -0.6」
   「第三層（實物撕裂）：溢價擴大至 8.2%，COMEX 庫存月下降 2.3%」
   「第四五層：基本為零，無政策信號」

   「→ 整體評估：假說強化指標」

T11 班組5 回報主控（趨勢預警）
   班組5 → 回報主控：
   「下月監測重點：」
   「1. 金銀比若跌破 80，進入新區間」
   「2. 實物溢價若突破 10%，信號明顯強化」
   「3. 無新增交割困難事件，但需持續監測」
   「→ 風險預警：若金銀比反彈回 85，信號減弱」

T13 工頭（主控）開始彙整
   主控統一分析：
   ✅ 班組1 的基線數據
   ✅ 班組2 的實時快照
   ✅ 班組3 的時效性確認
   ✅ 班組4 的跨層對標（五層信號狀態矩陣）
   ✅ 班組5 的未來風險預警

   主控做「交叉驗證」：
   • 班組1 說「金銀比下降 0.8」
   • 班組2 說「當日金銀比 86.1」
   • 主控檢查：環比是否正確？（86.1 vs 84.2 = 上升，非下降）
   • 主控發現矛盾 → 要求班組1 澄清

   班組1 澄清：
   「我說的 84.2 是月平均值，班組2 說的 86.1 是月末單日值」
   「月末跳升是因為白銀相對回升，但月平均趨勢仍是下降」

   → 主控統一解釋並記入報告

T15 主控生成最終報告 + 決策建議
   報告包括：
   • 五層信號月度狀態矩陣（清晰可視）
   • 班組建議匯總
   • 證偽條件檢查
   • 下月監測重點
   • 總體評估：「假說強化 / 穩定 / 減弱 / 驗證失敗」

T16 呈現給你（最高決策人）
   你看到完整分析 + 主控建議 → 審視 → 做決策

T17 你決策：
   ✅ 下月繼續監測
   ✅ 增加「實物溢價」監測頻率（改為周度）
   ✅ 準備撰寫 Substack 月度報告
   ✅ 更新「證偽條件檢查」文件

T18 工頭（主控）協調執行
   • 班組5 負責「下月監測框架調整」
   • 班組1 準備「實物溢價周度監測模板」
```

#### 班組配置

```
主控：Claude Lead Agent（唯一通訊中樞）
  • 決定大方向：五層信號三步驗證框架
  • 顯式派遣每個班組、收齊回報、交叉驗證
  • 仲裁班組結論衝突
  • 統一彙整成「一份已對齊的報告」
  • 生成決策建議清單

班組1（數據源審查）— Subagent: 可信度評估
  • 檢驗 30 天 API 數據可信度
  • 識別數據矛盾（源頭驗證）
  • 標記過時或異常數據
  • 回報主控：可信度評估報告 + 基線數據矩陣

班組2（現實核實）— Subagent: 實時查詢
  • 執行實時 API 查詢
  • 收集五層信號的當前數據（月末快照）
  • 驗證數據時效性（需 24 小時內）
  • 回報主控：當日數據快照

班組3（時效性檢查）— Subagent: 時效驗證
  • 驗證整月數據新鮮度
  • 標記過期或延遲數據
  • 確認數據採集時間戳
  • 回報主控：時效性驗證報告

班組4（信號關聯分析）— Subagent: 五層對標
  • 對標五層信號的月度狀態
  • 識別跨層信號的相關性
  • 檢查證偽條件是否觸發
  • 生成信號狀態矩陣（可視化）
  • 回報主控：信號關聯分析 + 矩陣

班組5（趨勢預警）— Subagent: 風險識別
  • 識別未來 30-60 天的風險信號
  • 提出下月監測框架調整
  • 預測關鍵指標突破點
  • 回報主控：風險預警報告 + 建議清單

⚠️ 注意：班組之間無直接通訊，所有協調經過主控轉派
   班組 1 → 回報主控 → 主控轉派給班組 4
   （非班組 1 直接喊班組 4）
```

#### 決策方式

- **主控決定大方向**：「五層信號三步驗證」
- **主控統一編排**：班組各自回報，主控收齊後轉派/仲裁（中心輻射）
- **主控仲裁分歧**：班組結論不一致時，主控比對後裁決
- **用戶做最終決策**：審視主控彙整的報告後，批准或修改方案
- **特點**：中心輻射式 — 主控是唯一通訊中樞

```
→ L2 是月度報告的最優選擇
```

### L3：每日監測自動化型 — 【本案每日現用】

#### 應用場景

每日早上 8:00 自動觸發「FiatTideMonitoring」Workflow：自動收集五層信號 → 時效性檢查 → 異常預警 → 生成日誌。

#### 執行流程（純 JavaScript + 命令式原語）

```javascript
// 法幣退潮每日監測流程
export const meta = {
  name: 'FiatTideMonitoring',
  description: '每日 08:00 收集五層信號數據 → 時效性檢查 → 異常預警',
  phases: [{ title: 'Collect' }, { title: 'Alert' }],
}

phase('Collect')
// pipeline：每層信號獨立流過 查詢→驗證→存儲
const SIGNALS = [
  { layer: 1, name: '美元指數', api: 'alphavantage' },
  { layer: 1, name: '黃金價格', api: 'metals-api' },
  { layer: 1, name: '脫鉤係數', api: 'calculated', depends: ['DXY', 'Gold'] },
  { layer: 2, name: '金銀比', api: 'calculated', depends: ['Gold', 'Silver'] },
  { layer: 3, name: 'COMEX庫存', api: 'comex-official' },
  { layer: 3, name: '實物溢價', api: 'dealer-survey' },
  { layer: 4, name: '政策信號', api: 'news-search' },
]

const results = await pipeline(SIGNALS,
  // Stage 1: 查詢
  (sig) => agent(
    `查詢 ${sig.name} 實時數據`,
    { schema: DATA_SCHEMA, model: 'haiku' }
  ),
  // Stage 2: 驗證時效性
  (data) => agent(
    `驗證時效性（需24小時內）：${data}`,
    { schema: TIME_SCHEMA, model: 'haiku' }
  ),
  // Stage 3: 存儲
  (verified) => agent(
    `存儲至日誌 & 檢查異常：${verified}`,
    { schema: STORE_SCHEMA, model: 'haiku' }
  )
)

phase('Alert')
// 異常檢測：價格突變、庫存驟降、政策變化
for (const r of results.filter(Boolean)) {
  // 只對高風險指標進行深度分析
  if (r.layer >= 2) {
    const alert = await agent(
      `檢測異常（突破閾值 > 5% 環比變化）：${r}`,
      { schema: ALERT_SCHEMA, model: 'sonnet' }
    )
    if (alert.isAnomaly) {
      log(`⚠️ 異常預警 [${r.layer}層] → ${r.name}：${alert.description}`)
      // 觸發通知（用戶郵件/Slack）
      notify('user', alert.message)
    }
  }
}

return { results, alerts: [...] }
```

## 🏁 本案的最終架構決策

### 為什麼選 L3（每日）+ L2（月度）？

| 維度 | L1.5 單獨 | L3 + L2 混合 |
|------|---------|-----------|
| 數據積累 | 無（每天獨立報告） | ✅ 30 天累積 |
| 趨勢識別 | 困難（無歷史對比） | ✅ 月度趨勢清晰 |
| 成本分配 | 平均（每天 15k） | ✅ 尖峰設計（日低+月高） |
| 人工負擔 | 高（每天綜合報告） | ✅ 低（日掃一眼+月審視） |
| 交叉驗證 | 無 | ✅ L2 全面交叉驗證 |
| 決策質量 | 中等（自己綜合） | ✅ 高（主控統一彙整） |

### 成本優化策略

```
L3 每日監測：
  • 查詢層：Haiku（最便宜，適合簡單 API 調用）
  • 驗證層：Haiku（簡單時效檢查）
  • 異常檢測層：Sonnet（複雜模式識別時用）

L2 月度報告：
  • 班組1-3（資料收集）：Sonnet（需要邏輯推理）
  • 班組4（信號對標）：Opus（複雜跨層分析）
  • 班組5（趨勢預警）：Sonnet（預測性分析）
  • 主控（交叉驗證）：Opus（高級仲裁）

預期月度成本：~385k tokens（可接受範圍）
```
