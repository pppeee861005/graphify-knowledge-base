# A／B 方法之分析

## 一、核心假設

本文件將兩種工作方式定義如下：

- **A 方法**：探索、一次性任務與處理例外
- **B 方法**：穩定、可重複、可擴充的內容發布架構

兩者不是互相排斥的方案，而是內容發布系統在不同成熟階段所需要的兩種能力。

## 二、A 方法：探索與例外處理

A 方法的流程通常是：

```text
Codex 讀取畫面
  ↓
理解目前狀態
  ↓
判斷下一步操作
  ↓
透過瀏覽器與 Playwright 執行
  ↓
重新觀察結果
```

### A 方法的優點

- 能處理尚未被規格化的新流程
- 能應對 Substack 介面改版或不預期狀態
- 適合第一次探索某個平台
- 適合處理登入、權限、CAPTCHA、草稿重複等例外
- 不需要先投入時間開發完整工具

### A 方法的限制

- 每次都需要重新理解頁面
- 操作結果較依賴即時判斷
- 容易因 UI 小幅改動而失敗
- 不容易批次執行大量文章
- 難以建立一致的測試與審計紀錄

A 方法的本質是「智慧型人工操作」。它的強項不是速度，而是適應未知情況。

## 三、B 方法：固定化發布管線

B 方法將瀏覽器操作封裝成固定工具，例如 `substack-cli`：

```text
文章 Markdown
  ↓
Content Pipeline
  ↓
substack-cli
  ↓
Playwright
  ↓
Substack
```

可能的介面如下：

```bash
substack draft article.md
substack verify article.md
substack publish article.md --confirm
substack schedule article.md --at "2026-08-11 08:00" --confirm
```

### B 方法的優點

- 流程一致且容易重複
- 適合批次處理多篇文章
- 可以集中處理 Markdown、圖片、標題與摘要
- 能加入格式驗證、重複偵測與發布紀錄
- 任何 Agent 都能使用同一套工具
- 未來可擴充至 WordPress、Medium、LinkedIn 等渠道

### B 方法的限制

- 需要先投入設計與開發成本
- Substack UI 改版時，固定流程可能失效
- 不能假設所有文章格式都相同
- 例外狀況仍需要回到 A 方法處理
- `publish`、`schedule` 與寄送 Email 具有高風險，必須設計明確授權

B 方法的本質是「可重複的內容發布基礎設施」。它的強項不是理解未知，而是可靠地執行已知流程。

## 四、A 與 B 的比較

| 面向 | A 方法 | B 方法 |
|---|---|---|
| 主要用途 | 探索與例外處理 | 穩定與批次發布 |
| 操作方式 | 即時觀察與判斷 | 固定流程與工具呼叫 |
| 彈性 | 高 | 中等 |
| 重複性 | 中低 | 高 |
| 開發成本 | 低 | 中高 |
| 對未知狀況的適應力 | 高 | 較低 |
| 批次執行能力 | 低 | 高 |
| 可測試性 | 較低 | 高 |
| 多平台擴充 | 需要重新探索 | 可共用 Publisher 介面 |
| 適合階段 | 專案早期、特殊任務 | 流程成熟後 |

## 五、最佳解不是 A 或 B，而是 A／B 混合架構

成熟的系統應該採用以下流程：

```text
                    ┌→ 正常流程 → B：固定 Publisher
Codex 判斷任務 ────┤
                    └→ 未知或失敗 → A：探索與例外處理
                                      ↓
                              更新 B 的規則
```

也就是：

1. 先由 Codex 判斷任務是否符合已知流程。
2. 符合時，直接呼叫 B 方法執行。
3. 發生未知頁面、登入問題、格式問題或操作失敗時，切換到 A 方法。
4. 將成功處理過的例外整理成新的規則、測試或恢復流程。
5. 讓 B 方法逐漸吸收 A 方法探索出的經驗。

這形成一個持續改進循環：

```text
探索 → 解決例外 → 規格化 → 自動化 → 發現新例外 → 再探索
```

## 六、推薦的三層系統

### 第一層：AI Writer

負責：

- 主題與角度
- 文章內容
- 標題與副標題
- 發布意圖
- 是否需要人工確認

### 第二層：Content Pipeline

負責：

- Markdown 解析
- Frontmatter 管理
- 標題與摘要抽取
- HTML 轉換
- 圖片與附件處理
- SEO、標籤與系列資訊
- 文章版本與發布狀態

### 第三層：Publisher

負責：

- Substack 草稿建立
- 正文貼入
- 圖片上傳
- 保存狀態確認
- 草稿網址記錄
- 發布、排程與寄信控制

A 方法主要存在於 Publisher 的「探索與恢復層」；B 方法則是 Publisher 的「正常執行層」。

## 七、授權與安全設計

建議把動作分成三個風險等級：

### 低風險：可自動執行

```bash
substack draft article.md
substack verify article.md
```

這些動作只建立或檢查草稿，不會對訂閱者造成外部影響。

### 中風險：需要檢查重複與內容

```bash
substack update draft-id article.md
```

更新既有草稿前，必須確認草稿 ID、標題與使用者授權，避免覆蓋錯誤文章。

### 高風險：必須明確確認

```bash
substack publish article.md --confirm
substack schedule article.md --at "2026-08-11 08:00" --confirm
substack publish article.md --email --confirm
```

發布、排程與寄送通知不應由 Agent 默認推斷。尤其 Email 發送，應該是獨立且清楚的授權選項。

## 八、對目前工作方式的結論

目前使用 A 方法完成 Substack 任務，適合以下原因：

- 需要先確認出版物與登入狀態
- 需要辨識第 1 篇已發布、第 2～8 篇尚未建立的差異
- 需要處理瀏覽器分頁、瀏覽器類型與頁面狀態
- 需要避免重複建立或誤發布

但當這類任務變成固定工作，例如每週發布多篇文章，便應將已驗證的流程轉化為 B 方法：

```text
Markdown → 解析 → 建立草稿 → 驗證 → 回報網址
```

最終形成 A／B 方法：

> A 負責理解未知，B 負責執行已知。  
> A 處理例外，B 累積可靠性。  
> A 發現規則，B 將規則變成工具。

## 九、最終建議

建議先建立最小可用版本，而不是一次開發完整多平台系統：

1. 先建立 `substack draft article.md`。
2. 加入標題、正文、圖片與 Saved 狀態驗證。
3. 加入草稿網址與發布紀錄。
4. 加入重複草稿偵測。
5. 再加入 `verify`、`publish` 與 `schedule`。
6. 最後才抽象化成多平台 Publisher。

這樣可以保留 A 方法的靈活性，同時逐步獲得 B 方法的穩定性，讓內容系統從一次性操作，演化成真正可持續運作的發布基礎設施。
