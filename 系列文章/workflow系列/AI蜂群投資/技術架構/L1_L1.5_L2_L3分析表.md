# 五信號驗證任務：四層架構分析表

**任務背景**：美伊協議五信號實時驗證（2026-06-19）
**核心需求**：三步驗證 + 版本管理 + 後續監測規劃
**實際執行**：L2 Agent Teams（施工隊協作）

>
> 本表**結論正確**（多信號交叉驗證該用 L2），但原 v1.0 的**機制描述大幅失真**，已校準：
>
> | 項目 | 原 v1.0（錯） | v2.0（真實） |
> |------|------------|------------|
> | **L2 運作** | 「真正的 peer-to-peer、班組自主協商、班組1→直接告訴班組4」 | **三模式**：①一次性派遣(中心輻射,默認/本案) ②常駐隊友(真點對點,需 `SendMessage`+具名顯式配置) ③Workflow(隔離回傳)。**班組默認不互通，由主控收齊後轉派** |
> | **L2 勝 L1.5 的真因** | 「班組能互相喊話」 | **「主控統一編排交叉驗證，產出單一調和結論」**——你拿到一份已對齊的報告，而非 3 份要自己綜合 |
> | **L3 語言/API** | TypeScript + 宣告式 config（`{parallel,qualityAssurance,decisionRules}`） | **純 JavaScript** + 命令式原語 `agent()/parallel()/pipeline()`；QA/決策用 for/if 控制流 |
> | **L3 併發** | 50+25+10+5 agents 同時 | **同時併發約 16**（min(16,核心-2)），其餘排隊；總量上限 1000 |
> | **Token** | L1~500 / L2~2500 / L3~50k | **嚴重低估約 100 倍**：實測單份 5 班組＝**235,019 tokens**；L2 級任務屬十萬級，L3 批次百萬級 |
>
> **保留**：本案「該用 L2」的判斷正確（質量+交叉驗證需求）；校準的是「L2/L3 是什麼」與「為何勝 L1.5」。

### L1：Subagents（廚房型）

#### 執行流程

```
時間線：
T0 你說「幫我驗證五信號」
   ↓
T1 我（Claude）收到任務 → 決定步驟1：查詢美債
   ↓ 調用 Subagent-1 查詢美債
T2 Subagent-1 返回：「美債 4.46%」
   ↓ 我看著結果 → 決定步驟2：查詢油價
   ↓ 調用 Subagent-2 查詢油價
T3 Subagent-2 返回：「油價 $75」
   ↓ 我看著兩個結果 → 決定步驟3：查詢 VIX
   ...
T6 我收集完所有數據 → 決定步驟7：生成報告
   ↓ 調用 Subagent-6 編寫報告
T7 Subagent-6 返回報告
   ↓
T8 我把報告給你看 → 等待你的反饋
   ↓
T9 你說「要廢棄舊版本嗎？」
   ↓
T10 我決定是否調用 Subagent 去編輯舊文件
```

Subagent-2: 可信度評估
Subagent-3: 時效性檢查
Subagent-4: 版本管理
Subagent-5: 報告生成
```

- Claude 逐步驟決策 → 等待 Subagent 回應 → 下一步決策
- **特點**：完全序列化，無並行

### L1.5：Agent View（監控台型）

#### 執行流程

```
T0 你起動 3 個 background agent sessions
   ├─ Session-A: 負責「數據查詢」
   ├─ Session-B: 負責「可信度評估」
   └─ Session-C: 負責「版本管理」

T1-T15 三個 session 各自獨立運行
   • Session-A 執行：調用網路查詢 → 返回美債/油價/VIX/匯率
   • Session-B 執行：分析數據可信度 → 返回評估報告
   • Session-C 執行：準備版本標記 → 返回編輯方案

T16 你監看三個 session 的進度條
   • A：✅ 完成數據查詢
   • B：⏳ 正在分析（70%）
   • C：⏳ 準備編輯（40%）

T20 你可以「切進」Session-B，直接和我（B 中的 Claude）對話
   你：「為什麼認為早期版本是情景推演？」
   我（B）：「因為數據不匹配...」
   你：「同意，繼續」

T25 全部 session 完成
   你看到三份報告

T26 你做決策：「廢棄舊版本」
   ↓ 但無法讓 A、B、C 互相討論
   ↓ 你要自己綜合三份報告
```

#### 班組配置

```
Session-A（獨立）：數據查詢層
  • 執行網路搜索
  • 返回原始數據

Session-B（獨立）：可信度評估層
  • 自己分析（不知道 A 的發現）
  • 返回評估報告

Session-C（獨立）：版本管理層
  • 自己準備編輯方案
  • 不知道 A 和 B 的矛盾
```

#### 決策方式

- 三個 session 各自運行（互不通訊）
- 你監看進度 → 可隨時「attach」進任一 session 對話
- **特點**：並行但獨立，無協作

#### 成本評估

| 維度 | 評分 |
|------|------|
| Token 消耗 | ⭐⭐⭐ 中低 |
| 執行時間 | ⏱️ 快（並行）|
| 人工干預 | 🤝 中等（需監看） |
| 質量保障 | 🟡 中（無 peer review） |
| 複雜度控制 | ⭐⭐⭐⭐ 容易 |

#### 適配本案的評分

```
整體評分：⭐⭐⭐ (3/5)

優點：
✅ 三個 session 並行，比 L1 快
✅ 你可以隨時切進任一 session 監看
✅ Token 消耗相對低

缺點：
❌ Session-A、B、C 互不通訊
   → Session-B 無法直接告訴 Session-A：「你查的數據有問題」
   → 必須你（人類）做為中介綜合意見
❌ 容易遺漏矛盾
   → 如果 B 發現「A 的數據過時」，B 只能「報告給你」
   → 你要自己決定是否讓 A 重查

可能發生的問題：
  場景1：你沒看 B 的報告就看了 C 的編輯方案
         → 遺漏了 A、B 的矛盾
  場景2：B 發現 A 的數據有問題，但 B 沒有「強制 A 重查」的權力
         → 必須等你介入

適合場景：多項目並行、獨立進度監看（寫 5 個系列文章）
不適合場景：複雜協作、需要互查（本案）
```

### L2：Agent Teams（施工隊協作）— 【本案現用】

#### 執行流程

```
T0 任務起動
   工頭（Claude）設定大方向：
   「三步驗證：源頭 → 現實 → 時效」

T1 主控（中樞）並行派遣班組（中心輻射，默認模式①）
   ├─ 班組1（數據源審查）：檢查早期版本可信度 → 回報主控
   ├─ 班組2（現實核實）：查詢實時網路數據 → 回報主控
   ├─ 班組3（時效性檢查）：時效驗證框架 → 回報主控
   ├─ 班組4（口徑協調）：對標早期vs實時 → 回報主控
   └─ 班組5（風險預警）：長期監測框架 → 回報主控

T3（班組1 回報主控）
   班組1 → 回報主控：
   「早期版本美債 4.9%，現實 4.46%，差異巨大」
   → 主控把此矛盾餵給班組4，請它對標時強調
   （不是班組1「直接喊」班組4；經主控轉派）

T5（班組2 回報主控）
   班組2 → 回報主控：「五個最新數據，都是 24小時內」
   → 主控轉給班組3 標註時效性

T7（版本廢棄判斷 — 主控仲裁，非班組互談）
   主控把班組1（矛盾）+ 班組4（對標）結果一起評估：
   「要不要廢棄早期版本？怎麼標記？」
   → 由主控統一裁決，非班組私下協商

T10（風險評估）
   主控把班組4 的「60天三大風險」轉給班組5
   → 班組5 回報主控：「我會設計這三大風險的監測機制」

T13（主控收齊全部 → 彙整）
   主控（我）開始彙整：
   • 檢查五個班組有沒有遺漏
   • 確認版本管理方案一致
   • 確認後續監測框架清晰

T15（工頭生成最終報告 + 決策建議）
   報告包括：
   • 三步驗證的完整分析
   • 四層對比（本表）
   • 版本管理方案
   • 決策建議清單

T16 呈現給你（最高決策人）
   你看到完整分析 → 審視班組的建議 → 做決策

T17 你決策：
   ✅ 廢棄早期版本
   ✅ 標記為「已棄用」
   ✅ 選擇「動態監測頻率」
   ✅ 要求「60天計劃」

T18 工頭（我）協調執行
   • 班組4 負責版本標記編輯
   • 班組5 負責監測計劃設計
   • 班組1-3 待命檢查
```

#### 班組配置

```
主控：Claude Lead Agent（唯一通訊中樞）
  • 決定大方向：三步驗證框架
  • 顯式派遣每個班組、收齊回報、決定下一棒
  • 仲裁班組結論衝突（如是否廢棄早期版本）
  • 生成最終報告 + 決策建議

班組1（數據源審查）
  • 檢驗早期/實時版本可信度、識別矛盾 →【回報主控】

班組2（現實核實）
  • 執行實時網路查詢 →【回報主控】

班組3（時效性檢查）
  • 驗證所有數據新鮮度 →【回報主控】

班組4（口徑協調）
  • 對標早期vs實時、提版本標記方案 →【回報主控】

班組5（風險預警）
  • 識別 60天內風險、設計監測機制 →【回報主控】

⚠️ 注意：本案所有「向班組X」其實都是「回報主控，由主控轉派」（模式①）。
   班組之間的「協商」實為主控收齊後的統一仲裁。
   若要班組邊跑邊直接互通，需開模式②（background+具名+SendMessage）。

#### 決策方式

- **主控決定大方向**：「三步驗證」
- **主控統一編排**：班組各自回報，主控收齊後轉派/仲裁（非班組私下直通）
- **主控仲裁分歧**：班組結論不一致時，主控比對後裁決
- **用戶做最終決策**：審視主控彙整的報告後，批准或修改方案
- **特點**：中心輻射式（模式①）—— 主控是唯一通訊中樞；點對點需顯式開模式②

### L3：Dynamic Workflows（工廠自動化型）

#### 執行流程

⚠️ 校準：舊版這段是「TypeScript + 宣告式 config」，全錯。真實 Workflow 是純 JavaScript + 命令式原語。

```javascript
// 五信號驗證自動化流程（真實 Workflow 寫法，純 JS）
export const meta = {
  name: 'VerifyFiveSignals',
  description: '五信號實時查詢 → 可信度 → 版本對標',
  phases: [{ title: 'Verify' }, { title: 'QA' }],
}

phase('Verify')
// pipeline：每個信號獨立流過 查詢→可信度→對標，無 barrier
const SIGNALS = ['美債', '油價', 'VIX', '匯率', '黃金']
const results = await pipeline(SIGNALS,
  (sig) => agent(`查詢 ${sig} 實時數據`, { schema: DATA_SCHEMA, model: 'haiku' }),
  (data) => agent(`評估可信度（需3個獨立來源）：${data}`, { schema: CRED_SCHEMA, model: 'sonnet' }),
  (cred) => agent(`對比早期vs實時、標記矛盾：${cred}`, { schema: CMP_SCHEMA, model: 'opus' })
)

phase('QA')
// 對抗性審查與決策規則：用一般 for/if 控制流，不是宣告式鍵
for (const r of results.filter(Boolean)) {
  const votes = await parallel([
    () => agent(`紅隊：找此判斷的邏輯漏洞：${r}`, { schema: VERDICT_SCHEMA }),
    () => agent(`紅隊：找此判斷的數據漏洞：${r}`, { schema: VERDICT_SCHEMA }),
  ])
  if (votes.filter(v => v.refuted).length >= 1) log(`衝突 → arbitration：${r.signal}`)
  if (r.contradiction) log(`發現早期矛盾 → 標記棄用 + 備份：${r.signal}`)  // decisionRules = if
}
return { results }
```

**真實併發**：即使丟 5 信號 × 3 stage，**同時最多約 16 個 agent**跑，其餘排隊（非「50+25+10 同時」）。
**後續監測**：每日自動報告用 `CronCreate` 排程觸發此 workflow，非「100+ agents 常駐」。

#### 班組配置

```
⚠️ 校準：真實同時併發約 16，下列是「累計派遣量」（排隊執行），非「同時跑」。
   且五信號任務根本不需 50 份冗餘 —— scale down 到每信號幾個 agent 即可。

每信號一條 pipeline（查詢→可信度→對標）：
  ├─ 美債：3 stage agents
  ├─ 油價：3 stage agents
  ├─ VIX：3 stage agents
  ├─ 匯率：3 stage agents
  └─ 黃金：3 stage agents
  （5 信號 × 3 = 15 個，自然落在 ~16 併發內，幾乎一波跑完）

QA 對抗審查：每個高風險判斷派 2 個紅隊 agent（for 迴圈，邊跑邊驗）

決策與彙整：用腳本 if/log 表達，不需專門的「decision agent」
```

#### 決策方式

- **完全自動化**：計畫寫在 script 裡
- **自動決策**：觸發條件 → 自動執行（不等人類）
- **人類審批點**：只有最後一個（看完整報告 + 確認）
- **特點**：零中間人工，最後才需要人類

#### 成本評估

| 維度 | 評分 |
|------|------|
| Token 消耗 | ⭐ 最高（超過 10 萬 token） |
| 執行時間 | ⏱️ 快（全並行） |
| 人工干預 | 🤝 無（只需最後審批） |
| 質量保障 | ⭐⭐⭐⭐⭐ 最高（對抗審查） |
| 複雜度控制 | ⭐⭐ 低（計畫寫死） |

#### 適配本案的評分

```
整體評分：⭐⭐⭐ (3/5) 【一次性驗證不需，監測自動化可用】

✅ 事實校準（L3 不是只配做大工廠）：
   → L3 可 scale down，五信號跑 15 個 agent 的小 workflow 完全合理
   → 純 JavaScript + agent()/parallel()/pipeline()，同時併發約 16

❌ 但「一次性驗證」確實不必用 L3（這個結論成立）：
   → 本案是「快速一次性驗證 + 邊做邊調整」
   → 寫腳本的前置成本 > 直接用 L2 手動編排的收益
   → 確定性腳本適合「重複跑同一流程」，一次性任務用 L2 即可

✅ 但「後續監測」很適合 L3 小 workflow：
   → 每日自動驗證五信號 = 固定流水，正是 pipeline 的用例
   → 配 CronCreate 排程，每日自動跑

❌ Token 成本（修正舊估）：
   → 舊版「L2~2000、L3~50000」嚴重低估
   → 實測單份 5 班組就 235k；L3 批次屬十萬～百萬級
   → 但這不影響「一次性驗證用 L2」的結論

結論（校準後）：
一次性驗證用 L2（手動編排，快）；後續每日監測用 L3 小 workflow（非大工廠）。
工具沒有過度設計問題，是「一次性任務」本就不必寫確定性腳本。
```

## 💡 本案的關鍵決策

### 為什麼選 L2 而不是 L1.5？

```
L1.5 假設：
  Session-A：查詢數據
  Session-B：評估可信度
  Session-C：版本管理

  你看到三個 session 的進度條
  → 但 B 無法直接告訴 A「你的數據有問題」
  → 必須你作為中介

結果：
  ❌ B 發現「美債 4.9% 與現實 4.46% 差異巨大」
  ❌ B 無法直接告訴 A「去重新查詢」
  ❌ 你要自己綜合三份報告，做出「廢棄舊版本」決策

L2 實際（中心輻射，非班組互談）：
  主控派 5 班組各自回報 → 主控收齊後交叉驗證 + 仲裁
  ✅ 班組1 發現矛盾 → 回報主控
  ✅ 主控把矛盾餵給班組4 對標、自己裁決「要不要廢棄」
  ✅ 主控彙整成「一份已對齊的統一報告」呈現給你
  ✅ 你只需「批准」，不需要「綜合」3 份散報告

結論：
L2 勝 L1.5 的真因 = 「主控統一交叉驗證+彙整」，不是「班組互相喊話」。
→ L1.5：3 個獨立 session，你自己綜合；L2：主控替你綜合成單一結論。
→ 質量更高，用戶決策更簡單。
```

### L2 的 Token 代價值不值得？

```
成本對比（實測校準，非舊版的千級）：
  L1.5：數萬 token（3 個獨立 session）
  L2：  ~235k token（5 班組 + 交叉驗證，實測錨點）
  差價：L2 貴一個數量級——這是「交叉驗證冗餘」的代價

質量差異：
  L1.5：
    • 需要你自己綜合三份報告
    • 容易遺漏 session 間的矛盾
    • 決策時間：10分鐘

  L2：
    • 主控已交叉驗證+彙整，直接呈現單一方案
    • 遺漏率最低
    • 決策時間：2分鐘

結論：
  L2 貴一個數量級，但換來「決策時間快 5 倍」+「主控替你交叉驗證」
  → 高風險任務（金融/地緣政治）值得；但要知道這是十萬級 token，非千級
  → 若預算敏感，可混用模型（查詢用 Haiku、仲裁用 Opus）壓成本
```
