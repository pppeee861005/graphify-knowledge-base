# 📝 文章中的術語使用策略

> **這份指南決定了整個系列文章中「蜂群 Agent」「DW」「Ultracode」的正確使用方式，確保品牌一致性和讀者理解。**

---

## 🎯 核心原則

```
三個概念的定位階層：

蜂群 Agent（品牌層 - 最突出）
    ↑ 專有 IP

DW Framework（理念層 - 次突出）
    ↑ 通用框架，未來趨勢

Ultracode（技術層 - 最少提及）
    ↑ 實現細節，第三方技術棧
```

**使用黃金比例**：
- **蜂群 Agent**：70%（主題）
- **DW 框架**：25%（原理）
- **Ultracode**：5%（技術驗證）

---

## 📊 三個概念詳細分析

### 1️⃣ 蜂群 Agent（專有品牌）

**定義**：
我們基於 DW 框架開發的原創應用系列，包括蜂群覺醒、三維獵殺、自動校準等具體投資決策 Agent。

**何時使用**：
- ✅ 介紹我們**原創的應用案例**
- ✅ 強調我們的**獨特視角**
- ✅ 建立**讀者的品牌認知**
- ✅ 作為系列文章的**主角**

**使用示例**：
```markdown
「我們的蜂群投資 Agent 能同時監控 5000 隻股票，
  在 3 秒內完成多層決策流程...」

「蜂群系列的第一篇介紹的是『蜂群覺醒』——
  一個基於 DW 框架的投資監控 Agent...」

「蜂群不是一個工具，而是一種新的決策方式」
```

**品牌優勢**：
- 🎯 容易記住，便於傳播
- 🎨 有視覺想像空間（群體、協作）
- 💪 建立差異化認知
- 📈 可擴展（蜂群 HR Agent、蜂群內容 Agent...）

**禁止**：
- ❌ 不要說「DW 的蜂群實現」（應該說「蜂群基於 DW」）
- ❌ 不要把蜂群當成技術名詞
- ❌ 不要淡化蜂群的品牌身份

---

### 2️⃣ DW (Dynamic Workflow)（通用框架）

**定義**：
一套通用的決策框架理念，強調「計劃優先、Human in the Loop、思想進程、動態穩定」。

**何時使用**：
- ✅ 解釋**蜂群背後的系統思想**
- ✅ 涉及**通用決策框架**時
- ✅ 面對**多領域讀者**時（HR、採購、策略等）
- ✅ 說明**為什麼蜂群這樣設計**
- ✅ 強調**可擴展性和通用性**

**使用示例**：
```markdown
「蜂群 Agent 的底層是 DW（Dynamic Workflow）框架，
  這個框架可以應用到投資、HR 招聘、供應商採購、戰略決策...」

「DW 的核心原則是『計劃優先於執行』，
  蜂群投資正是這個理念的具體實現」

「為什麼蜂群要先『展示計劃』再『用戶確認』再『自動執行』？
  因為 DW 框架明確規定了決策的四個階段...」
```

**戰略優勢**：
- 🧠 展示系統性思維
- 🔗 連接多個應用場景
- 📚 展示思想深度
- 🚀 為計劃11、12 等新項目鋪路

**禁止**：
- ❌ 不要把 DW 當成具體產品
- ❌ 不要在開頭就講 DW（讀者會迷茫）
- ❌ 不要用 DW 替代蜂群作為主題

---

### 3️⃣ Ultracode（技術實現層）

**定義**：
Claude Code 的 xhigh effort 設置，支持動態工作流自動編排和多 Agent 並行執行。

**何時使用**：
- ✅ 說「這**不是理論，而是可以立刻用的**」
- ✅ 面向**工程師/科技決策者**時
- ✅ 強調**技術先進性和可實現性**
- ✅ 證明**我們用了最新的 AI 工程**

**使用示例**：
```markdown
「蜂群 Agent 是通過 Claude Code 的 Ultracode 功能
  實現的多 Agent 協作和自動決策...」

「這不是概念驗證或演示，而是使用 Ultracode 動態工作流
  自動編排實現的生產級決策系統」

「Ultracode 讓我們可以並行運行數百個 Agent，
  同時監控和控制整個決策過程」
```

**戰略優勢**：
- ✨ 增加可信度（用最新技術）
- 🏆 差異化競爭（技術領先）
- 🎓 吸引工程師和 CTO
- 🔐 表明未來路線圖

**禁止**：
- ❌ 不要在開頭或標題中提 Ultracode
- ❌ 不要假設普通讀者知道什麼是 Ultracode
- ❌ 不要讓 Ultracode 成為文章重點

## 🎬 不同場景的使用方式

### 場景1：普通讀者（大多數人）

**文章結構**：
```
標題：用蜂群 Agent 做投資決策
  ↓
開頭（3段）：
- 介紹蜂群是什麼（具體功能）
- 展示蜂群能做什麼（案例故事）
- 為什麼需要蜂群（問題引入）
  ↓
中間（5段）：
- DW 框架為什麼是最優方案
- 蜂群如何應用 DW 框架
- DW 的四大原則（計劃優先等）
  ↓
側邊欄或腳注：
「技術通過 Claude Code Ultracode 實現」
  ↓
結尾：
加入蜂群社群
```

**術語出現頻率**：
- 蜂群：20-30 次（主題）
- DW：5-8 次（說明原理）
- Ultracode：1-2 次（技術提及）

---

### 場景2：決策者/創業者

**文章結構**：
```
標題：用蜂群 Agent 實現自動化決策（適合決策者）
  ↓
開頭：
- 你面臨 100 個決策，蜂群可以自動化其中 80 個
- 蜂群已經在 X 家公司驗證
  ↓
中間：
- DW 框架確保決策的「計劃優先」（降低風險）
- 人始終保有最終決策權（Human in the Loop）
- 思想進程資產化（長期競爭力）
  ↓
結尾：
- 蜂群的成本模型和投資回報
- Ultracode 保證實時監控和靈活調整
```

**術語出現頻率**：
- 蜂群：25-35 次（主題）
- DW：8-12 次（框架信心）
- Ultracode：2-3 次（技術保障）

---

### 場景3：工程師/AI 愛好者

**文章結構**：
```
標題：用 Ultracode 動態工作流實現蜂群 Agent
  ↓
開頭：
- DW 框架的設計思想（多層協作）
- Ultracode 為什麼能完美實現 DW
  ↓
中間：
- 蜂群 Agent 的架構設計
- 如何使用 Ultracode 的 xhigh effort 和多 Agent

**術語出現頻率**：
- DW：15-20 次（框架）
- Ultracode：10-15 次（技術細節）
- 蜂群：10-15 次（應用案例）

## 📋 編寫檢查清單

在完成任何一篇系列文章時，檢查以下要點：

### ✅ 品牌一致性檢查
- [ ] 蜂群 Agent 在標題中出現
- [ ] 蜂群被定位為「我們的應用」（不是通用框架）
- [ ] 第一段清晰介紹了蜂群是什麼
- [ ] 蜂群的出現頻率明顯高於 DW 和 Ultracode

### ✅ 框架深度檢查
- [ ] 文章中至少解釋了 DW 的一個核心原則
- [ ] 讀者能理解「為什麼蜂群要這樣設計」
- [ ] DW 的通用性得到強調（可應用到其他領域）

### ✅ 技術驗證檢查
- [ ] Ultracode 被自然地提及（不生硬）
- [ ] 增加了技術可信度
- [ ] 普通讀者不會被技術細節嚇到

### ✅ 讀者體驗檢查
- [ ] 標題吸引人
- [ ] 開頭有故事感
- [ ] 中間有「啊哈」時刻（理解深度）
- [ ] 結尾有行動號召

```
重點：蜂群 Agent 本身
配合：DW 框架說明

## 💡 常見問題

**Q1：在什麼情況下應該重點說 DW？**
A：當你想解釋「為什麼蜂群這樣設計」或「蜂群能應用到其他領域」時。DW 是蜂群的底層邏輯。

**Q2：Ultracode 需要多詳細？**
A：普通讀者只需要知道「技術支持」即可。詳細技術細節留給工程師版本或進階教程。

**Q3：如果讀者不知道 Ultracode 怎麼辦？**
A：不需要詳細解釋。可以說「通過最新的 AI 工程技術實現」，如果讀者深入提問再詳細說。

**Q4：能用「DW Agent」代替「蜂群 Agent」嗎？**
A：不建議。蜂群是我們的品牌，DW 是技術框架。應該說「蜂群 Agent（基於 DW）」。
