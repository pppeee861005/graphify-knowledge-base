> Buzz 裡的 AI Agent，究竟可以替團隊做哪些事情？

  根據 Buzz 官方 README (https://github.com/block/buzz#stuff-you-do-in-buzz)，可以歸納成五種核心能力。

  ## 1. 詢問專案問題，而且答案有證據

  你可以問：

  > 我們以前遇過這個錯誤嗎？

  Agent 不只是憑模型記憶回答，而是搜尋工作空間的歷史訊息，找出過去的討論、原因和處理方法，再附上相關討論串。

  關鍵不是「AI 很會回答」，而是：

  > 答案可以被查證。

  這能降低 AI 一本正經地胡說的風險。

  ## 2. 讓 Agent 處理 Bug，但限制它的權限

  Agent 可以：

  - 搜尋 Bug 的相關紀錄
  - 檢查程式碼
  - 分析可能原因
  - 提出修正 patch
  - 執行指定工作流程

  但它不需要獲得整個系統的最高權限。它有自己的身分、金鑰與頻道成員資格。

  這就像邀請一位外部工程師進入特定專案，而不是直接把老闆的帳號密碼交給他。

  ## 3. 把功能分支變成協作房間

  這是 README 中很有特色的概念：Branch as Room。

  一個功能分支可以對應一個房間，裡面集中保存：

  - 開發需求
  - 程式 patch
  - CI 結果
  - Agent 初步審查
  - 人類審查意見
  - 最終合併決定

  以後想知道「這段程式當初為什麼這樣寫」，不用分別翻 Slack、GitHub 和 CI 平台。

  ## 4. 一次搜尋完整工作脈絡

  在普通開發流程中，資訊經常散落在不同地方：

  - 對話在 Slack
  - 程式碼在 GitHub
  - CI 在另一個平台
  - 核准可能只是一個表情符號

  Buzz 希望把它們表示成同一套事件，因此可以一起搜尋。

  真正的價值是保存「決策脈絡」，而不只是保存最後的程式碼。

  ## 5. Agent 可以操作工作空間

  Buzz 裡的 Agent 不只發送文字，還可以參與：

  - 頻道
  - Canvas
  - Workflow
  - 語音 huddle
  - Git 與程式審查
  - 其他 Agent 的協調

  這是 Buzz 與一般聊天機器人的最大差異：

  > 一般 AI 主要產生答案；Buzz Agent 則能在有身分、有權限、有稽核紀錄的情況下採取行動。

  ## 第一個實際情境

  假設你的程式出現錯誤：

  登入後偶爾會回傳 500

  理想的 Buzz 流程會是：

  1. 你在專案頻道提出問題。
  2. Agent 搜尋過去是否出現相同錯誤。
  3. Agent 找出相關討論、commit 與修正紀錄。
  4. Agent 檢查目前分支並提出 patch。
  5. CI 執行測試，把結果貼回房間。
  6. Agent 做初步程式審查。
  7. 由你決定是否核准及合併。
  8. 整段處理過程都能日後搜尋。

  所以這一節真正要傳達的是：

  > Buzz 想讓「對話、證據、程式修改、自動化與人工決策」發生在同一個可追溯空間。

  對你而言，最值得先掌握的應該是第一項：**讓 Agent 搜尋專案歷史，提供有來源的答案。**這最容易體驗，也最能看出 Buzz 與普通 AI 聊天工具的不同。
