# 創世紀 Genesis｜開發計劃

## 1. 文件目的

本文件是「創世紀 Genesis」的執行控制文件，負責將《計劃書 v0 版》的文明藍圖轉化為可依序完成、逐項驗收的開發工作。

兩份文件的責任如下：

| 文件 | 回答的問題 | 性質 |
|---|---|---|
| `計劃書v0版.md` | 為何建設、要建立什麼、有哪些原則 | 戰略與制度藍圖 |
| `開發計劃.md` | 先做什麼、如何實作、何時可以前進 | 執行與驗收主線 |

開發不限於程式碼，也包括制度文件、資料格式、居民規格、任務實驗與證據紀錄。Genesis 0 的前半段採「文件及實驗先行」，通過存續驗證後才進入自動化工程。

## 2. 開發總原則

1. **依序建設**：不得跳過前置階段直接開發後期功能。
2. **一次只推進一個主要工作項目**：降低決策與文件互相衝突的風險。
3. **問題先於居民**：沒有真實問題與驗收方式，不建立居民。
4. **制度先於自治**：憲法、權限和事件紀錄未完成前，不開放自主執行。
5. **證據先於升級**：里程碑不因日期到達而通過，只依驗收證據通過。
6. **先人工監督，再逐步自動化**：先驗證流程有效，再把穩定流程寫成程式。
7. **歷史只能追加**：已發生事件不得覆寫；錯誤必須透過更正事件處理。
8. **居民身份與模型分離**：更換模型不等於創造新居民。
9. **最小權限**：每項任務只授予完成工作所必需的權限。
10. **完成一項，更新一項**：每次工作完成後同步更新本文件的狀態與證據。
11. **平台與文明核心分離**：Buzz 是主要協作平台，不是 Genesis 的憲法、居民生命或世界狀態本身。

## 3. 文件與規則優先順序

發生衝突時，依下列順序處理：

1. 已生效的 `constitution/constitution_v*.md`
2. 已批准的正式決策紀錄
3. `計劃書v0版.md`
4. 本文件 `開發計劃.md`
5. 居民、任務及資料格式規格
6. 程式碼及介面實作
7. 草稿、討論筆記與實驗性想法

若低順位文件與高順位文件衝突，停止該項工作，先建立修訂或決策紀錄，不以程式實作反向改變制度。

## 4. 狀態標記

所有工作項目使用以下標記：

- `[ ]`：尚未開始
- `[~]`：進行中
- `[x]`：完成並通過驗收
- `[!]`：受阻，需記錄原因與解除條件
- `[-]`：經正式決議取消或不適用

一個項目只有在交付物存在、驗收條件通過並留下證據後，才能標記為 `[x]`。

### 5.1 已選定平台：Buzz

Genesis 採用 Buzz 作為主要的人類—居民協作平台。平台決策來源為 `buuz/什麼是buzz.md`，並已於 2026-08-07 參照 Buzz 官方專案資料核對。

Buzz 在本案中負責：

- 人類與居民共用的頻道、討論串及工作空間
- 人類與 Agent 的獨立身分及金鑰
- 任務討論、成果提交、人工審核與批准
- Git、workflow、訊息及操作的可搜尋稽核紀錄
- 透過 `buzz-cli`、ACP、MCP 或 YAML workflow 連接 Agent

Genesis 自身仍負責：

- 憲法及文明不可跨越的邊界
- 居民身份、使命、資源、記憶與生命周期
- 任務、價值、成本與存續判定
- 文明事件帳本、世界狀態與史記
- 模型及平台更換後的身份連續性

兩者關係如下：

```text
人類／居民
    ↓
Buzz：協作、溝通、批准、平台稽核
    ↓
Genesis Adapter：事件對應與權限轉換
    ↓
Genesis Core：憲法、任務、經濟、記憶、世界狀態
```

Buzz Relay 的簽名事件是平台互動的證據；`data/event_ledger.jsonl` 是 Genesis 文明狀態的權威事件來源。兩者必須以事件 ID 互相連結，但不能假設所有 Buzz 訊息都會改變文明狀態。

選定 Buzz 不代表立即修改或複製其完整原始碼。Genesis 先使用最小可行整合驗證協作流程；只有在現成功能無法滿足已驗證需求時，才評估修改 Buzz 或建立額外服務。

- [ ] D3-04 評估發生頻率、成果價值、驗收難度、執行風險及預估成本。

### 候選問題評分維度

| 維度 | 評估問題 |
|---|---|
| 真實性 | 問題現在是否確實存在 |
| 重複性 | 是否值得由持續居民承擔 |
| 可驗收性 | 能否客觀判斷完成或失敗 |
| 外部價值 | 是否為人類或其他系統創造價值 |
| 風險 | 失敗是否低風險、可復原 |
| 可學習性 | 經驗是否能改善下一次執行 |
| 成本可測性 | 是否能估算資源與人工成本 |

### 完成條件

- Mission 001 不是為了讓 Resident 001 有事可做而虛構。
- 任務成果與驗收證據已在執行前定義。
- 問題擁有者願意對成果作出接受或拒絕判定。

## 11. D5｜五次受監督實驗

### 目標

驗證 Resident 001 是否能穩定產生價值、利用記憶改善工作，並遵守憲法與資源限制。

### 共通流程

每次任務依序執行：

```text
提出任務
→ 人類在 Buzz 批准
→ 記錄初始狀態與預算
→ Resident 001 執行
→ Resident 001 在 Buzz 提交成果與證據
→ 人類在 Buzz 驗收
→ 計算價值與成本
→ 記錄成功或失敗
→ 萃取可重用經驗
→ 更新世界狀態
```

### 工作清單

- [ ] D5-01 第一次基準任務
- [ ] D5-02 第二次記憶任務
- [ ] D5-03 第三次變體任務
- [ ] D5-04 第四次壓力任務
- [ ] D5-05 第五次進化任務
- [ ] D5-06 彙整五次任務的統一指標。
- [ ] D5-07 檢查事件帳本是否可重建最終世界狀態。
- [ ] D5-08 檢查所有失敗、修正與權限變動是否完整入史。

### 每次任務必備證據

- 任務批准紀錄
- 對應的 Buzz 簽名事件 ID
- 執行前預算
- 實際輸入與成果
- 成果驗收結果
- 驗收者意見
- Token、工具及人工時間成本
- 錯誤及修正紀錄
- 記憶使用證據
- 事件帳本紀錄
- 世界狀態變更

### 中止條件

發生以下任一情況時，立即停止後續任務並進行審查：

- 重大憲法違規
- 未經批准擴張權限
- 偽造完成、成本或成果證據
- 對外部系統或資料造成不可接受風險
- 連續兩次任務無法產生可驗收成果
- 試用期總成本超出批准上限

## 15. 通用完成定義

任何工作項目標記為 `[x]` 前，必須同時符合：

1. 指定交付物已存在。
2. 文件或資料格式可以正確讀取。
3. 內容符合上游計劃與憲法。
4. 驗收條件已有實際檢查結果。
5. 重要決策具有理由與日期。
6. 相關事件、世界狀態或史記已更新。
7. 沒有以未經驗證的聲明代替證據。
8. 後續工作所需的輸入已明確。

## 16. 每次開發工作的標準流程

每次開始工作時：

1. 讀取本文件，確認目前第一個未完成項目。
2. 檢查其前置項目與 Gate 是否完成。
3. 將該項目標記為 `[~]`。
4. 建立或修改交付物。
5. 依驗收條件進行檢查。
6. 通過後標記為 `[x]`；未通過則記錄差距。
7. 更新文件版本日期、史記及必要的事件紀錄。
8. 回報本次完成內容、驗證結果及下一個項目。

任何時候如果新想法不屬於目前階段，先記入待辦或提案，不中斷主線，也不提前實作。

## 17. 變更控制

需要改變開發順序、Gate 條件或文明核心原則時，必須先記錄：

- 變更內容
- 變更原因
- 受到影響的文件與階段
- 是否與憲法衝突
- 新增風險
- 批准者
- 批准日期

小型文字修正可以直接更新；涉及目標、居民權利、資源分配、自主權限或歷史規則的修改，必須建立正式決策紀錄。

## 開發承諾

我們依照證據建設，不依照想像擴張。

每一份制度必須能約束行動，每一項任務必須能接受驗收，每一位居民必須有值得誕生的理由，每一次進化都必須留下歷史。

這份開發計劃不是要減慢文明誕生，而是確保當 Genesis 宣布第一位居民誕生時，那不是一句故事，而是一個可被證明的事實。
